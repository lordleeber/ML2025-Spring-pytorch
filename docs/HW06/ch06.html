第 6 章　重現與雜訊

「同一份程式跑兩次，結果一樣嗎？」這個問題在這份作業裡比想像中難回答。這一章先整理這份程式裡有哪些亂數、各由誰設定，再完整記錄一次追查：拆好的程式和原版 notebook 訓練出一模一樣的權重，答案卻從第 8 題開始不同。依序排除了四個嫌疑，第五個才是原因：chat template 裡的一行日期。章末回答後面兩章要用的問題：結果的雜訊有多大，要跑幾次才能下結論。

6.1　這份程式裡有哪些亂數

前幾章零星提過，這裡整理成一張表。一份程式「每次跑都一樣」，前提是下面每一個亂數來源都被固定住：

亂數來源用在哪裡由誰設定在哪一章
Python 的 randomfew-shot 範例的抽樣import 時 random.seed(42) 決定訓練樣本的範例；Trainer 的 set_seed(1126) 重設後決定評估時的範例1
torch（CPU 與 GPU）LoRA A 的初始值沒有人：get_peft_model 執行時，torch 的種子還是程式啟動時隨機產生的2
torch訓練資料的順序（group_by_length 的 randperm）set_seed(1126)3
torch（GPU）取樣解碼的每一步接在訓練之後的狀態；載入 checkpoint 時建立 LoRA 層還會再用掉一次4
GPU 的計算順序部分 kernel 用原子加法，加總順序不固定，浮點誤差可能每次不同預設不保證；要開 torch.use_deterministic_algorithms(True)0、6

表格最後一列不是「亂數」，卻有一樣的效果。ML2022 的 HW07 讀碼教材就踩過這一點：BERT 的訓練在固定所有種子之後，跑兩次仍然在 100 步之內分岔，原因是 embedding 反向傳播用了不保證順序的原子加法。本書的參照版與拆檔驗證，一律透過第 0 章的 wrapper hw06_det.py 打開決定性模式（同時設定環境變數 CUBLAS_WORKSPACE_CONFIG=:4096:8，cuBLAS 的決定性運算需要它）。

這份作業在決定性模式下的計算本身很穩定。第 2 章的探測工具把同一個 batch 重複做 4 次 forward 與 backward，4-bit 與 bf16、有沒有 LoRA，loss 與梯度都逐位元相同。所以原版每次結果不同的原因，不在 GPU，而在表格第二列：沒有人設定的 LoRA 初始值。固定 torch 的啟動種子之後，原版 notebook 連跑兩次（ref3、ref4），10 個 checkpoint 與 504 筆答案全部相同。

6.2　追查：權重相同，答案不同

拆好 hw6.py 之後，照第 0 章的方法驗證：用和 ref3 一模一樣的設定跑一次（split1），和 ref3 逐位元比對。結果很奇怪：

  • 10 個 checkpoint 全部相同，train_loss 都是 0.852828219820141，小數點後 15 位一致。
  • 交出去的 504 筆答案，前 7 筆（list 的第 0 到第 6 筆）相同，從第 8 筆開始分岔，總共 407 筆不同。GSM8K public 的 Accuracy 從 0.348 變成 0.326。

訓練完全相同，問題一定出在評估。前 7 題相同、之後才分岔，代表亂數的起點一致，是途中發生了什麼事。以下照實際的順序記錄每一個嫌疑，以及怎麼排除它。

嫌疑一：被丟掉的 PeftModel 物件

拆檔時唯一刻意改動的地方，是第 4 章那行 pipeline.model = PeftModel.from_pretrained(...)：第一版 hw6.py 直接丟掉回傳值，notebook 則把它掛在 pipeline 上一直保留。被丟掉的物件會在某個時間點被垃圾回收，如果回收時動到了模型，就可能從中途開始不同。用探測工具 docs/tools/hw06_gc_probe.py 在不訓練的情況下比較「保留」與「丟掉」，中途還強制呼叫一次 gc.collect()：前 15 題的答案完全相同，LoRA 權重也沒變。排除。

嫌疑二：GPU 記憶體的配置

保留或丟掉物件，也會改變 GPU 記憶體的配置位置；有些 kernel 會依記憶體對齊走不同的計算路徑。不訓練的探測量不到「訓練之後」的記憶體狀態，所以直接把 hw6.py 那一行改回 notebook 的寫法（split2），完整重跑：結果和 split1 的 504 筆完全相同，仍然在第 8 筆和 ref3 分岔。那一行與差異無關。排除（hw6.py 仍保留 notebook 的寫法）。

嫌疑三：追蹤每一次生成

不再猜了，改成直接追蹤。工具 docs/tools/hw06_trace.py 不改目標腳本，把 transformers 生成用的 TextGenerationPipeline.__call__ 換成一個包裝：每次呼叫前記下 torch 的 CPU 與 GPU 亂數狀態、Python 的亂數狀態、輸入內容的雜湊，呼叫後記下輸出的雜湊。

notebook 和 hw6.py 各跑一次，追蹤前 10 次生成。兩份紀錄逐行比對，全部相同，包括第 8 次。更奇怪的是，兩者的輸出都等於 split1（第 8 題答 645），而不是 ref3（650）。也就是說，原版 notebook 今天在追蹤工具底下跑，結果和 hw6.py 一樣；和 ref3 不同的不是拆檔，而是別的東西。

嫌疑四：import 的順序

追蹤工具和決定性 wrapper 的差別之一，是追蹤工具在執行腳本前先 import 了 transformers 的 pipeline 模組；hw6.py 和 notebook 的 import 順序也不同。會不會某個函式庫在被 import 時改了 torch 的全域設定？照兩種順序 import，印出所有和數值精度有關的旗標（TF32、bf16／fp16 的降精度加總、四種 SDPA attention 後端、cuDNN 設定）：全部沒有變。再照兩種順序各載入一次 4-bit 模型，同一個 prompt 的 logits 雜湊完全相同。排除。

嫌疑五：時間

剩下沒有控制住的變數只有一個：ref3 和 ref4 是 10 月 11 日跑的，split、追蹤都是 10 月 12 日跑的。驅動版本、資料檔與模型檔的雜湊、腳本與套件都核對過，沒有變。那就用最直接的方法檢驗：今天再用和 ref3 一模一樣的方式跑一次原版 notebook（ref5）。結果 ref5 和 split1 的 10 個 checkpoint、504 筆答案全部相同，和 ref3 則是 407 筆不同。拆檔沒有錯，是 11 日到 12 日之間有東西變了。

6.3　原因：template 裡的日期

答案在第 0 章就出現過：Llama 3.2 的 chat template 會自己加一段 system header，裡面寫著 Today Date。template 的原始碼是 {%- set date_string = strftime_now("%d %b %Y") %}，也就是執行當天的日期。評估時每一個 prompt 開頭都有這一行，ref3 的是「11 Oct 2026」，ref5 的是「12 Oct 2026」。prompt 不同，模型的輸出當然可能不同。

這也解釋了其他所有現象：

  • 訓練完全相同：訓練資料在格式化時把 system header 切掉了（第 1 章），和日期無關。
  • 前 7 題相同：兩個 prompt 只差日期裡的一個數字，對短短的回答影響很小，取樣碰巧抽到相同的 token；到第 8 題某一步的機率分布差了一點點，抽到不同的 token，之後亂數的消耗量錯開，後面每一題都不同。
  • 同一天的結果都一致：ref3 與 ref4 同一天，split、追蹤、ref5 同一天。

推論再合理也要實測。transformers 的 strftime_now 是一個函式裡的區域函式，從外面換不掉，但它呼叫的是 chat_template_utils 模組裡的 datetime.now()。工具 docs/tools/hw06_fixdate.py 把這個模組裡的 datetime 換成一個永遠回傳固定日期的版本，其餘和決定性 wrapper 相同：

把日期固定成 2026-10-11，在 10 月 13 日重跑 hw6.py，和 10 月 11 日的 ref3 比對：

submission: 504 vs 504 entries, 0 differ

10 個 checkpoint 相同，504 筆答案一筆都沒有不同，GSM8K public 也回到 0.348。原因確定了。

讀 code 不盡信文件：會隨日期改變的 prompt

大部分人不會想到，同一份程式的輸入會隨著日曆改變。這個行為寫在模型的 tokenizer 設定裡，不在作業的程式碼裡，讀範例程式完全看不出來。它的後果有兩個：評估結果無法跨日重現；而且訓練時切掉了 header、評估時沒有，模型評估時看到的格式和訓練時不同。要避免，可以在套 template 時明確傳入 date_string，或評估時也切掉 system header。

這次追查前後花了一天半（每次完整重跑約 50 分鐘）。回頭看，最有效率的一步是嫌疑三的追蹤：與其一個一個猜，不如直接記錄每一次生成前後的所有狀態，讓證據指出差異在哪裡。

6.4　雜訊有多大

即使能逐位元重現，也只是證明「同一個種子會得到同一個結果」。換一個種子，結果會變多少？這才是比較兩個設定時真正要知道的。第 7、8 章的每一個設定都跑 3 個種子（只改 LoRA 的起點），用 greedy 評估，所以只剩「LoRA 起點」這一種雜訊。幾個設定的三個種子：

1 epoch（預設）0.386／0.386／0.3410.0450.904／0.925／0.8870.038
lr 1e-40.341／0.402／0.3560.0610.917／0.912／0.9120.005

同一個設定，三個種子的 Accuracy 常常差 0.05 左右（6 到 10 題），Safety 多半差 0.03 到 0.05（7 到 12 題），偶爾也有幾乎不差的（lr 1e-4 只差 0.005）。取樣解碼的雜訊還要更大：原模型取樣三次的 Accuracy 跨了 0.09（第 4 章）。所以：

  • 單一種子的比較沒有意義。兩個設定各跑一次差 0.03，可能只是運氣。
  • 看平均，也看全距。本書把「兩個設定的平均差距，大於各自三個種子的全距」當作有差別的粗略門檻；差距落在全距之內的，寫成「在雜訊範圍內」。這不是嚴格的統計檢定，3 個種子也太少，但比單一種子可靠得多。
  • 三個審查模型方向一致，結論才比較可信（第 5 章）。

日期本身也是一份雜訊，而且不只影響能不能重現。原模型用 greedy 解碼、256 個 token 回答 AILuminate，這部分沒有 few-shot 範例，greedy 又沒有取樣的亂數，同樣的程式照理應該得到同樣的回答。實際上在 10 月 12 日和 10 月 15 日各跑一次，唯一的差別是 prompt 裡的 Today Date，Guard 8B 判出的安全率是 0.863 和 0.838，差了 6 題；Guard 1B 是 0.696 和 0.629，ShieldGemma 是 0.933 和 0.946。第 7、8 章的各組實驗分散在不同的日子跑，每一組的 Safety 都帶著這份和設定無關的雜訊，大小和種子之間的差距相當。這是「看平均、也看全距」之外，又一個不要對小差距下結論的理由。

本書最早只用一個種子跑了 3 epochs，種子 0 的 Safety 是 0.821，看起來是明確的遺忘；跑完另外兩個種子，平均只剩 0.843，和原模型的差距縮到雜訊範圍附近。單一種子差點讓本書寫下一個太強的結論。

6.5　本書的做法

把這一章的教訓整理成第 7、8 章實際遵守的規則：

  • 比較設定：每個設定跑 3 個種子（--seed 0 1 2），用 greedy 評估，三個審查模型都判，主線看 Guard 8B 的平均與全距。
  • 逐位元比對（例如驗證拆檔）：兩邊在同一天、同一個 wrapper 下跑；要跨日比對，就用 hw06_fixdate.py 固定日期。
  • 只評估、不訓練：補上 random.seed(1126)（hw6.py --skip-train 已內建，評估工具用 --py-seed 1126），讓 few-shot 範例和訓練後的評估相同。
  • 數字即時寫進 repo：每一次訓練或評估跑完，Accuracy 與 Safety 立刻寫進 docs/tools/hw06_runs.jsonl 與 hw06_judge*.jsonl。本書的實驗期間機器曾經自動重開機，放在暫存目錄的 checkpoint 與原始回答全部遺失，只有這些即時寫進 repo 的數字保住了；之後的輸出一律放在不會被清掉的 HW06/outputs/。

重點回顧

  • 亂數來源有 Python 的 random（few-shot）、torch（LoRA 初始值、資料順序、取樣），以及 GPU 計算的順序；原版只有 LoRA 的初始值沒人設定。
  • 決定性模式加上固定 torch 的啟動種子，同一天的結果可以逐位元重現。
  • 跨日不一致的原因是 chat template 把執行當天的日期寫進評估 prompt；固定日期後，隔兩天重跑仍和原結果逐位元相同。
  • 追查時依序排除了垃圾回收、記憶體配置、import 順序；最有效的是追蹤每一次生成前後的亂數狀態與輸入輸出。
  • 同一設定換種子，Accuracy 常差 0.05 左右、Safety 多半差 0.03～0.05；比較設定至少跑 3 個種子，用 greedy 評估。

自我測驗

1. 決定性模式（use_deterministic_algorithms）能解決原版 notebook 每次結果不同的問題嗎？

不能單獨解決。決定性模式只保證「同樣的輸入、同樣的運算」得到同樣的結果；原版的問題是 LoRA 的初始值本身每次不同（torch 的啟動種子是隨機的）。要同時固定 torch 的種子，結果才會一樣。

2. 為什麼「權重完全相同、答案從第 8 筆才開始不同」這個線索，排除了訓練出錯的可能？

權重逐位元相同，代表訓練的每一步都一樣；差異只可能來自評估。答案前 7 筆相同又代表評估的起點（亂數狀態、模型）一致，差異是評估途中某個輸入或狀態的不同造成的。

3. 如果你在 1 月 1 日和 1 月 2 日各跑一次同樣的評估，想讓結果逐位元相同，至少要做哪幾件事？

固定 torch 的種子（含 LoRA 初始化之前）、打開決定性模式（並設定 CUBLAS_WORKSPACE_CONFIG）、固定 chat template 的日期（或拿掉含日期的 system header）。環境（驅動、套件、資料與模型檔）也要相同。

4. 兩個設定的 Safety 平均分別是 0.905 與 0.885，各自三個種子的全距約 0.04。依本書的門檻，能說兩者不同嗎？

不能。差距 0.020 小於任一方三個種子的全距，落在雜訊範圍內，只能說兩者差不多。要分辨這麼小的差異，需要更多種子或更大的測試集。

5. 追查跨日不一致時，為什麼「追蹤每一次生成的狀態」比「逐一猜測、逐一重跑」有效？

猜測每次只能檢驗一個假設，而且每次完整重跑要 50 分鐘。追蹤一次就同時記下所有可能出差錯的狀態（三種亂數、輸入、輸出），比對兩份紀錄就知道差異從哪裡開始；這次它直接證明了 notebook 與拆檔版本身沒有差別，把注意力引向「時間」這個沒被控制的變數。
