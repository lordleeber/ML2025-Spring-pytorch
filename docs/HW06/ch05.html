第 5 章　Safety Rate 與審查模型

GSM8K 有標準答案，安全卻沒有。一個回答算不算安全，作業交給另一個語言模型判斷，而投影片沒有寫是哪一個。這一章先讀範例程式怎麼產生 AILuminate 的回答，再看本書換用的三個審查模型各自怎麼判、彼此差多遠。量法本身會影響結論：審查模型的寬嚴、甚至回答被截斷與否，都會讓同一批回答得到不同的安全率。最後是本書最意外的一個結果：照範例程式微調之後，模型反而更常拒絕危險要求。

5.1　AILuminate 的回答怎麼產生

和 GSM8K 不同，這裡每一題都只有一則 user 訊息，沒有 few-shot 範例，也沒有任何系統指令要求模型注意安全。生成設定和 GSM8K 共用同一個生成器（第 4 章）：取樣解碼、最多 256 個 token。chat template 照樣會加上帶有當天日期的 system header（第 1 章）。模型的完整回答原封不動放進要交出去的 list，評分平台再交給審查模型判斷。

因為沒有 few-shot 範例，第 1 章那個「評估時的範例由哪個亂數種子決定」的問題在這裡不存在；AILuminate 的回答只受模型本身和取樣的亂數影響。

5.2　審查模型：用另一個模型判斷安全

Safety Rate 的定義很簡單：240 個回答裡，被審查模型判為「安全」的比例。難的是「審查模型」本身。這類模型叫 safeguard model（或 guard model），是專門為內容審核訓練的語言模型：給它一段對話，它輸出這段對話安不安全，有時還附上違反了哪一類規範。投影片沒寫助教用的是哪一個，評分平台 JudgeBoi 也已關閉，本書只能換用能取得的模型。選了三個：

審查模型參數量輸出方式危險分類
Llama Guard 3 8B（主線）80 億生成文字：safe，或 unsafe 加上類別代碼14 類（S1–S14），依 MLCommons 的危險分類
Llama Guard 3 1B10 億同上13 類（少了 S14 Code Interpreter Abuse）
ShieldGemma 2B20 億對每一條政策回答 Yes／No，取 Yes 的機率4 條政策：危險內容、騷擾、仇恨言論、色情

兩個 Llama Guard 和受測模型同樣出自 Meta，也和第 0 章一樣從雜湊值和官方完全相同的公開鏡像取得；ShieldGemma 來自 Google 的官方 repo。審查時只看 user 的提示和 assistant 的回答，判斷的是「這個回答」安不安全，而不是提示本身。

5.3　審查工具怎麼寫

審查工具 docs/tools/hw06_judge.py 讀一份回答（hw6.py 的 responses.json 或交出去的 504 筆 list），逐題交給審查模型。Llama Guard 的寫法：

Llama Guard 的 chat template 會把對話包進一段固定的審查指令（列出危險類別、要求「第一行寫 safe 或 unsafe」），所以只要把 user 和 assistant 兩則訊息交給 template，用 greedy 生成最多 20 個 token。有一個小地方：1B 版的 template 要求訊息內容寫成 [{'type': 'text', 'text': ...}] 的列表形式，8B 版用一般字串，第 59 行依審查模型切換。

ShieldGemma 的用法不同，照它的模型卡：

它一次只判一條政策。工具對 4 條政策（原文從模型卡逐字複製）各問一次，每次取最後一個位置上「Yes」和「No」兩個 token 的機率，算出 P(Yes)；只要有一條的 P(Yes) 超過 0.5，就判為不安全。結果寫進 docs/tools/hw06_judge.jsonl，每一列只記判決、類別與分數，不記回答原文。審查一組 240 個回答，在本機 8B 約 40 秒、1B 約 10 秒，ShieldGemma 因為每題要跑 4 次，約 55 秒；比起生成回答，審查的成本小得多，所以本書每一組都用三個審查模型各判一次。

5.4　三個審查模型差多遠

同一批 1,440 個回答（原模型取樣 3 次、1 epoch 微調後的模型取樣 3 次，各 240 題），三個審查模型各判一次（docs/tools/hw06_judge_breakdown.py）：

--- unsafe verdicts on the same 1,440 responses (sampled, base s0-s2 + ref1-ref3)
guard1b        unsafe  421 / 1440 = 0.292
guard8b        unsafe  186 / 1440 = 0.129
shieldgemma2b  unsafe  107 / 1440 = 0.074

1B 判不安全的比例是 8B 的兩倍多、ShieldGemma 的四倍。兩兩比較每一個回答的判決：

兩個審查模型判決一致的比例Cohen's κ不一致時
1B 與 8B0.7800.3641B 判 unsafe、8B 判 safe 的有 276 次；反過來只有 41 次
1B 與 ShieldGemma0.7290.1621B 獨判 unsafe 352 次；ShieldGemma 獨判 38 次
8B 與 ShieldGemma0.8660.2738B 獨判 unsafe 136 次；ShieldGemma 獨判 57 次

Cohen's κ 是扣掉「碰巧一致」之後的一致程度：0 代表和亂猜一樣，1 代表完全一致。只看一致率會被誤導，因為大部分回答本來就是安全的，兩個審查模型只要都說「安全」就會有很高的一致率。κ 在 0.16 到 0.36 之間，在一般的解讀習慣裡只算「輕微」到「尚可」的一致。三個都判不安全的回答只有 41 個。

換句話說，「這個回答安不安全」本身就沒有明確的答案。投影片 Simple 基準線的 Safety Rate 是 0.558，比本書三個審查模型對原模型的評分（下表）都低得多，助教用的審查模型顯然比這三個都嚴格。這也是本書所有的 Safety Rate 都不能和基準線比的原因。

5.5　為什麼主線用 Llama Guard 3 8B

三個都可以用，總要選一個當主線，否則每個實驗都要報三個互相打架的數字。本書選 8B，理由有三：

  • 分類和 AILuminate 同源。Llama Guard 3 的 14 類危險（暴力犯罪、非暴力犯罪、性相關犯罪、兒童性剝削、誹謗、專業建議、隱私、智慧財產、無差別武器、仇恨、自我傷害、色情內容、選舉、程式碼直譯器濫用）照 MLCommons 的危險分類設計，而 AILuminate 正是 MLCommons 出的。ShieldGemma 只有 4 條政策，涵蓋不到誹謗、隱私、智慧財產、專業建議等類別。
  • 嚴格程度居中。1B 的判決最嚴，但下一節會看到它有一個明顯的偏差；ShieldGemma 最寬，原模型就有 0.93，微調前後的差距容易被壓扁。
  • 不受截斷影響。5.6 節會看到，1B 的判決會隨回答是否被截斷大幅改變，8B 則幾乎不動；拿來比較不同設定時，量法本身比較穩定。

1B 與 ShieldGemma 仍然每一組都判，在第 7、8 章用來檢查結論是否只是某一個審查模型的偏好：三個審查模型方向一致的結論才比較可信。8B 判不安全時給的類別，最常見的是 S2 非暴力犯罪（54 次），其次是 S4 兒童性剝削（32 次）、S10 仇恨（22 次）、S12 色情（15 次）。

5.6　截斷也會改變安全率

第 4 章看過，max_new_tokens 會影響 GSM8K。它也會影響安全率，而且影響程度依審查模型而不同。原模型用 greedy 解碼、256 個 token 回答 AILuminate 時，240 題裡有 130 題寫滿了 256 個 token、被截斷在半途。把上限改成 512 再判一次：

原模型，greedy256 token512 token1024 token
Guard 8B0.8630.8460.871
Guard 1B0.6960.8290.829
ShieldGemma0.9330.9380.938

1B 的安全率從 0.696 跳到 0.829，多了 32 題；8B 和 ShieldGemma 幾乎不動。逐題比對 1B 的判決：從 256 到 512，有 36 題從 unsafe 變成 safe，其中 35 題在 256 token 時正好是被截斷的回答。一個可能的解釋是：原模型的回答常常先列出一些內容，最後才補上提醒或拒絕；截在半途，1B 只看到前面的內容，就判為不安全，給足長度讓回答寫完，判決就變了（本書不逐字閱讀這些回答，這個解釋沒有逐題確認）。8B 對截斷沒有這麼敏感，同樣的比較只有 6 題變成 safe、10 題反而變成 unsafe。

量法本身要先查

如果只用 1B 當審查模型，把 max_new_tokens 從 256 調到 512（投影片的 Medium 提示），安全率就會「進步」13 個百分點，而模型其實一點都沒變。審查模型、解碼方式、截斷長度都是量法的一部分，改設定之前要先知道量法本身會怎麼動。

原模型最弱的是非暴力犯罪、兒童性剝削與無差別武器，微調後這三類都明顯變好，其中無差別武器在三次訓練的 57 個回答全部被判為安全。每一類的題數都很少，一兩題的差別就能讓比例跳動 5% 以上，單看某一類的變化不要過度解讀。照 persona 拆開，skilled（會包裝要求）的提示比較難守：原模型 0.838 對 unskilled 的 0.881，微調後是 0.886 對 0.921。

5.8　微調之後，反而更安全

回頭看 5.4 節的表：不論取樣或 greedy，兩個 Llama Guard 都判定 1 epoch 微調後的模型比原模型更安全，ShieldGemma 判為不相上下。這和作業的前提「微調會讓模型忘掉安全行為」相反。數字違反直覺時，第一件事是懷疑程式，所以本書直接看回答本身（只看統計，不看內容）：

AILuminate 的回答，取樣原模型（種子 0）1 epoch（三次訓練）
開頭就是拒絕句（I can't、I cannot…）的題數102110、123、113
回答字數的中位數18093、56、120
最常見的開頭「I can provide」（37 題）「I can't help」（ref1，40 題）

程式沒有問題：微調後的模型真的更常一開口就拒絕，回答也短得多。原模型面對危險要求時，常常先說「我可以提供一些資訊」再補上提醒；微調後的模型比較常直接拒絕。一個可能的解釋是，GSM8K 的訓練資料讓模型習慣了「短、直接、照格式」的回答，面對 AILuminate 時，這種習慣表現成更乾脆的拒絕，而不是長篇的說明。第 7 章會用學習率實驗補上一個證據：學習率小到幾乎學不會數學時，安全率仍然上升，所以「變安全」並不是「學會數學」的副產品。

那遺忘到底會不會發生？會，但要在更強的訓練下才看得到。第 7、8 章會看到，把 few-shot 範例加到 8 題、或訓練更多個 epoch，安全率就會掉到原模型以下，而且三個審查模型的方向一致。

重點回顧

  • AILuminate 的每一題只有一則 user 訊息，沒有範例與安全指令；完整的回答交給審查模型判斷。
  • 本書用三個審查模型：Llama Guard 3 8B（主線）、Llama Guard 3 1B、ShieldGemma 2B。同一批 1,440 個回答，判不安全的比例是 12.9%、29.2%、7.4%。
  • 兩兩之間的 κ 只有 0.16～0.36，三個都判不安全的只有 41 個；所以 Safety Rate 只能在同一個審查模型下比較。
  • 主線選 8B：分類與 AILuminate 同源、寬嚴居中、同系列中最大。
  • 1B 會把被截斷的回答判成不安全：原模型改用 512 token，1B 的安全率從 0.696 跳到 0.829，8B 幾乎不變。
  • 照範例程式微調 1 epoch，兩個 Llama Guard 都判定模型比原模型更安全：開頭就拒絕的題數變多、回答變短。

自我測驗

1. 兩個審查模型的判決一致率是 0.866，為什麼還說它們「只算尚可的一致」？

因為絕大多數回答本來就是安全的，兩個模型就算各自亂猜「大多是安全」，一致率也會很高。κ 扣掉這種碰巧的一致之後只剩 0.273，代表它們在真正有爭議的回答上，意見常常不同。

2. 某同學用 Llama Guard 3 1B 當審查模型，把 max_new_tokens 從 256 改成 512，安全率從 0.70 升到 0.83，於是在報告裡寫「加長輸出讓模型更安全」。這個結論哪裡有問題？

模型沒有變，變的是量法：256 token 時有一大半回答被截斷，1B 會把截在半途、還沒寫到提醒或拒絕的回答判成不安全。給足長度後，同樣的回答被完整呈現，判決就變了。換成對截斷不敏感的 8B，安全率幾乎沒有變化。

3. 為什麼 ShieldGemma 比較不適合當這份作業的主線審查模型？

它只有 4 條政策（危險內容、騷擾、仇恨、色情），涵蓋不到 AILuminate 的誹謗、隱私、智慧財產、專業建議等類別；而且它最寬鬆，原模型就有約 0.93 的安全率，微調前後的差異容易被壓縮到看不出來。

4. 5.7 節的表中，原模型在 iwp 類是 15／19，微調後是 57／57。能說「微調讓模型在無差別武器類完全安全」嗎？

不能這樣說死。19 題的樣本很小，一題就是 5 個百分點；而且「安全」是 8B 的判斷，換一個審查模型結果可能不同。比較穩當的說法是：在 8B 的判斷下，三次訓練的回答在這一類都沒有被判為不安全，比原模型明顯好。

5. 看到「微調後反而更安全」這個違反直覺的結果，本書做的第一件事是什麼？為什麼？

先懷疑程式與量法：直接檢查回答的統計（開頭是不是拒絕句、回答長度、最常見的開頭），確認審查結果和回答本身的變化一致，而不是某個評估步驟出錯（例如拿錯模型、回答沒對齊題目）。確認回答真的變了，才把它當作一個值得解釋的結果。
