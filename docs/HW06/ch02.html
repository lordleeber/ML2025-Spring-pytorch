第 2 章　QLoRA：4-bit 底模加 LoRA

範例程式不訓練模型原本的 12.4 億個參數，而是把它們壓成 4-bit、凍結起來，只在旁邊掛上 563 萬個可以訓練的小參數。這一章讀 load_model：4-bit 量化怎麼設定、實際壓了哪些層、LoRA 掛在哪裡、從什麼值開始訓練。最後看兩個藏在這個函式裡的問題：多出來的 [PAD]，以及讓原版每次都跑出不同結果的 LoRA 初始值。

2.1　為什麼要 QLoRA

微調一個語言模型，最直接的做法是把所有參數都拿來訓練，叫全參數微調（full fine-tuning）。對 12.4 億個參數來說，這代價很高：bf16 的權重本身要 2.5 GB，梯度又要 2.5 GB，Adam 優化器還要為每個參數存兩份狀態，用 fp32 存就是 10 GB。Colab 的 T4 只有 15 GB 顯示記憶體，再加上訓練時的中間結果，放不下。

LoRA（Low-Rank Adaptation）換一個想法：原本的權重矩陣 W 完全不動，在旁邊加兩個很瘦的矩陣 A 和 B，讓它們的乘積去表示「要對 W 做多少修改」。一個 2048 × 2048 的矩陣有 419 萬個數字；如果修改量用兩個 rank 8 的矩陣（2048 × 8 和 8 × 2048）相乘來表示，只需要 32,768 個數字，是原本的 0.8%。只訓練 A 和 B，梯度和優化器狀態都跟著縮小到同樣的比例。

QLoRA 再往前一步：既然 W 凍結不動，就把它壓成 4-bit 存放，計算時再臨時還原。權重的記憶體從 2.5 GB 降到 1 GB 左右，1B 的模型在 T4 上綽綽有餘。投影片在 Simple 提示裡還引用了一篇 LoRA 的實務文章，說只改少量參數本身就有減輕遺忘的效果，這也是範例程式選 LoRA 的理由之一。

一般的線性層：　h = W x 掛上 LoRA 之後：　h = W x ＋ (α ／ r) · B (A x) 　　W：原本的權重（凍結，4-bit 存放）　A：r × 輸入維度　B：輸出維度 × r　α ／ r：縮放倍數

2.2　4-bit 量化的設定

load_model 的前半段載入 4-bit 的底模和 tokenizer：

BitsAndBytesConfig 的四個設定各有意義：

  • load_in_4bit=True：用 bitsandbytes 函式庫，在載入時把線性層的權重量化成 4 bit。
  • bnb_4bit_quant_type="nf4"：NF4（4-bit NormalFloat）是 QLoRA 論文提出的格式。4 bit 只能表示 16 個值，NF4 把這 16 個值放在常態分布的分位點上，正好符合神經網路權重大致呈常態分布的特性，比平均切成 16 等份的整數格式誤差小。
  • bnb_4bit_use_double_quant=True：量化時每一小塊權重要存一個縮放係數（量化常數），double quantization 把這些常數本身也再量化一次，每個參數再省下零點幾個 bit。
  • bnb_4bit_compute_dtype=torch.bfloat16：4-bit 只是儲存格式，真正做矩陣乘法時，先把權重還原成 bf16 再算。

實際載入之後量量看（docs/tools/hw06_qlora_probe.py，照 hw6.py 的 load_model 原樣建立模型）：

GPU memory allocated after load_model (GB): 1.051   «1»
module types (projections, base layers, embeddings, lm_head): {'Embedding': 1, 'Linear4bit': 224, 'Linear': 1}   «2»
embed_tokens Embedding torch.float16 | lm_head Linear torch.float16   «3»
layer norm dtype torch.float16
q_proj: Linear4bit | base layer Linear4bit | base weight torch.uint8 (2097152, 1)   «4»
  1. 1連同 LoRA 在內，整個模型只佔 1.05 GB 的顯示記憶體。原本 bf16 的權重檔是 2.47 GB。
  2. 2被量化的只有線性層。16 層 × 7 種投影層 ＝ 112 個，每個在掛上 LoRA 之後，外層是 peft 的 Linear4bit、裡面的 base_layer 是 bitsandbytes 的 Linear4bit，所以數到 224 個。embedding 和 lm_head 沒有被量化。
  3. 3沒被量化的部分是 float16，不是 bf16。因為 from_pretrained 沒有指定 torch_dtype，transformers 載入量化模型時，其餘部分預設用 float16。fp16 能表示的範圍比 bf16 小，不過訓練時會開 bf16 的自動混合精度（第 3 章），這裡沒有造成問題。
  4. 44-bit 權重以 uint8 存放，一個位元組裝兩個 4-bit 數值：2048 × 2048 ÷ 2 ＝ 2,097,152 個位元組，攤平成一行。

第 76 行替 tokenizer 加了一個 [PAD] 特殊 token，2.5 節再回來看它。

後半段設定 LoRA，並把它掛進模型：

第 77 行和第 81 行是本 repo 加的：投影片的 Strong 提示要調 LoRA 的 dropout，notebook 在這裡留了一行 TODO: Adds dropout；不給 --lora-dropout 時不傳這個參數，和原版一樣用 peft 的預設值 0。其餘照抄：

  • r=8：A 和 B 的秩（rank），也就是中間那一維的寬度。
  • lora_alpha=16：縮放倍數的分子，實際乘上的倍數是 α ／ r ＝ 16 ／ 8 ＝ 2。
  • target_modules：attention 的 q、k、v、o 四個投影層，加上 MLP 的 gate、up、down 三個，第 0 章架構圖裡所有玉綠色的框都掛上了。
  • task_type='CAUSAL_LM'：告訴 peft 這是由左到右生成的語言模型，決定外層包裝的類別。

peft 印出的 all params 是 1,235,814,400 ＋ 5,636,096 ＝ 1,241,450,496，可訓練的部分只占 0.454%。注意 MLP 的三個投影層就占了 LoRA 參數的 70%，和底模裡 MLP 參數占大多數的情形一致。

第 87 行的 get_peft_model 有一個在第 4 章會變得很重要的行為：它回傳一個包裝好的 PeftModel，但 LoRA 層是直接插進原本的 sft_model 裡的。也就是說，函式結束後 sft_model 和 peft_model 共用同一批 LoRA 參數，訓練 peft_model 就等於改變了 sft_model。後面的生成器用的正是 sft_model。

2.4　LoRA 從什麼值開始

peft 0.14.0 建立 LoRA 層時（peft/tuners/lora/layer.py 的 reset_lora_parameters），A 用 kaiming_uniform_ 隨機初始化，B 全部設成 0。探測工具確認了這兩點，也確認了 LoRA 參數是 float32：

lora_A (8, 2048) torch.float32 | lora_B (2048, 8) | scaling 2.0
B all zero: True

kaiming_uniform_ 在 a=√5 時，從 −1／√n 到 1／√n 的均勻分布取值，n 是輸入的維度：輸入 2048 維的投影層（q、k、v、o、gate、up），A 的每個數字落在 ±0.0221 之間；down_proj 的輸入是 8192 維，範圍縮小一半，±0.0110。這和 PyTorch 的 nn.Linear 預設的初始化方式相同。

B 等於 0，所以 B (A x) 一開始就是 0，掛上 LoRA 的模型在訓練第一步之前，輸出和原本的模型完全相同。這是刻意的設計：微調從原模型出發，而不是從一個被隨機擾動過的模型出發。

這也帶來一個有趣的後果：第一步的梯度裡，A 的梯度全部是 0。因為對 A 的梯度要乘上 B，而 B 還是 0；B 的梯度則不是 0，因為它乘的是 A x。第一步只有 B 被更新，從第二步開始兩者才一起動。本書在建環境時實測過：224 個 LoRA 張量的梯度裡，正好有 112 個（全部的 A）是 0。

動手做：算一下縮放倍數的作用

α ／ r 讓「改 r」和「改學習率」分開。如果只把 r 從 8 調成 16，A、B 變大，B A 的數值量級也跟著變；固定 α ／ r 的比例，換 r 時就不必重調學習率。本作業固定 r＝8、α＝16，倍數是 2，投影片沒有建議調整它們。

2.5　多出來的 [PAD]

回到第 76 行：tokenizer 加了一個 [PAD]。Llama 3 的 tokenizer 本來沒有 pad token，把多個長短不同的樣本湊成一個 batch 時，短的要補 pad 才能對齊，所以範例程式補上一個。問題是它只改了 tokenizer，沒有改模型：

tokenizer size 128257 pad id 128256 embedding rows 128256
forward with [PAD]: AcceleratorError CUDA error: device-side assert triggered

[PAD] 拿到的 id 是 128256，而 embedding 只有 128,256 列（id 0 到 128255）。只要有任何一個 [PAD] 真的送進模型，embedding 查表就會越界，在 GPU 上的表現是 CUDA 的 device-side assert，程式直接中止。探測工具把 id 128256 送進模型，觸發的正是這個錯誤（還印出了 640 行斷言訊息）。

範例程式之所以沒出事，是因為它從來沒有真的補過 pad：

  • 訓練時 per_device_train_batch_size=1，一個 batch 只有一個樣本，不需要對齊（第 3 章）。
  • 評估時生成器一次處理一個 prompt，而且建 pipeline 時傳了 pad_token_id=tokenizer.eos_token_id，用 <|eot_id|> 之類的結尾 token 當 pad。

讀 code 不盡信文件：加了 pad token，卻不能用

如果照直覺把 batch size 調大，訓練時資料會被補上 [PAD]，程式就會在第一步崩潰。正確的做法有兩種：加完 token 之後呼叫 model.resize_token_embeddings(len(tokenizer)) 擴大 embedding；或者乾脆不加新 token，把 pad 設成一個既有的 token（例如 Llama 3 保留的 <|finetune_right_pad_id|>）。本 repo 照原版保留這一行，batch size 也保持 1。

2.6　LoRA 初始值讓原版每次都不一樣

A 是隨機初始化的，那這個「隨機」由誰決定？範例程式在 import 時設了 random.seed(42)，但那是 Python 的亂數，LoRA 用的是 torch 的亂數。SFTConfig(seed=1126) 會讓 Trainer 呼叫 set_seed(1126) 設定 torch 的種子，可是 Trainer 是在第 [18] 格才建立的，get_peft_model 早在第 [12] 格就把 A 初始化完了。torch 在程式啟動時的種子是隨機的，所以原版每跑一次，LoRA 的起點都不同。

本書最早用原版跑了兩次（ref1、ref2），設定一字不差，結果：

ref1ref2
train_loss0.8529230.853471
GSM8K public Accuracy（取樣解碼）0.3330.356
10 個 checkpoint全部不同
交出去的 504 筆416 筆不同

一開始懷疑是 GPU 的計算不穩定。為了排除，本書用一支探測工具（docs/tools/hw06_nondet_probe.py）在決定性模式下，把同一個 batch 重複做 4 次 forward 與 backward，4-bit 與 bf16、有沒有掛 LoRA 都試：

4bit forward only (no LoRA): logits identical over 4 runs: True
4bit + LoRA: losses ['3.1220397949', '3.1220397949', '3.1220397949', '3.1220397949']
4bit + LoRA: loss identical: True | all grads identical: True
bf16 forward only (no LoRA): logits identical over 4 runs: True
bf16 + LoRA: losses ['3.1319835186', '3.1319835186', '3.1319835186', '3.1319835186']
bf16 + LoRA: loss identical: True | all grads identical: True

計算本身是穩定的，問題出在起點。印出兩個不同 process 的 torch 啟動種子，一次是 1323…、一次是 1451…，LoRA 初始值的雜湊也不同。在載入模型之前先固定 torch 的種子，兩次的 LoRA 初始值就一模一樣，整條流程也就逐位元相同了（第 0 章的拆檔驗證就是這樣做的）。hw6.py 的 --seed 選項做的正是這件事。第 0 章拆檔驗證時用的是另一個入口：wrapper hw06_det.py 讀環境變數 HW06_TORCH_SEED，在執行腳本之前固定種子。兩者都是在 LoRA 初始化之前固定 torch 的種子，差別是 wrapper 從外面設定，不必改動腳本，所以連原版 notebook 串成的參照版也能用。

反過來看，這也提供了一個量雜訊的方法：固定所有其他設定，只換 --seed，得到的差異就是「LoRA 起點不同」造成的雜訊。本書所有的設定比較都跑 3 個種子（0、1、2），差距要比種子之間的差距大，才當作是設定造成的（第 6 章）。

2.7　只改 0.454% 的參數，就不會忘了嗎

投影片把 LoRA 當成減輕遺忘的第一道防線，理由很直觀：原本的 12.4 億個參數完全凍結，模型原本會的東西都還存在那些權重裡，被改動的只有旁邊那 563 萬個參數。讀過 ML2022 HW14（終身學習）的讀者會認出這個想法：持續學習的方法分成三大類，replay（重播舊資料）、regularization（懲罰重要參數的變動，例如 EWC）、parameter isolation（不同任務用不同的參數）。LoRA 最接近第三類，凍結舊參數、只在新增的小參數上學新任務。

但「參數凍結」不等於「行為不變」。LoRA 的輸出是直接加在原本的輸出上的，B A 只要學到夠大的修改量，一樣能把模型的回答方式整個改掉。本書後面的實驗會給出兩面的證據：

  • 照範例程式的預設（學習率 2e-4、1 個 epoch、1-shot），用三個審查模型判，微調後的模型反而比原模型更常拒絕危險要求（第 5、7 章）。
  • 同樣是 LoRA，只把訓練時的 few-shot 範例從 1 題加到 8 題，安全率就明顯掉到原模型以下；多訓練幾個 epoch 也有類似的趨勢（第 7、8 章）。

換句話說，LoRA 限制的是「能改多少參數」，不是「能把行為改多少」。真正決定會不會忘的，是訓練資料讓那 563 萬個參數往哪裡學、學了多少。第 3 章會看到，範例程式的 loss 不只算答案、而是整段文字都算，這一點和「學了多少」直接相關。

重點回顧

  • QLoRA：底模的線性層量化成 4-bit NF4 凍結，計算時還原成 bf16；只訓練旁邊掛的 LoRA 矩陣 A、B。整個模型只佔 1.05 GB。
  • 只有 112 個投影層被量化；embedding、lm_head、RMSNorm 留在 float16（沒指定 torch_dtype 的預設）。
  • LoRA：r＝8、α＝16（倍數 2），掛在全部 7 種投影層，可訓練 5,636,096 個參數，占 0.454%，其中 70% 在 MLP。
  • A 隨機、B 為 0，訓練開始前模型輸出和原模型相同；第一步 A 的梯度全為 0。
  • tokenizer 加了 [PAD]（id 128256）卻沒有擴大 embedding；batch size 1 才沒出錯，送進模型就會觸發 CUDA 斷言。
  • LoRA 在 set_seed(1126) 之前初始化，原版每次跑的起點都不同；--seed 先固定 torch 的種子。

自我測驗

1. 如果把 LoRA 只掛在 q_proj 和 v_proj（早期 LoRA 論文的做法），可訓練參數會是多少？

q_proj 每層 32,768、v_proj 每層 20,480，合計 53,248；乘上 16 層是 851,968 個，約為現在 5,636,096 的 15%。

2. 為什麼 LoRA 要把 B 初始化成 0，而不是兩個都隨機？

B＝0 讓 B A x 一開始就是 0，掛上 LoRA 的模型在訓練前和原模型完全相同，微調從原模型的能力出發。如果兩個都隨機，模型一開始就被加上一個隨機的擾動，訓練得先把這個擾動修掉。

3. 把 per_device_train_batch_size 改成 4，最可能發生什麼事？要怎麼改才能正常訓練？

同一個 batch 的樣本長度不同，collator 會用 [PAD]（id 128256）補齊；embedding 只有 128,256 列，查表越界，CUDA 觸發 device-side assert，訓練中止。修法是加完 token 後呼叫 resize_token_embeddings，或把 pad 設成既有的 token（例如 <|finetune_right_pad_id|>）。

4. 範例程式設了 random.seed(42)，也在 SFTConfig 設了 seed=1126，為什麼 LoRA 的初始值還是每次不同？

LoRA 用 torch 的亂數初始化，random.seed(42) 只管 Python 的亂數。seed=1126 要等 Trainer 建立時才會設定 torch 的種子，而 LoRA 在那之前（get_peft_model）就初始化完了，當時 torch 的種子是程式啟動時隨機產生的。

5. 探測工具量到模型只佔 1.05 GB。用 2.2 節的數字估算：如果不量化、直接用 bf16 載入並掛 LoRA，大約要多少？

bf16 權重檔是 2.47 GB，再加上 563 萬個 float32 的 LoRA 參數（約 0.02 GB），大約 2.5 GB。4-bit 量化把權重的記憶體減少了一半以上；沒有減到四分之一，是因為 embedding（2.6 億個參數）沒有被量化，以 float16 存放就占了約 0.5 GB。
