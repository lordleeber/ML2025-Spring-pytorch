ML2025 Spring · HW6 讀碼教材

第 3 章　訓練

訓練只有一個函式：設定好 SFTConfig，交給 trl 的 SFTTrainer，呼叫 train()。這一章逐項讀這些設定，算出 1868 步和 10 個 checkpoint 從哪裡來。接著打開 trl 的原始碼，回答兩個範例程式沒有交代的問題：loss 到底算在哪些 token 上，以及 trl 拿到一個已經掛好 LoRA 的模型時，做了什麼、又跳過了什麼。

3.1　SFTConfig 逐項讀

SFT（supervised fine-tuning，監督式微調）就是拿「輸入 → 正確輸出」的成對資料，讓模型照著學。trl 是 Hugging Face 專門做語言模型後訓練的函式庫，SFTTrainer 是它包好的 SFT 訓練器，底下仍是 transformers 的 Trainer。

第 128–132 行和第 147 行是本 repo 加的：weight decay 和 warmup 有給選項才傳進去，不給時和原版一樣用預設值 0。其餘逐項照抄 notebook：

3.2　1868 步與 10 個 checkpoint

batch size 1、梯度累積 4，每 4 個樣本更新一次參數。transformers 4.48.3 計算一個 epoch 有幾步的那一行是 len_dataloader // args.gradient_accumulation_steps：7,473 // 4 ＝ 1868，取整數部分。Colab 的輸出 global_step=1868 和本機的 checkpoint 編號都對得上。2026 版範例把評估路徑寫成 checkpoint-1869，可能是較新版本的 transformers 把除不盡的那一個樣本也算成一步，本書沒有實際驗證。

logging_steps=0.1 是比例，換算成步數是 ⌈1868 × 0.1⌉ ＝ 187：每 187 步記一次 loss、存一個 checkpoint，得到 checkpoint-187、374、561……1683，最後在訓練結束時再存一個 checkpoint-1868，一共 10 個。每個 checkpoint 裡的 LoRA 權重有 224 個張量（第 0 章），另外還存了優化器的狀態，所以才能從中間接著訓練。投影片 Medium 提示的「評估不同 checkpoint」就是從這 10 個裡面挑，第 7 章會逐一評估。

把 epoch 改成 3，總步數變成 5604，log 與 checkpoint 的間隔變成 561 步；改成 5 是 9340 步、間隔 934 步。間隔永遠是總步數的十分之一，所以不管訓練多久，都是 10 個 checkpoint。

3.3　學習率與優化器

學習率從 2e-4 開始，每一步線性往下降，最後一步降到 0。訓練 log 裡第一筆記錄（第 187 步）的學習率是 0.00017997858672376876，正好等於 2e-4 ×（1 − 187 ／ 1868）。沒有 warmup，第一步就用接近 2e-4 的學習率；第 2 章說過，第一步 B 從 0 開始、A 的梯度全為 0，所以第一步實際上只更新了 B。

paged_adamw_32bit 是 QLoRA 論文提出的「分頁優化器」。AdamW 要為每個可訓練參數存兩份狀態（梯度的一階與二階動差），這裡存成 32-bit。「分頁」的意思是這些狀態放在 NVIDIA 的統一記憶體上，顯示記憶體不夠時可以自動搬到 CPU 記憶體，避免訓練到一半遇到特別長的樣本而記憶體不足。對這份作業來說，可訓練參數只有 563 萬個，狀態總共約 45 MB，分頁的功能其實用不到。

投影片 Medium 提示的第一項就是「降低學習率」，建議範圍 1e-4 到 1e-5；Strong 提示還有 weight decay（1e-2 到 1e-4）。這些都已經做成 hw6.py 的選項，效果在第 7、8 章。

3.4　group_by_length 在 batch size 1 時做了什麼

group_by_length 的本意是省記憶體與計算：同一個 batch 裡的樣本要補成一樣長，長度差很多的樣本放在一起，就會補很多沒用的 pad。打開 transformers 的 get_length_grouped_indices，它的做法是：

  1. 用 torch.randperm 把所有樣本隨機排列。
  2. 每 50 個 batch 切成一個「大塊」（mega-batch）。這裡的 batch 指的是一次參數更新看的樣本數：Trainer 建立 sampler 時傳的是 train_batch_size × gradient_accumulation_steps ＝ 4，所以一塊是 200 個樣本。
  3. 每塊裡面按長度由長到短排序，再把全部資料最長的那一個樣本換到最前面，讓記憶體不足的問題盡早發生。

結果是每一次參數更新的 4 個樣本長度相近。但每次 forward 仍然只放 1 個樣本，根本沒有補 pad 的問題，這個選項省不到任何東西，唯一的效果是改變訓練的順序：模型看資料的順序變成「一塊 200 題由長到短，接著下一塊 200 題又由長到短」的鋸齒狀。這不是錯誤，只是一個不起作用、卻會影響結果的設定。如果把它關掉，訓練順序就變成一般的隨機排列，即使其他一切相同，結果也會不同。

順帶一提 data_seed。transformers 把它交給 accelerate，由 accelerate 用來替換一般的 RandomSampler，讓資料順序有自己的種子。開了 group_by_length 之後，sampler 換成 LengthGroupedSampler，第 1 步的 randperm 沒有指定 generator，用的是 torch 的全域亂數，也就是被 set_seed(1126) 設定過的那一個。讀原始碼的結論是：在這份設定裡 data_seed 很可能沒有作用，資料順序由 seed 決定。本書沒有實際改 data_seed 來驗證這一點。

3.5　loss 算在哪些 token 上

範例程式沒有指定 data collator。trl 0.15.2 的 SFTTrainer 遇到這種情況，用的是 transformers 最基本的語言模型 collator：

DataCollatorForLanguageModeling(mlm=False) 把 labels 設成和 input_ids 一模一樣，只把 pad 的位置遮掉。也就是說，整段文字的每一個 token 都算 loss：few-shot 範例的問題和答案、真正題目的問題、那句「Let's think step by step…」、chat template 的標頭，全都在訓練範圍內，不只是最後那段要學的答案。

trl 另外提供 DataCollatorForCompletionOnlyLM，可以只算答案。給它 assistant 標頭的字串，它會找到樣本裡最後一個標頭，把之前的 token 全部遮掉。hw6.py 把它做成選項 --completion-only-loss：

兩種 collator 到底差多少？工具 docs/tools/hw06_loss_mask.py 把前 200 個訓練樣本照 hw6.py 的方式格式化，分別送進兩種 collator，數一數有多少 token 進了 loss：

5-shot, 200 samples: tokens 217647, in loss (default) 217647, in loss (completion only) 21214 = 9.7%
8-shot, 200 samples: tokens 322008, in loss (default) 322008, in loss (completion only) 21214 = 6.6%

1-shot 的時候，真正的答案只占 28.3% 的 token，其餘 71.7% 的 loss 來自「預測範例題、預測題目、預測那句固定指令」。換句話說，範例程式除了教模型解題，也同時教它寫出 GSM8K 風格的題目、背下那句固定的指令。few-shot 的範例越多，這個比例越懸殊：8-shot 時答案只占 6.6%，每個樣本裡有 9 段 GSM8K 式的回答都在被訓練，進入 loss 的 token 是 1-shot 的 4.3 倍。

上面只數了前 200 個樣本。把全部 7,473 個 1-shot 訓練樣本都算一次（docs/tools/hw06_loss_share.py）：合計 2,736,998 個 token，答案占 771,495 個，28.2%，和前 200 個樣本的 28.3% 幾乎一樣。逐個樣本看，答案占的比例中位數是 27.1%，最少的只有 6.5%（範例題的解答很長、本題的解答很短），最多的是 56.5%，八成的樣本落在 17.4% 到 39.3% 之間。也就是說，對絕大多數樣本而言，模型在一個樣本上收到的訓練訊號，有六到八成和「解這一題」無關。

這兩種算法也會讓 loss 的數字本身不能直接比：預設的 loss 是整段文字的平均，其中範例題、題目和 template 標頭有很多容易猜的 token，平均下來比較低；只算答案時，平均的對象全是解題的文字。第 8 章比較兩種訓練的 train_loss 時要記得這一點。

這個差別可能直接關係到遺忘。第 7 章會看到，把 few-shot 從 1 題加到 8 題，安全率明顯掉到原模型以下；一個合理的猜測是，8-shot 讓模型在每一步都被灌進大量數學題的語氣。為了驗證，本書加了一組實驗：用 --completion-only-loss 重做 1-shot 和 8-shot，結果在第 8 章。

3.6　trl 拿到已經掛好 LoRA 的模型時

範例程式在 load_model 裡已經用 get_peft_model 掛好 LoRA，卻又把 peft_config 傳給 SFTTrainer。會不會掛兩層？打開 trl 處理 LoRA 的函式：

第 290–291 行：如果傳進來的已經是 PeftModel，直接原樣回傳。所以不會掛兩層，checkpoint 裡也確實只有一組 LoRA（224 個張量）。但原樣回傳也代表這個函式後面的步驟全部跳過。後面原本會做兩件事：

  • prepare_model_for_kbit_training：專為量化模型訓練準備，開啟 gradient checkpointing（用重算換記憶體），並把 layer norm 等參數轉成 fp32，讓訓練數值比較穩定。
  • peft_module_casting_to_bf16：開了 bf16=True 的 4-bit 模型，把相關模組轉成 bf16。

2025 版的範例因為先自己掛好 LoRA，這兩步都沒做；2026 版改成把原始的 4-bit 模型連同 peft_config 交給 trl，這兩步就會執行。兩年的範例看起來只差一兩行，訓練的實際內容卻不完全相同。第 2 章看到 2025 版的 layer norm 停在 float16，正是因為少了第一步。以本作業的規模，這沒有造成數值問題：本機的 train_loss 和 Colab 的 0.85249 只差在小數第四位（0.85283），記憶體也綽綽有餘。

怎麼確認自己的程式走的是哪一條？最直接的線索就是第 2 章量到的 dtype：訓練開始後，看任何一層 RMSNorm 的權重。還是 float16，就代表 prepare_model_for_kbit_training 沒有執行；變成 float32，就代表執行了。另一個線索是 trainer.model is peft_model：走捷徑時，Trainer 拿到的就是你自己建的那個物件。這兩個檢查都不需要真的訓練，建好 Trainer 之後印出來就知道。這兩個方法是依原始碼推論的，本書只實際看過第一個線索（第 2 章量到的 float16），沒有另外跑 2026 版來對照。

讀 code 不盡信文件：同一份設定，兩條路徑

trl 的說明文件教的是第二種寫法（把原始模型和 peft_config 交給 SFTTrainer）。2025 版範例混用了兩種寫法，結果走的是「原樣使用」的捷徑。這種差異不會報錯、不會警告，只能讀原始碼才知道。拿別人的訓練程式來改時，值得先確認自己走的是哪一條路徑。

loss 在第一段降得最快，從 0.981 到 0.896，之後每段大多只降 0.01 到 0.03，最後兩段幾乎持平（0.805、0.802，只差 0.003），那時學習率已經降到 4e-5 以下。這和 3.3 節的線性排程一致：後半段的更新越來越小。整個 epoch 的平均 train_loss 是 0.85281，和 Colab 的 0.85249 只差在小數第四位。本書最早用原版跑的兩次（LoRA 起點不同）前三段是 0.9813、0.8956、0.8844 與 0.9825、0.8958、0.8852，和這條曲線幾乎重合：不同的 LoRA 起點影響的是最後的權重細節，不是 loss 的走勢。

token accuracy 從 0.764 升到 0.797，意思是在整段文字（包括範例與題目）裡，模型約有八成的 token 預測對了。這個數字看起來很高，是因為大量 token 是格式和題目本身，很好猜；它不代表模型能答對八成的數學題。梯度範數在 0.5 到 0.9 之間，沒有出現突然變大的訓練不穩定。

把 epoch 加到 3 或 5，train_loss 會繼續下降（3 epochs 平均約 0.63，最後一段只剩 0.42；5 epochs 約 0.46），但第 8 章會看到，GSM8K 的 Accuracy 不升反降：模型越來越會背訓練資料，卻沒有越來越會算題。

重點回顧

  • batch size 1 × 梯度累積 4，7,473 // 4 ＝ 1868 步；每 10% 存一次，共 10 個 checkpoint，間隔 187 步。
  • 學習率 2e-4 線性降到 0、沒有 warmup；優化器是 bitsandbytes 的分頁 AdamW。
  • group_by_length 在 batch size 1 時省不到東西，只把訓練順序變成「每 200 題由長到短」；它的排列用 torch 的全域亂數，data_seed 很可能沒有作用。
  • 預設 collator 讓整段文字都算 loss；1-shot 時答案只占 28.3% 的 token，8-shot 只占 6.6%。--completion-only-loss 改成只算最後的答案。
  • trl 拿到已經是 PeftModel 的模型就原樣使用，跳過 prepare_model_for_kbit_training 與 bf16 轉型；2026 版的寫法會做這兩步。
  • 1 epoch 的 train_loss 約 0.853，和 Colab 的 0.852 一致。

自我測驗

1. 把 gradient_accumulation_steps 改成 8、其他不變，總步數和 checkpoint 間隔各變成多少？

7,473 // 8 ＝ 934 步；間隔是 ⌈934 × 0.1⌉ ＝ 94 步，仍是 10 個 checkpoint（最後一個是 checkpoint-934）。每一步看的樣本變成 8 個，在學習率排程相同的情況下，參數的更新次數只剩一半。

2. 用 3.3 節的式子算一下：第 935 步（訓練一半）時的學習率是多少？

2e-4 ×（1 − 935 ／ 1868）≈ 9.99e-5，大約剩一半。

3. 預設的 collator 讓 few-shot 範例的問題也算 loss。這對模型的行為可能有什麼影響？

模型被訓練去預測「使用者會問什麼」，也就是學會生成 GSM8K 風格的題目和那句固定的指令，而不只是學怎麼回答。訓練訊號裡有很大一部分花在這些內容上，而且 few-shot 數越多，這部分越大，可能讓模型的整體語氣更偏向數學題，進而影響它面對其他要求時的反應。

4. 範例程式同時用了 get_peft_model 和 SFTTrainer(peft_config=...)，會不會掛兩層 LoRA？少做了什麼？

不會。trl 的 _prepare_peft_model 看到傳入的已經是 PeftModel，就直接回傳。但回傳之後原本要做的 prepare_model_for_kbit_training（gradient checkpointing、layer norm 轉 fp32）與 bf16 轉型都被跳過了。

5. 為什麼說 group_by_length=True 在這份作業裡「不起作用、卻會影響結果」？

batch size 是 1，沒有補 pad 的問題，所以它省不到記憶體或計算（不起作用）。但它改變了訓練樣本的順序，順序不同，每一步看到的資料就不同，最後的權重也會不同（會影響結果）。
