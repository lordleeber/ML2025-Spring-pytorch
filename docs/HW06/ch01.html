ML2025 Spring · HW6 讀碼教材

第 1 章　資料與 prompt

模型學什麼、被考什麼，全看餵給它的文字。這一章先看五個資料檔各裝了什麼，再看範例程式怎麼把一道數學題包成多輪對話、套上 chat template。最後會發現，訓練時餵進去的文字和評估時的 prompt 並不一樣，而且評估時每一題配到哪個範例，是由一個和訓練資料無關的亂數種子決定的。

1.2　GSM8K 的答案長什麼樣

GSM8K（Grade School Math 8K）是 OpenAI 在 2021 年釋出的小學數學應用題，需要二到八步的四則運算。每一題的 answer 欄位是一段解題過程，最後一行用 #### 標出最終答案。訓練集的第一題：

Natalia sold 48/2 = <<48/2=24>>24 clips in May.   «1»
Natalia sold 48+24 = <<48+24=72>>72 clips altogether in April and May.
#### 72   «2»
  1. 1<<48/2=24>> 是計算標記（calculator annotation）。GSM8K 的作者在每個算式後面標出可以交給計算機執行的式子和結果，原本是為了讓模型生成時可以呼叫外部計算機。對這份作業來說，它只是一段會被模型學起來的固定寫法。7,473 題裡有 7,378 題帶這種標記。
  2. 2#### 72 是最終答案。範例程式的 prompt 明確要求模型「在 #### 之後寫一個整數」，評估時也只取最後一個 #### 之後的文字（第 4 章）。

訓練集答案的中位數是 4 行、47 個英文字。這個長度很重要：模型微調之後，回答會變得和訓練資料一樣短、一樣照格式寫，第 4 章會看到這個效果。

1.3　self-instruct 版的訓練資料

Strong 提示裡的「self-instruct」指的是第二份訓練檔。投影片描述了助教怎麼做出它：拿原本還沒微調的模型去解訓練集的題目，取樣出多個回答，再篩選答對的留下來。換句話說，問題和原版相同，答案卻是模型自己的口吻。同一題的 self-instruct 答案：

Natalia sold 48 clips in April.
In May, she sold half as many clips, which is 48/2 = 24 clips.
The total number of clips Natalia sold in April and May is 48 + 24 = 72.
#### 72

和原版逐題比對，得到這些事實：

原版self-instruct
題數7,4737,472（少 1 題，其餘問題全部出自原版）
帶 #### 的答案7,4737,472
帶 <<…>> 計算標記7,378103
答案行數的中位數46
答案字數的中位數4774
最終答案和原版相同7,472 題全部相同

最終答案全部相同，代表助教確實只留下答對的回答。差別在寫法：模型自己不會寫 <<48/2=24>> 這種標記，會多寫一兩句說明，回答也比較長。用這份資料訓練，模型要學的只有「把題目算對」，不需要同時學一種陌生的寫作格式。為什麼這可能讓模型比較不會忘掉原本的行為，要等第 8 章用實驗回答。

1.4　AILuminate：240 個危險提示

AILuminate 是 MLCommons 發布的 AI 安全基準。每個提示都標了屬於哪一類危險（hazard）、模擬哪一種使用者（persona）、用哪一種語言（locale）；這份測試檔的 hazard 欄一共用到 15 個代碼，其中「專業建議」細分成財務、法律、選舉、健康四個。這份測試檔的 release_prompt_id 都以 airr_practice_1_0 開頭，出自官方公開的練習題集（共 12,000 題），助教從中挑了 240 題。

本書不放 AILuminate 的題目原文

這些提示本身就是危險或冒犯性的內容，模型的回答也可能是。本書只放類別、統計和審查結果，不逐字引用任何一題或任何一個回答。投影片上已經公開的那個例子（白帽駭客問 keylogger 與 IP 追蹤）是唯一的例外。

1.5　few-shot 對話怎麼組

範例程式不是把題目直接丟給模型，而是先給它看一個（或幾個）解好的例子，這叫 few-shot prompting。組對話的函式：

它組出的是一段多輪對話。每個範例變成一組「user 問、assistant 答」，問題前面加 Q: 、答案前面加 A: 。最後一輪是真正要解的題目，後面接上一句固定的指令：「Let's think step by step. At the end, you MUST write the answer as an integer after '####'.」前半句是 chain-of-thought 提示，鼓勵模型先寫出推理過程；後半句規定答案的格式，好讓程式抽得出來。

mode 決定最後要不要附上答案：訓練時（'train'）把標準答案當作 assistant 的最後一輪接上去，模型要學的就是這段；評估時（'test'）停在問題，等模型自己生成。第 97 行選範例的方式有兩種：預設是 random.sample，每呼叫一次就從訓練集隨機抽 n 題；給了 --fixed-shots-seed 時改用一組固定的範例（本 repo 加的，第 8 章）。

範例從訓練集抽，包括測試的時候

評估時的 few-shot 範例也是從 gsm8k_train 抽的。這不算作弊，訓練集本來就可以看，但它有兩個副作用。第一，每一題配到的範例不同，有的範例剛好和題目很像、有的毫不相干，評估結果因此多了一份隨機性。第二，訓練時模型已經把這些範例的答案背得很熟，評估時又看到它們。投影片 Strong 提示的「固定 few-shot 範例」就是針對這兩點。

1.6　訓練樣本和評估 prompt 不一樣

對話組好之後，要用 chat template 轉成一長串文字。訓練資料的格式化在這裡：

第 120 行把文字從開頭切到第一個 <|eot_id|> 為止，丟掉。第 0 章看過，template 一開頭會自動加一段 system header，裡面有「Cutting Knowledge Date」和執行當天的日期；第一個 <|eot_id|> 正是這段 header 的結尾，所以這一行的效果就是把 system header 整段刪掉，連 <|begin_of_text|> 一起。第 122 行用 tokenizer 量每個樣本的長度，取最大值當作訓練的 max_seq_length，確保沒有樣本被截斷；1-shot 時最長 790 個 token，中位數 356 個。

讀 code 不盡信文件：訓練和評估的格式不一致

範例程式第 [16] 格的註解寫「Remove Cutting Knowledge Date in prompt template」，用意是讓訓練資料乾淨一點，但評估時並沒有做同樣的處理。結果是模型在訓練時從沒看過 system header，評估時卻每一題都有。更麻煩的是 header 裡的日期每天不同，同一個模型、同一份程式，不同日子跑出來的答案就不一樣。本書在拆檔驗證時就是被這一行絆住，追查過程在第 6 章。如果要修正，最簡單的做法是評估時也把 system header 拿掉，或在套 template 時傳入固定的 date_string；本 repo 為了忠於原版，hw6.py 保持原樣，只在需要逐位元比對時用 docs/tools/hw06_fixdate.py 固定日期。

1.7　兩個亂數種子各管什麼

few-shot 範例是用 Python 的 random 抽的。範例程式在 import 時設了 random.seed(42)，看起來整份程式的抽樣都由 42 決定，實際上不是：

  • 42 只管訓練樣本。格式化訓練資料的迴圈為 7,473 題各呼叫一次 random.sample，這些抽樣決定每個訓練樣本配到哪個範例。
  • 1126 管評估。訓練開始前，transformers 的 Trainer 會呼叫 set_seed(1126)（1126 是範例程式在 SFTConfig 裡設的 seed）。這個函式除了設定 torch 和 NumPy，也會呼叫 random.seed(1126)。訓練過程本身完全不用 Python 的 random，所以訓練結束、開始評估時，Python 的亂數狀態和剛設好 1126 時一模一樣。

第二點本書用工具 docs/tools/hw06_pyrandom_probe.py 驗證過：在 CPU 上用一個小模型照同樣的設定訓練 3 步，訓練前後的狀態都和全新的 random.seed(1126) 相同。

state after SFTTrainer() == state after random.seed(1126): True
state after trainer.train() == state after random.seed(1126): True

這帶來一個好處：所有用 hw6.py 訓練的實驗，不管學習率、epoch 數怎麼改，評估時每一題配到的範例都相同（只要 few-shot 數一樣），比較起來比較公平。也帶來一個陷阱：如果不經過訓練、直接評估一個模型，就得自己補上 random.seed(1126)，否則範例會不同。本書一開始評估原模型時就漏了這一步，那批數字用的是 42 之後的範例；第 0 章提過的 --skip-train 和評估工具的 --py-seed 1126 就是為此加上的，原模型也用相同的範例重新評估了一次（第 4 章）。

重點回顧

  • 五個資料檔：訓練 7,473 題、self-instruct 7,472 題、public 132 題（有答案、不在訓練集）、private 132 題（沒答案）、AILuminate 240 題。
  • GSM8K 的答案帶 <<式子=結果>> 計算標記，最後以 #### 答案 結尾。self-instruct 版問題和最終答案都相同，但幾乎沒有計算標記、回答比較長，是原模型自己的口吻。
  • AILuminate 有 15 類危險、兩種 persona，12 題重複；本書只放統計，不放題目與回答原文。
  • few-shot 對話：範例是 user／assistant 輪流，最後一題接上一句固定的格式指令；訓練時附上答案，評估時停在問題。
  • 訓練樣本切掉了 system header，評估 prompt 沒切，而且 header 裡有當天日期：格式不一致，結果也隨日期改變。
  • random.seed(42) 只決定訓練樣本的範例；Trainer 的 set_seed(1126) 決定評估時的範例。

自我測驗

1. 為什麼 public 的標準答案 65,960 不會因為逗號而永遠被判錯？

評估時，標準答案和模型的回答都會經過同一個抽取函式：取最後一個 #### 之後的文字，再刪掉逗號、錢號、百分號和字母 g。65,960 被處理成 65960，模型寫 65960 或 65,960 都能對上。

2. self-instruct 的 7,472 題最終答案全部和原版相同，這透露了助教做資料時的哪一個步驟？

助教用原模型取樣出多個回答後，有用標準答案篩選，只留下最終答案正確的那些。所以資料保留了模型自己的寫法，卻不會教模型錯的答案。

3. 分析 AILuminate 的審查結果時，用 release_prompt_id 當 key 把兩份結果合併，會出什麼問題？

有 12 題的 id 重複出現兩次，用 id 當 key 會讓後出現的那筆蓋掉前一筆，只剩 228 筆，算出來的一致率或安全率就不是 240 題的結果。要用列的順序對齊。

4. 訓練樣本開頭沒有 system header，評估 prompt 卻有。舉出這個不一致會造成的兩個後果。

第一，模型在微調時從沒看過帶 system header 的輸入，評估時的輸入格式和它學的不同。第二，header 裡的日期每天不同，同一個模型、同一份程式在不同日子會得到不同的答案，讓結果無法跨日重現。

5. 把學習率從 2e-4 改成 1e-4 重新訓練，評估時 public 第一題配到的 few-shot 範例會變嗎？為什麼？

不會。評估時的抽樣從 Trainer 設好的 random.seed(1126) 開始，訓練過程不使用 Python 的 random，學習率也不影響這個亂數狀態。只要 few-shot 數不變，每一題配到的範例都相同。
