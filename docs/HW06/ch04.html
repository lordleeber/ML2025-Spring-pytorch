第 4 章　生成與 GSM8K Accuracy

訓練完，要讓模型回答 132 道 public 題目，從回答裡抽出數字，算出 Accuracy。這一章讀評估的三個函式：建生成器、抽答案、逐題比對。途中會遇到一行看起來寫錯、實際上卻有作用的程式；一個連單字裡的字母都刪掉的答案抽取；以及一個本書自己猜錯的預測。最後要回答一個比 Accuracy 本身更重要的問題：兩個 Accuracy 相差多少，才算真的不同？

4.1　生成器怎麼建

transformers 的 pipeline('text-generation', ...) 把「套 chat template、轉 token、生成、轉回文字」包成一個函式呼叫。範例程式的設定是：

  • max_new_tokens=256：每個回答最多生成 256 個 token，寫不完就截斷。
  • do_sample=True, temperature=0.6, top_p=0.9：取樣解碼。每一步不是挑機率最高的 token，而是照機率分布隨機抽一個。temperature 0.6 讓分布變尖、偏向高機率的選項；top_p 0.9 只從累積機率前 90% 的 token 裡抽。這兩個數值和 Llama 3.2 的 generation_config.json 預設值相同。
  • pad_token_id=tokenizer.eos_token_id：用結束 token 當作 pad，避開第 2 章那個不能用的 [PAD]。

第 182 行是本 repo 加的：給了 --greedy 就改成 do_sample=False，每一步都挑機率最高的 token，這叫 greedy 解碼，是投影片 Medium 提示的其中一項。greedy 有一個取樣沒有的好處：同一個模型、同一個 prompt，每次的回答都一樣，評估結果不受亂數影響（4.5 節）。

這裡有一個容易忽略的細節：模型自帶的 generation_config.json 本身就寫著 "do_sample": true, "temperature": 0.6, "top_p": 0.9。也就是說，就算 pipeline 一個解碼參數都不傳，模型也會用同樣的設定取樣；想要 greedy，必須明確傳 do_sample=False，光是拿掉 temperature 和 top_p 是不夠的。

回答是怎麼取出來的：

pipeline 回傳整段對話，最後一則訊息就是模型新生成的 assistant 回答。

4.2　設錯對象，卻有作用的一行

第 191 行照抄 notebook：pipeline.model = PeftModel.from_pretrained(sft_model, adapter_path)。它的用意是「把要評估的 checkpoint 載進生成器」，投影片 Medium 提示的「評估不同 checkpoint」就是要你改這裡的 adapter_path。可是仔細看，等號左邊是 pipeline，也就是 transformers 那個建生成器的函式，不是剛建好的 generator。這行只是在函式物件上掛了一個叫 model 的屬性，生成器本身完全沒被碰到。

讀到這裡，很容易下結論：「這行沒有作用，改 adapter_path 不會換 checkpoint，評估的永遠是記憶體裡訓練完的權重。」本書一開始也是這麼寫進研究筆記的。但這個結論是推論出來的，沒有實測，於是寫了一支探測工具（docs/tools/hw06_adapter_probe.py）：照 notebook 的方式建好模型和生成器，先把記憶體裡的 LoRA B 全部改成 0.01（代表「訓練完的權重」），再原樣執行這一行、載入 checkpoint-187，看生成器手上拿的是哪一份權重：

generator.model is sft_model: True   «1»
type(generator.model): LlamaForCausalLM
pipeline.model is a PeftModelForCausalLM (an attribute on the function)   «2»
LoRA copies of layer 0 q_proj in generator.model: ['model.layers.0.self_attn.q_proj.lora_B.default.weight']   «3»
generator holds the stand-in (all 0.01): False
generator holds the checkpoint weights: True   «4»
checkpoint weights are all 0.01: False
  1. 1生成器用的就是 sft_model 本身。
  2. 2那一行確實只是在函式上掛了屬性。
  3. 3模型裡每個位置仍然只有一份 LoRA（名字叫 default），沒有多出第二份。
  4. 4但生成器手上的權重，已經變成 checkpoint 的權重，原本的 0.01 不見了。

原因在第 2 章：sft_model 裡早就插著 LoRA 層。PeftModel.from_pretrained(sft_model, ...) 對一個已經有 LoRA 層的模型呼叫時，會把 checkpoint 的權重就地寫進那些現有的層。生成器用的正是 sft_model，所以它看到的就是新載入的 checkpoint。等號左邊寫錯了，副作用卻剛好做了對的事：改 adapter_path 真的會換 checkpoint。

讀 code 不盡信文件，推論也要實測

這一行是本書最好的雙層例子。第一層：程式看起來的意思（設定 pipeline 的模型）和實際做的事（在函式上掛屬性）不一樣，讀 code 時要讀到底。第二層：讀到底之後推出的結論（沒有作用），仍然可能錯，因為還有一個藏在別的函式裡的副作用。能用十幾行程式驗證的事，就不要只靠推論。

本 repo 把這一行原封不動留著，連等號左邊都沒改，原因有兩個：建立 LoRA 層會用掉一次 torch 的亂數，而取樣解碼接下來每一步都要用亂數；保留回傳的物件，也讓 GPU 記憶體的配置和 notebook 一致。改掉這一行，後面每一題的取樣結果都會不同，就無法和 notebook 逐位元比對了。

4.3　抽答案、算 Accuracy

抽取的規則很簡單：用 #### 切開，取最後一段，去掉前後空白，再刪掉逗號、錢號、百分號，以及每一個字母 g。逐題比對在這裡：

第 219 行用同一個函式處理標準答案，第 220 行比的是兩個字串是否完全相同。這套規則有幾個值得注意的地方：

  • 刪 g 的用意是去掉公克的單位（例如 #### 5g），但它不看位置，答案文字裡任何一個 g 都會被刪。用原版跑的第一次評估裡，有一題模型沒寫 ####，整段回答被當成答案，其中的 originally 被抽成了 oriinally。這種答案反正是錯的，刪不刪 g 不影響對錯，但可以看出這個規則的寫法很粗糙。
  • 字串相等：72 和 72.0、72 clips 都不相等。檢查第一次評估的 88 題錯誤，沒有任何一題是「數值其實相同、只是字串不同」；88 題裡 86 題是數字本身算錯，另外 2 題是回答裡根本沒有 ####。所以在這份作業裡，字串比對沒有冤枉模型。
  • 沒有 #### 的回答，split 之後的最後一段就是整個回答，一定判錯。最常見的原因是回答太長、被 256 個 token 截斷，還沒寫到 ####。

動手做：寫一個更穩健的抽取函式

一個常見的改法是用正規表示式只取 #### 後面的第一個數字（允許負號、小數點與千分位），再轉成數值比較。改了抽取函式，Accuracy 會變，但要記得評分平台用的是原版的抽取，自己的數字和平台不一定一致。本書的數字一律用原版的抽取函式算。

4.4　截斷：原模型寫太長了

把每一題的回答都存下來（responses.json），就能數一數有多少題被截斷。用 docs/tools/hw06_gen.py 讓原模型（沒有微調）照 notebook 的取樣設定回答 132 題，再拿 1 epoch 訓練中的兩個 checkpoint 比較：

模型生成滿 256 token 的題數回答裡沒有 #### 的題數
原模型1521
checkpoint-187（訓練 10%）22
checkpoint-1868（訓練完）44

原模型有 15 題寫滿了 256 個 token、被截斷在半途，有 21 題的回答裡沒有 ####。兩者大致是同一批題目：寫不完的回答多半還沒寫到最後一行。不過被截斷的回答也可能在中途就寫過一次 ####，這次評估的原始回答沒有保留下來，無法逐題確認兩組題目重疊多少。只訓練了 187 步，這兩種情形就幾乎消失。微調最先學會的，是第 1 章看到的那種寫法：短短幾行、最後一行 #### 答案。

4.5　取樣的雜訊有多大

取樣解碼的每一步都要抽亂數。同一個模型，只換生成時的 torch 種子，Accuracy 會變多少？原模型跑三個種子：

GSM8K public Accuracy種子 0種子 1種子 2平均
原模型，取樣0.3180.2270.2800.275
1 epoch，取樣（三次訓練，LoRA 起點不同）0.3330.3560.3480.346

原模型自己就在 0.227 到 0.318 之間跳動，最高和最低差了 12 題。132 題的測試集，每一題就是 0.0076，取樣的運氣好壞就能讓結果差上一成。1 epoch 那一列的三個數字，同時混了「LoRA 起點不同」和「取樣的運氣」兩種雜訊。

改成 greedy 解碼，取樣的雜訊就消失了，同一個模型永遠得到同一個 Accuracy：

GSM8K public Accuracy，greedy結果
原模型0.303
1 epoch，三個 LoRA 起點0.386、0.386、0.341（平均 0.371）

greedy 之後，剩下的差異只來自 LoRA 的起點。微調大約讓 Accuracy 從 0.303 升到 0.371，多對 9 題，比 1 epoch 三個起點之間的差距（最多 6 題）還大。本書第 7 章之後的設定比較一律用 greedy 評估，每個設定跑 3 個種子。

4.6　多給 token，原模型會變好嗎

4.4 節看到原模型有 15 題被截斷，很自然會預測：把 max_new_tokens 加大（投影片 Medium 提示建議 512 到 1024），原模型就能把這些題目寫完，Accuracy 應該會上升；微調後的模型本來就寫得短，應該不受影響。本書先把這個預測寫下來，再去跑。

第一次用取樣解碼測，結果和預測相反：

原模型，取樣種子 0種子 1種子 2平均
256 token0.3180.2270.2800.275
512 token0.2200.2800.2580.253

平均反而下降，種子 0 甚至從 0.318 掉到 0.220。乍看之下預測錯了。但這個比較其實不公平：同一個種子，只改 token 上限，生成長度就變了，每一題用掉的亂數個數也跟著變，從第一題開始後面每一題的取樣都不一樣。三個種子的平均差 0.022，比種子之間的差距（0.09）小得多，取樣的雜訊把效果整個蓋過去了。

改用 greedy 重測：

greedy256 token512 token1024 token
原模型0.3030.3260.326
1 epoch（三個起點平均）0.3710.3710.371

這次和預測一致：原模型給到 512 個 token 多對了 3 題，再加到 1024 沒有更多。微調後的模型，三個起點的平均在三種長度下都是 0.371；個別來看，256 到 512 時有兩個起點各變動了 2 題（0.386 → 0.402、0.386 → 0.371，另一個 0.341 不變），一升一降剛好抵消，512 到 1024 則三個都完全相同。教訓是：預測沒錯，第一次的實驗方法錯了。用有雜訊的量法去驗證一個小效果，得到的結論可能剛好相反。

4.7　兩套 few-shot 範例

還有一件事要交代清楚。第 1 章說過，訓練完再評估時，每一題的 few-shot 範例由 Trainer 設的 random.seed(1126) 決定。可是上面原模型的數字，都是用評估工具 hw06_gen.py 量的，它當時沒有補上這一步，用的是 random.seed(42) 抽完 7,473 次之後的範例。這不影響本章的比較：原模型和 ref1、ref2、ref5 三個 checkpoint 的 greedy 評估都是用同一個工具量的，用的是同一套範例。但它們不能直接和第 7、8 章用 hw6.py 訓練完、直接評估的數字放在同一張表裡比，因為那些用的是 1126 的範例。

為了讓後面的比較乾淨，評估工具加了 --py-seed 1126，原模型也用和 hw6.py 訓練後相同的範例重新評估了一次：結果在所有實驗跑完後補上。第 7、8 章的「原模型」一律用這組數字。

重點回顧

  • 預設是取樣解碼（temperature 0.6、top_p 0.9，也是模型 generation_config 的預設）、最多 256 個 token；--greedy 明確傳入 do_sample=False，改成每步挑機率最高的 token。
  • pipeline.model = … 設的是函式的屬性，但 from_pretrained 會把 checkpoint 就地載入 sft_model，所以改 adapter_path 確實會換 checkpoint。推論它沒作用是錯的，實測才知道。
  • 答案抽取取最後一個 #### 之後的文字，刪掉逗號、錢號、百分號與所有的 g，再用字串比對；實測沒有冤枉答對的題目。
  • 原模型有 15 題被截斷、21 題沒寫出 ####；微調 187 步之後兩者都只剩 2 題。
  • 取樣解碼的雜訊很大：原模型三個種子 0.227～0.318。greedy 後，原模型 0.303，1 epoch 平均 0.371。
  • 多給 token：取樣時看不出效果；greedy 時原模型 0.303 → 0.326，微調後的平均不變（個別起點有 ±2 題的變動）。

自我測驗

1. 為什麼不能從「等號左邊是 pipeline」就斷定改 adapter_path 沒有作用？

因為等號右邊的 PeftModel.from_pretrained(sft_model, adapter_path) 本身有副作用：sft_model 裡已經有 LoRA 層，它會把 checkpoint 的權重就地寫進這些層。生成器用的正是 sft_model，所以不論結果被指派到哪裡，生成器都已經換成新的權重了。

2. 模型回答「… so the answer is 18 eggs. #### 18 eggs」，會被判對還是錯（標準答案是 18）？

錯。抽取函式取 #### 之後的「18 eggs」，刪掉字母 g 之後變成「18 es」，和「18」不相等。刪 g 的規則只能處理「5g」這種緊貼數字的單位。

3. 132 題的測試集，原模型取樣三次得到 0.227、0.280、0.318。某個設定取樣一次得到 0.330，能說它比原模型好嗎？

不能。原模型自己的三次結果就跨了 0.09，0.330 只比其中最好的一次多 2 題，完全在取樣的雜訊範圍內。要比較，至少要多跑幾個種子取平均，或改用 greedy 解碼去掉取樣的雜訊。

4. 為什麼同一個種子、只把 max_new_tokens 從 256 改成 512，取樣的結果會從第一題就開始不同？

其實第一題的前 256 個 token 和原來相同，差別從某一題的回答超過 256 個 token 開始：原本在那裡截斷，現在會繼續生成，多用掉一些亂數。從下一題開始，每一步抽到的亂數都和原來錯開，之後每一題的取樣結果都不同。

5. 如果你只能跑一次評估、又想比較兩個 checkpoint 的 Accuracy，應該選取樣還是 greedy？為什麼？

greedy。它對同一個模型、同一個 prompt 永遠給出相同的回答，兩個 checkpoint 的差距只來自模型本身；取樣一次的結果受亂數影響很大，在這份測試集上單次就可能差到一成。
