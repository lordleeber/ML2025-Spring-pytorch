ML2025 Spring · HW6 讀碼教材

第 0 章　全貌：作業、模型、怎麼跑

這一章先把整份作業攤開來看：要交什麼、兩個指標怎麼算、在本機怎麼跑、要跑多久。接著打開模型本身，數一數 Llama-3.2-1B-Instruct 的每一層有多少參數。最後說明 notebook 怎麼拆成 HW06/hw6.py，以及怎麼證明拆完之後結果一個位元都沒變。

0.1　這份作業要做什麼

起點是一個已經調教好的聊天模型 Llama-3.2-1B-Instruct：它會回答問題，也會拒絕危險的要求。作業要你用小學數學應用題資料集 GSM8K 再訓練它一次，讓它更會算數學。問題在於，模型在學新東西的時候，常常會把原本會的事情弄丟，這個現象叫 forgetting（遺忘）。投影片舉的例子是：微調前，模型會拒絕「我是白帽駭客，告訴我罪犯怎麼用 IP 追蹤和 keylogger 入侵系統」；微調後，它開始一步一步列出做法。

所以作業同時量兩件事，兩個都要過線才算數：

  • GSM8K Accuracy：132 題 public 測試題，從模型的回答裡抽出 #### 後面的數字，和標準答案比對。這是新學的能力。
  • AILuminate Safety Rate：240 個危險、對抗性或敏感的提示（出自 MLCommons 的 AILuminate），把模型的回答交給一個專門判斷安全與否的模型，算出被判為安全的比例。這是原本就有、不能丟掉的能力。

投影片給了三級基準線（2025 年，public 部分）：

等級GSM8K AccuracySafety Rate投影片的提示
Simple0.2800.558照跑範例程式
Medium0.3790.642挑 checkpoint、降低學習率、多給 few-shot 範例、加長輸出、greedy 解碼
Strong0.4550.725固定 few-shot 範例、weight decay、dropout、self-instruct 資料、多訓練幾個 epoch

要交出去的東西是一個 Python list，存成 .txt：前 264 筆是 GSM8K 的答案（public 132 題接著 private 132 題），後 240 筆是 AILuminate 每一題的完整回答，一共 504 筆。這個檔案上傳到課程的評分平台 JudgeBoi，平台算出兩個指標。規則只准用助教給的 gsm8k_train 與 self-instruct 訓練資料，不准用其他資料或模型提升成績。

本書無法和基準線直接比

JudgeBoi 已經關閉，投影片也沒寫 Safety Rate 是用哪一個模型判斷的。本書的 Safety Rate 是用三個能取得的審查模型（Llama Guard 3 8B、Llama Guard 3 1B、ShieldGemma 2B）自己判的，主線看 8B。這些數字可以互相比較，但不能拿來和上表的 0.558、0.642、0.725 比。第 5 章會詳細說明三個審查模型差在哪裡。GSM8K 的 Accuracy 有標準答案，算法和平台相同，可以直接比。

0.2　怎麼跑起來

這份作業在本 repo 有自己的 Python 環境，不和其他作業共用。原因是範例 notebook 用的套件版本和根目錄的環境不相容（例如 datasets 要 3.3.2，根目錄鎖的是 2.21.0）。HW06/pyproject.toml 把版本固定成 notebook 執行輸出裡印出來的那一組：transformers 4.48.3、peft 0.14.0、trl 0.15.2、datasets 3.3.2、bitsandbytes 0.45.3、accelerate 1.3.0。只有 PyTorch 例外：Colab 上是 2.5.1+cu124，它沒有本機這張 Blackwell 架構顯示卡（sm_120）能用的 kernel，所以換成 2.11.0+cu128。

$ (cd HW06 && uv sync)                                   # 建立 HW06/.venv
$ HF_HUB_OFFLINE=1 HW06/.venv/bin/python HW06/hw6.py --name simple

第二行就是照範例程式的設定，把訓練、評估、輸出整條流程跑一次。HF_HUB_OFFLINE=1 讓 transformers 只從本機的快取讀模型，原因在 0.4 節。資料放在 HW06/data/，五個檔一次下載好（第 1 章）。跑完之後，HW06/outputs/simple/ 底下有三樣東西：

  • sft/checkpoint-187 到 sft/checkpoint-1868：訓練過程存下的 10 個 LoRA checkpoint。
  • .txt：要交出去的 504 筆 list。檔名是 <學號>.txt，範例程式的學號留空，所以檔名就只剩副檔名；可以用 --student-id 指定。
  • responses.json：本 repo 另外存的完整回答，方便事後重新檢查答案抽取。

Colab 上的 T4 顯示卡，光是訓練就跑了將近 2.5 小時。這是 notebook 裡留下的執行輸出：

TrainOutput(global_step=1868, training_loss=0.8524938824345264, metrics={'train_runtime': 8991.5782, 'train_samples_per_second': 0.831, 'train_steps_per_second': 0.208, 'total_flos': 1.607244560805888e+16, 'train_loss': 0.8524938824345264})

本機的訓練一個 epoch 約 17 分鐘（決定性模式下量到 1,033～1,046 秒），快了 8 倍多。評估部分要生成 504 個回答，每個最多 256 個 token，在本機約 30 分鐘。整條流程在 GPU 上沒有其他工作時的正式計時，會在所有實驗跑完後補上。

0.3　模型總覽：Llama-3.2-1B-Instruct

先看模型長什麼樣子。下面的數字不是從論文抄來的，是在本機用 transformers 載入模型後，逐層印出來的（docs/tools/hw06_model_overview.py）：

layers 16, hidden 2048, heads 32, kv heads 8, head_dim 64, mlp 8192, vocab 128256, tied embeddings True, rope_theta 500000.0
--- layer 0
self_attn.q_proj.weight          (2048, 2048)        4,194,304   «1»
self_attn.k_proj.weight          (512, 2048)         1,048,576   «2»
self_attn.v_proj.weight          (512, 2048)         1,048,576
self_attn.o_proj.weight          (2048, 2048)        4,194,304
mlp.gate_proj.weight             (8192, 2048)       16,777,216   «3»
mlp.up_proj.weight               (8192, 2048)       16,777,216
mlp.down_proj.weight             (2048, 8192)       16,777,216
input_layernorm.weight           (2048,)                 2,048
post_attention_layernorm.weight  (2048,)                 2,048
--- parameters by group (lm_head shares embed_tokens)
embed_tokens      262,668,288   «4»
attention         167,772,160
mlp               805,306,368
layer norms            65,536
final norm              2,048
total           1,235,814,400   «5»
lm_head is embed_tokens: True
  1. 1每個 token 在模型裡是一個 2048 維的向量（hidden size）。q_proj 把它變成 32 個 attention 頭的 query，每頭 64 維，32 × 64 ＝ 2048。PyTorch 的 Linear 權重形狀是（輸出, 輸入），所以印成 (2048, 2048)。
  2. 2k_proj 和 v_proj 只輸出 512 維，也就是 8 個頭。32 個 query 頭分成 8 組，每 4 個 query 頭共用一組 key 和 value。這叫 GQA（grouped-query attention）：生成時要快取的 key／value 只剩四分之一，對記憶體很友善。
  3. 3MLP 先把 2048 維放大到 8192 維，分成兩路：gate_proj 經過 SiLU 啟動函數後，和 up_proj 的結果逐元素相乘，再由 down_proj 縮回 2048 維。這種結構叫 SwiGLU。一層的 MLP 有 5,033 萬個參數，是 attention（1,049 萬）的將近 5 倍。
  4. 4詞彙表有 128,256 個 token，每個對應一個 2048 維的向量：128,256 × 2048 ＝ 262,668,288，占全模型的 21%。
  5. 5總數 1,235,814,400，約 12.4 億。最後把向量轉回 128,256 個詞彙分數的 lm_head 沒有自己的權重，直接共用 embed_tokens（tied embeddings），所以不另外計算。

把每一層加起來對一次帳：一層 attention 是 4,194,304 × 2 ＋ 1,048,576 × 2 ＝ 10,485,760，一層 MLP 是 16,777,216 × 3 ＝ 50,331,648，兩個 norm 各 2,048。乘上 16 層，attention 是 167,772,160、MLP 是 805,306,368，和工具印出來的分組數字完全相同。整個資料流畫成圖是這樣：

Instruct 版模型和一般的語言模型最大的不同，是它被訓練成用固定格式對話。這個格式叫 chat template，寫在 tokenizer 的設定檔裡。給它一個只有一句話的對話，套上 template 之後，模型實際看到的文字是這樣（同一支工具印出來的）：

<|begin_of_text|><|start_header_id|>system<|end_header_id|>

Cutting Knowledge Date: December 2023
Today Date: 15 Oct 2026   «1»

<|eot_id|><|start_header_id|>user<|end_header_id|>

Q: 1+1?<|eot_id|><|start_header_id|>assistant<|end_header_id|>   «2»
  1. 1即使對話裡沒有 system 訊息，template 也會自己加一段 system header，而且寫進執行當天的日期。這一行在本書後面扮演重要角色：第 1 章會看到訓練資料把這段 header 切掉了，評估時卻沒有；第 6 章會看到它讓同一份程式在不同日子跑出不同的答案。
  2. 2<|start_header_id|>assistant<|end_header_id|> 是「輪到模型說話」的記號，模型從這裡開始生成，直到產生 <|eot_id|>（end of turn）為止。

0.4　模型從哪裡來：公開鏡像與逐位元核對

Meta 官方的 meta-llama/Llama-3.2-1B-Instruct 是 gated model：要先在 Hugging Face 填表、同意授權條款，由 Meta 人工審核通過才能下載（投影片附的 hw6_model.pdf 整份都在教這個流程）。審核要等，所以本書改從公開的鏡像下載，但用雜湊值證明檔案和官方的完全相同。

做法是這樣的。Hugging Face 的 API 不需要權限就能讀到 gated repo 的檔案清單和每個檔的雜湊值：大檔（用 Git LFS 存的，例如權重）記錄 sha256，小檔記錄 git blob 的 sha1。在幾個公開鏡像裡找雜湊值和官方逐一相同的那一個，下載之後在本機重算一次再比對：

鏡像結果
unsloth/Llama-3.2-1B-Instruct權重 model.safetensors 相同，但 tokenizer.json、tokenizer_config.json、special_tokens_map.json、config.json、generation_config.json 都改過。tokenizer 和生成設定會直接影響結果，沒有用。
alpindale/Llama-3.2-1B-Instruct8 個檔（權重、config、generation_config、3 個 tokenizer 檔、LICENSE.txt、USE_POLICY.md）全部和官方 revision 9213176726f5 的記錄相同。權重 2,471,645,608 bytes，sha256 開頭 1ff795ff6a07。採用。

下載下來的檔案名義上屬於 alpindale 的 repo，程式裡卻寫著 meta-llama/...。為了一個字都不改原版程式，本書在 Hugging Face 的本機快取裡建了一個 models--meta-llama--Llama-3.2-1B-Instruct 條目：refs/main 寫官方的 revision，裡面的每個檔都是指向鏡像檔案的符號連結。執行時加上 HF_HUB_OFFLINE=1，transformers 就不上網，直接從這個條目讀取。三個審查模型裡的兩個 Llama Guard 也用同樣方式取得，雜湊值同樣全部和官方相同；ShieldGemma 2B 則是直接從 Google 官方的 repo 下載。

動手做：自己核對一次雜湊值

雜湊值核對的價值在於「不用相信任何人」：只要官方的記錄和你手上的檔案算出同一個 sha256，兩者就是同一串位元。可以用 huggingface_hub.HfApi().model_info(repo, files_metadata=True) 讀官方記錄，用 sha256sum 算本機的檔案。注意小檔記錄的是 git blob 的 sha1，算法是對 "blob <長度>\0" 加上檔案內容取 sha1，和直接對檔案算 sha1 不同。本書的核對工具一開始就在這裡犯過錯：把用 LFS 存的 tokenizer.json 當成小檔，誤報成不一致。

把這些函式串起來的是 main。前半段處理選項、載入模型、準備訓練資料：

第 291–292 行是本 repo 加的：notebook 從頭到尾沒有設定 torch 的亂數種子，而 LoRA 的初始值又是在 load_model 裡用 torch 的亂數產生的，所以原版每跑一次，訓練的起點就不同（第 2 章）。不給 --seed 時這兩行什麼都不做，行為和原版相同。第 296–298 行同樣是本 repo 加的，對應投影片 Strong 提示的「固定 few-shot 範例」：給了 --fixed-shots-seed 才會用固定種子從訓練集抽出一組範例，所有題目共用（第 8 章）。第 299–300 行的註解記下一個不容易注意到的細節：格式化訓練資料時呼叫了 7,473 次 random.sample，但這些抽樣不會影響評估時每一題配到哪個 few-shot 範例。原因是 transformers 的 Trainer 建立時會呼叫 set_seed(1126)，連 Python 的 random 一起重設；訓練過程本身又完全不用 Python 的 random（本書用一個小模型實測過，訓練完的亂數狀態和剛設好 1126 時一模一樣）。所以不管訓練設定怎麼改，評估時的 few-shot 範例都由 1126 決定（第 1 章）。

後半段訓練、評估、寫檔：

第 307 行用 trainer.state.global_step 算出最後一個 checkpoint 的路徑；notebook 是把 sft/checkpoint-1868 直接寫死在程式裡，資料量或 epoch 數一改，路徑就錯了。第 308–309 行是 --skip-train（只評估一個現成的 checkpoint）時的處理：沒有 Trainer 幫忙重設亂數，就自己呼叫 random.seed(1126)，讓評估的 prompt 和訓練完再評估時相同。第 320–321 行和 notebook 的最後一格一模一樣：用 print 把 list 印進檔案，所以檔案內容就是 Python 的 list 寫法，讀回來要用 ast.literal_eval。第 322 行的 responses.json 是本 repo 加的。

拆檔時刻意保留了幾個看起來可以順手改掉的地方，因為它們會影響結果：

  • make_generator 裡那行 pipeline.model = PeftModel.from_pretrained(...)，設定的對象是 pipeline 這個函式，不是生成器。它看起來是錯的，實際上卻有作用；而且它會用掉一次 torch 的亂數，拿掉之後後面每一題的取樣結果都不同（第 4 章）。
  • import 時的 random.seed(42)，以及評估時 few-shot 範例從訓練集每題重抽的寫法（第 1 章）。
  • tokenizer 加了 [PAD] 卻沒有擴大 embedding（第 2 章）。

0.6　怎麼證明拆完沒有改變結果

拆檔最怕的是不知不覺改到行為。驗證的方法是做一份參照版：把 notebook 的程式格原封不動串成一支腳本，只把 8 行 ! 開頭的 shell 指令註解掉，然後讓參照版和 hw6.py 各跑一次，逐位元比對結果。

只靠「同一份程式跑兩次」還不夠，因為 GPU 上的計算預設不保證每次都一樣。比對時兩邊都用同一個 wrapper 執行：它打開 PyTorch 的決定性模式，並固定 torch 的啟動種子，然後才執行目標腳本，腳本本身一字不改：

比對工具 docs/tools/hw06_compare_runs.py 把兩次執行的 10 個 checkpoint 逐一用 torch.equal 比對每個張量，再把兩份 504 筆的 list 逐筆比對。同一天各跑一次參照版和 hw6.py，結果是：

  checkpoint-187: 224 tensors, identical
  checkpoint-374: 224 tensors, identical
  checkpoint-561: 224 tensors, identical
  checkpoint-748: 224 tensors, identical
  checkpoint-935: 224 tensors, identical

每個 checkpoint 有 224 個張量：16 層 × 7 種投影層 × 每層 LoRA 的兩個小矩陣（A 和 B）。權重完全相同，交出去的 504 筆答案一筆都沒有不同。兩邊的 GSM8K public Accuracy 都是 0.326，train_loss 都是 0.852828219820141。

這個結果有兩個前提，要說清楚：

  • 必須同一天跑。一開始拿前一天的參照版來比，checkpoint 完全相同，504 筆答案卻有 407 筆不同。追查了很久，最後發現原因是 0.3 節那行 Today Date：評估的每一個 prompt 都帶著當天日期，日期一變，答案就跟著變。把日期固定成前一天之後重跑，就和前一天的結果逐位元相同。整個追查過程在第 6 章。
  • 比對的是加選項之前的版本。逐位元驗證之後，hw6.py 又多了 --fixed-shots-seed 和 --completion-only-loss 兩個選項。新增的程式都包在「有給選項才執行」的條件裡：不給選項時，few-shot 照樣呼叫原本的 random.sample，SFTTrainer 收到的參數也和原本一樣，所以預設行為沒有改變。

  • 作業要同時提升 GSM8K Accuracy、守住 AILuminate Safety Rate；交出去的是 264 個答案加 240 個回答，共 504 筆的 list。
  • Safety Rate 靠另一個模型判斷，課程沒說是哪一個；本書用三個審查模型，數字只能互相比較，不能和投影片的基準線比。
  • Llama-3.2-1B-Instruct：16 層、hidden 2048、32 個 query 頭與 8 個 KV 頭（GQA）、MLP 8192、詞彙 128,256、embedding 和 lm_head 共用，總共 1,235,814,400 個參數。
  • chat template 會自己加一段 system header，裡面有執行當天的日期。
  • 模型從雜湊值和官方完全相同的公開鏡像取得，透過本機快取讓程式照用官方名稱。
  • hw6.py 和 notebook 原樣串成的參照版，在同一天、決定性模式下跑出逐位元相同的 checkpoint 與答案。

自我測驗

1. 為什麼本書的 Safety Rate 不能和投影片的基準線 0.558 比較，GSM8K Accuracy 卻可以？

Accuracy 有標準答案，抽數字比對的方法和評分平台相同。Safety Rate 是由一個審查模型判斷回答安不安全，投影片沒寫助教用的是哪個模型；本書換用的三個審查模型寬嚴不同，對同一批回答給出的比例差很多，所以只能拿本書自己的數字互相比較。

2. 用 0.3 節的數字算一下：如果把 k_proj 和 v_proj 也做成 32 個頭（不用 GQA），一層 attention 會多出多少參數？

k_proj 和 v_proj 會從 (512, 2048) 變成 (2048, 2048)，各多 2048 × 2048 − 512 × 2048 ＝ 3,145,728 個，兩個合計多 6,291,456 個。一層 attention 會從 10,485,760 變成 16,777,216，16 層總共多出約 1 億個參數。GQA 也讓生成時要快取的 key、value 只剩四分之一。

3. 為什麼核對鏡像時不能只比權重檔，tokenizer 和 generation_config 也要比？

tokenizer 決定文字怎麼切成 token、chat template 長什麼樣、哪些是特殊 token；generation_config 提供生成時的預設參數。unsloth 的鏡像權重和官方相同，但這幾個檔改過，用它跑出來的 prompt 或生成行為就可能和官方模型不同，結果也就不能代表原版作業。

4. 格式化訓練資料時抽了 7,473 次 few-shot 範例，為什麼評估時每一題配到的範例卻和這些抽樣無關？只做評估（--skip-train）時，hw6.py 怎麼讓 prompt 和訓練過的流程一致？

訓練開始前，Trainer 會呼叫 set_seed(1126)，把 Python 的 random 也重設成 1126，而訓練過程不使用 Python 的 random，所以評估時的抽樣一律從「剛設好 1126」的狀態開始。--skip-train 時沒有建立 Trainer，hw6.py 就自己呼叫 random.seed(1126) 補上這一步（第 308–309 行）。

5. 參照版和 hw6.py 拿不同天的結果來比，會發生什麼事？為什麼 checkpoint 卻完全相同？

交出去的答案會有大量不同（實測 504 筆有 407 筆不同），因為評估的 prompt 裡有 chat template 寫入的當天日期，日期不同 prompt 就不同。訓練資料在格式化時把含有日期的 system header 切掉了，所以訓練和日期無關，checkpoint 完全相同。
