ML2025 Spring HW03 教材

補充章　認識 Gemma-2-2b-it：這份作業拆的是什麼模型

HW03 的七題都在同一個模型上動手：看它吃進什麼格式、怎麼選下一個字、內部的向量與注意力長什麼樣。這個模型是 Google 在 2024 年 7 月釋出的 Gemma-2-2b-it。這一章先認識它：它屬於哪個家族、名字的每一段是什麼意思、是怎麼訓練出來的、技術報告怎麼描述它的架構，以及「-it」版和它的原始版（pt）到底差在哪裡。後者本機把兩個模型並排放上 GPU，直接量了權重與行為的差別。

本章重點

Gemma-2-2b-it 是 Google 開放權重的小型語言模型：decoder-only transformer，26 層、2,614,341,888 個參數，用 2 兆個（主要是英文的）token 預訓練，而且不是自己從頭學「下一個字」，而是向一個更大的老師模型學它的機率分布（knowledge distillation）。預訓練完的版本叫 gemma-2-2b（pt）；再經過監督式微調、RLHF 與模型平均，才得到會照對話指示回答的 gemma-2-2b-it。本機實測兩者的 config 只差停止 token 與 dtype，attention 與 MLP 的權重矩陣平均只變了約 7.6%，行為卻完全不同：pt 拿到對話格式只會重複題目，it 會回答。

  • 為什麼有這一章：目錄頁與第 0 章都直接從「載入模型」開始，沒有交代這個模型的來歷。後面每一章的現象（對話格式、tokenizer、<end_of_turn> 之後的 <eos>、pt 版的 SAE）都和它的訓練方式有關，這裡先一次講清楚。結構的細節（每層的形狀、參數怎麼算）仍在第 0 章，本章只回指。
  • 本章的外部資料原文摘錄在 docs/HW03/logs/sources_gemma.txt（下文寫成 logs/…），檔案裡用代號分段：[P] Gemma 2 技術報告（下稱「技術報告」，arXiv:2408.00118v3）、[C] Hugging Face 上的模型卡（google/gemma-2-2b-it 的 README）、[S] Gemma Scope 論文摘要（arXiv:2408.05147）、[B] Google 部落格的發表文、[H] Hugging Face 網站 API 查到的 repo 資訊。引用時保留英文原句。
  • 本章的實測數字來自 logs/facts_gemma.txt（工具 docs/tools/hw03_gemma.py 的輸出，各段以 ==== files ==== 這種標題分開，下文寫成「files 段」等）與 logs/facts_review1_ptit.txt（G.8 節）；第 0 章已經量過的參數量與記憶體，出處見第 0 章。

G.2　Gemma 家族：從 Gemini 分出來的開放模型

模型卡第一句話就交代了它的來歷：

Gemma is a family of lightweight, state-of-the-art open models from Google, built from the same research and technology used to create the Gemini models. They are text-to-text, decoder-only large language models, available in English, with open weights for both pre-trained variants and instruction-tuned variants.

— 模型卡 Description（logs/sources_gemma.txt 的 [C] 段）

拆開來看：Gemini 是 Google 的旗艦模型系列；Gemma 是用同一套研究與技術做出來、開放權重（任何人都能下載完整參數）的輕量版。它是「text-to-text」：輸入文字、輸出文字，不吃圖片；「decoder-only」是指只有 transformer 的 decoder 那一半，一次預測下一個 token（第 0 章的 CausalLM）；每個尺寸都同時釋出 pre-trained（預訓練完的原始版）與 instruction-tuned（微調成會對話的版本）兩種權重。

G.4　它是怎麼訓練出來的

G.4.1　預訓練：2 兆個 token，向老師學機率分布

技術報告 3.1 節：「We train Gemma 2 27B on 13 trillion tokens of primarily-English data, the 9B model on 8 trillion tokens, and the 2B on 2 trillion tokens.」資料來自網頁、程式碼與科學文章；報告也直接說「Our models are not multimodal and are not trained specifically for state-of-the-art multilingual capabilities.」這就是為什麼本書所有的 prompt 都是英文：模型卡同樣寫明它是「available in English」。第 3 章看到的中文切法（一個字一個 token 的情況不少），也要放在這個背景下理解：詞表繼承自多語言的 Gemini，但訓練資料以英文為主。

真正特別的是怎麼學。一般語言模型的預訓練是「next token prediction」：看前文，猜下一個 token，正確答案是一個 one-hot 向量（只有實際出現的那個 token 是 1，其餘 256,000 多個都是 0）。Gemma 2 的 2B 與 9B 不這樣做，摘要寫的是：

We also train the 2B and 9B models with knowledge distillation (Hinton et al., 2015) instead of next token prediction.

— 技術報告摘要

knowledge distillation（知識蒸餾）的意思是：先有一個比較大、已經訓練好的老師模型，讓它對同一段前文算出「下一個 token 的機率分布」，小的學生模型要學的就是這整個分布，而不是只有正確答案那一個 token。報告前言的說法是，蒸餾「replaces the one-hot vector seen at each token with the distribution of potential next tokens computed from a large model」。3.2 節寫成式子：

minPS Σx −PT(x | xc) · log PS(x | xc)

其中 xc 是前文（context），PT 是老師給的機率、PS 是學生的機率，加總跑過詞表裡每一個 token x。如果 PT 換成 one-hot，這個式子就退化成一般的 cross-entropy（只剩正確 token 那一項）；蒸餾讓學生同時學到「哪些 token 也算合理、各有幾分合理」。第 2 章 Q2 請模型說出一個彩虹的顏色，印出的 top-10 機率表（第一輪 Indigo 0.3068、Green 0.2624、Red 0.2012……）就是這種「分布」的樣子。

效果有多大？報告的 Table 6 做了一個縮小版的對照：同樣是 2B 模型、同樣訓練 500B 個 token，從頭訓練的三項評測平均 60.3，從一個 7B 老師蒸餾的平均 67.7。前言也說，2B、9B 訓練的 token 量是理論上「計算最省」的數量的 50 倍以上（「more than 50 × the compute-optimal quantity」）：用蒸餾，讓小模型能從大量資料裡持續學到東西。

訓練用的 tokenizer 和 Gemma 1、Gemini 相同（3.1 節）：「a SentencePiece tokenizer with split digits, preserved whitespace, and byte-level encodings … The resulting vocabulary has 256k entries.」數字一位一個 token、保留空白（▁）、詞表裡沒有的字元拆成位元組，第 3 章逐一實測過這三件事。

G.4.2　post-training：把 pt 變成會對話的 it

技術報告第 4 節：「For post-training, we fine-tune our pre-trained models into instruction-tuned models.」依序做三件事：

  1. SFT（supervised fine-tuning，監督式微調）：拿「提示 → 回答」的配對資料繼續訓練。報告說回答「predominantly synthetically generated by the teacher」，大多是由較大的老師模型生成的；也同樣做了蒸餾。
  2. RLHF（reinforcement learning from human feedback）：先用人類標註的偏好資料（「兩個回答哪個比較好」）訓練一個 reward model，再用強化學習讓模型的回答往高分的方向調。報告特別提到這個 reward model「an order of magnitude larger than the policy」，比被調整的模型大一個數量級。
  3. model merging（模型平均）：用不同超參數各跑一次上面的流程，把得到的幾個模型的權重平均起來。

微調時用的對話格式，就是第 1 章拆過的 chat template。技術報告的 Table 4 列出控制 token：<start_of_turn>、<end_of_turn>（一則對話訊息的開始與結束）、<bos>（beginning of sequence，整段序列的開頭）、<eos>（end of sequence，序列結束），角色名稱是 user 與 model。生成時，模型一吐出被指定為停止 token 的 id，generate 就停下來。接著有一句和本書直接相關的話：

Notice that the model explicitly ends generations with <end_of_turn><eos> tokens, while previously it only generated <eos>.

— 技術報告第 4 節 Formatting

it 模型被訓練成「說完話先打 <end_of_turn>，再打 <eos>」。第 4 章 4.5.2 節的 R3（G.1 節說的編號）實測正好看到這件事：Q4 傳給 generate 的參數把停止 token 蓋成只剩 <eos>，模型生成 <end_of_turn> 之後沒有停，下一步以機率 1.0000 接上 <eos>。這也是為什麼 it 版的 config 把兩個都列為停止 token（eos_token_id 是 [1, 107]，第 1 章 1.3.2 節），而 pt 版只有 1（G.6 節）。

G.5　架構：技術報告怎麼說，本機的 config 怎麼寫

Gemma 2 是 decoder-only transformer（報告第 2 節：「the Gemma 2 models are based on a decoder-only transformer architecture」）。報告列出和第一代相同的部分：「a context length of 8192 tokens, the use of Rotary Position Embeddings (RoPE) …, and the approximated GeGLU non-linearity」，以及幾項新的設計。下表把每一項對到本機 config 的欄位與第 0 章的段落（config 欄位取自 logs/facts_gemma.txt）：

G.5.1　報告和 config 對不上的兩個數字

把 Table 1、Table 2 和本機量到的數字逐一對照（第 0 章 0.8 節的參數量是 PyTorch 實際數的）：

項目技術報告本機對得上嗎
non-embedding 參數2,024,517,8882,024,517,888完全相同
embedding 參數590,118,912589,824,000差 294,912 = 128 × 2304
詞表大小256128256000差 128
Feedforward dim184329216剛好兩倍

詞表：590,118,912 = 256128 × 2304，所以報告的 embedding 參數是照 256128 列算的；Hugging Face 釋出的 checkpoint 只有 256000 列，tokenizer 的最大 id 是 255999（logs/facts_gemma.txt）。差的 128 列是什麼、為什麼沒有釋出，報告與模型卡都沒有交代，本書不猜。對作業沒有影響：所有 token id 都落在 0–255999 之內。

Feedforward dim：config 的 intermediate_size 是 9216，MLP 的 gate_proj 與 up_proj 各把 2304 維投影到 9216 維（0.8 節）。18432 = 2 × 9216，推論是報告把 gate 與 up 兩個投影合起來算（GeGLU 需要兩個並排的投影）；報告沒有明說，這一句是推論。

non-embedding 參數一個不差，說明兩邊講的是同一個模型；實物上的差異只有詞表這 128 列，FFN 則是（推論的）算法不同。讀論文、讀模型卡、讀 config，數字都要對照實物，這也是本書每章「讀 code 不盡信文件」的精神。

G.6　pt 與 it：同一個骨架，兩份權重

本機逐項比較 google/gemma-2-2b（pt）與 google/gemma-2-2b-it（it）（logs/facts_gemma.txt）：檔案與設定直接讀下載下來的檔案，權重差異直接從權重檔在 CPU 上算，行為比較則把兩個模型都以 fp16 載入同一張 GPU（合計 9.74 GiB）。重跑的方法見章末延伸閱讀。

chat template沒有（呼叫 apply_chat_template 會丟出 ValueError）有（第 1 章拆的那一段）

pt 的權重檔大一倍，只是因為存成 fp32；參數個數一樣。模型卡說 it 的權重「were exported in bfloat16 precision」，hw3.py 則以 fp16 載入（第 0 章 0.4 節），所以讀進來時每個數都從 bf16 轉成 fp16。兩者都是 2 bytes，但分配不同：bf16 的指數位多、能表示的範圍大、精度較低；fp16 精度較高、範圍較小。轉換會帶來極小的捨入差異，本書所有數字都是 fp16 載入後量的。

最值得注意的是最後一列：pt 的 tokenizer 根本沒有 chat template。對話格式不是模型架構的一部分，而是 post-training 時教會模型的一種「書寫慣例」，template 只是幫你把字串排成那個慣例。pt 沒學過這個慣例，給它 template 也沒有意義；下一小節實測就看得到。

G.6.2　權重改了多少

對每一類參數算「it 和 pt 差多少」：把 it 減 pt 的差值矩陣取 Frobenius 範數（所有元素平方和開根號），除以 pt 本身的範數，同一類參數把 26 層合起來算。直接讀兩個模型的權重檔（pt 是 fp32、it 是 bf16，都轉成 fp32 再算）。結果（logs/facts_gemma.txt 的 weights 段）：

參數類別相對變化
MLP：down_proj、gate_proj、up_proj0.0852、0.0847、0.0805
attention：k_proj、o_proj、q_proj、v_proj0.0576、0.0571、0.0570、0.0552
embedding（embed_tokens）0.0326
四種 RMSNorm、最後的 norm0.0020–0.0037
attention 與 MLP 的權重矩陣合計0.0756
全部參數合計0.0353

attention 與 MLP 這些權重矩陣平均動了約 7.6%：MLP 約 8%，attention 約 5.7%。「全部參數」只有 3.5%，是被另外兩類拉低的：embedding 本身的範數最大（範數平方約是 attention 與 MLP 所有矩陣合計的 5.7 倍，計算值），只改了 3.3%；norm 的權重數值也不小（例如每層 post_feedforward_layernorm 權重的平均絕對值約 1.42），卻幾乎沒動。所以「改了幾 %」要看是對哪些參數算的。embedding 的每一列和 pt 版的 cosine 相似度平均 0.9995、最低 0.9805；對話用的 <start_of_turn>、<end_of_turn> 也分別是 0.9996、0.9977，代表這兩個 token 的 embedding 在預訓練時就已經存在（詞表本來就有它們），微調幾乎沒改它們的向量。

逐層看，把每一層的 attention 與 MLP 分開算（norm 不算進去，否則它的大範數會把整層的比例壓低）：

每一層都改了，沒有哪一層幾乎不動；每一層都是 MLP 改得比 attention 多，後半段的層比最前面幾層略多。為什麼是這個形狀，技術報告沒有討論，本機也沒有做實驗分辨原因，這裡只記錄現象。權重的相對變化只是一種量法：平均不到一成的改動，就足以讓行為完全不同（下一小節）。

G.6.3　同一個輸入，兩種反應

四個輸入，兩個模型都用 greedy 生成（每一步都取機率最高的 token；logs/facts_gemma.txt 的 behaviour 段；引號內是模型原文，\n 是換行）：

(1) Q1 的問題，套上 chat template（31 個 token，就是第 1 章「有 template」的那條路）：

  • pt：「Please tell me about the key differences between supervised learning and unsupervised learning. Answer in 200 words. Answer in 200 words. Answer in 200 words. …」。它不認得 <start_of_turn>model 是「該你回答了」，只把前文最像的東西接下去：把題目抄一遍，再一直重複最後一句。第一個 token 是 Please（0.1872）。
  • it：「Supervised and unsupervised learning are two fundamental approaches in machine learning. …」，第一個 token Super 的機率 0.6631，直接開始回答。

(2) 同一個問題，不套 template（23 個 token，第 1 章「沒有 template」那條路）：兩者的第一個 token 都是換行 \n\n（pt 0.4585、it 0.9182）。pt 接著寫一段一再重複的定義（「The model is trained on a set of labeled data and the model is trained to predict …」）；it 寫成條列的 Markdown（「**Supervised Learning:** …」）。it 即使沒有 template 也會「回答」，只是格式不同：第 1 章 Q1 比較的正是這種差別。

(3) 「The capital of France is」：pt 接「a city of contrasts. It is a city of art, culture, and history. It is a」；it 接「Paris. \n\nIs this statement true or false?\n\nThe statement is **true**.」pt 只是在續寫一段像網頁的文字，it 則把它當成一個要回應的問題。

(4) 「Professor Hung-yi Lee teaches」：pt 接「in the Department of English at the University of California, Irvine. He is the author of」；it 接「at the University of California, Berkeley. He is a renowned expert in the field of artificial intelligence and」。兩個都是錯的：李宏毅老師在台灣大學任教，本作業所屬的課程就是台大的 ML 2025。模型會用流暢、有自信的語氣講出錯誤的事實，模型卡的 Limitations 也寫了：「They may generate incorrect or outdated factual statements.」

pt 與 it 的差別在「行為」，不在「知識」

四個例子合起來看：it 沒有比 pt 多知道什麼（第 4 例兩者都錯），它學會的是互動的方式：看到對話格式就回答、回答完會收尾、會把一句話當成問題來回應。post-training 只把權重矩陣改了不到一成，改的正是這一層「怎麼用已有的知識」。這是推論，綜合了本節的四個例子與 G.4.2 節技術報告的描述；本機沒有用評測集量兩者的知識量。技術報告 Table 17 有一組相關的數字：2B 的 MMLU（知識型選擇題）pt 52.2、it 56.1，微調後也只多了幾分。

G.7　能力與限制

技術報告與模型卡都附了評測。這些是業界常用的考題集：MMLU 是涵蓋幾十個學科的知識型選擇題、HellaSwag 與 ARC-c 是常識與推理題、GSM8K 與 MATH 是數學題、HumanEval 是寫程式題。「5-shot」是指題目前面先附 5 個示範例題再問，「pass@1」是指生成一次程式就通過測試的比例。兩份文件的數字不完全一樣，引用時要註明出處：

評測（pt 版 2B）技術報告 Table 13模型卡

HellaSwag（10-shot）72.973.0
ARC-c（25-shot）55.755.4

兩份文件都沒有說明差異從哪裡來，本書不猜。用來比較的話，技術報告同一張表的第一代 Gemma 2B 是 MMLU 42.3，第二代多了將近 10 分；同表 Gemma 2 9B 是 71.3、27B 是 75.2。2B 是三個尺寸裡最弱的，這是它換來「一張 GPU 跑得動」的代價。

對話能力的部分，技術報告 Table 14 列出 LMSYS Chatbot Arena（由人類盲測兩兩比較、算出 Elo 分數的排行榜）：gemma-2-2b-it 的 Elo 是 1126（±10），gpt-3.5-turbo-0613 是 1116。Google 部落格據此寫「Gemma 2 2B surpasses all GPT-3.5 models on the Chatbot Arena」（分數擷取於 2024-07-30）。這是一個時間點的排行榜分數，不同時間、不同對手組合都會變。

本書會直接碰到的限制：

  • 主要是英文：G.4.1 節引過「primarily-English data」。
  • 會編造事實：G.6.3 節的第 4 例。
  • 對格式敏感：技術報告 Table 11 量了 MMLU 在 12 種提示格式下分數的標準差，Gemma 2 2B 是 2.1，9B 是 0.9、27B 是 1.0，報告的說法是「The Gemma 2B models are slightly less format-robust than the larger ones」。第 1 章看到「同一個問題，套不套 template，回答與分數差很多」，第 2 章看到雙 <bos> 換成單 <bos> 回答就變了，都是這個特性的實例。
  • 上下文長度 8192：本作業的序列最長只有幾百個 token，碰不到。

G.8　Gemma Scope：為 Q7 準備的顯微鏡

和 Gemma 2 2B 同一天發表的 Gemma Scope，是 Q7 的主角。論文摘要（logs/sources_gemma.txt 的 [S] 段）：

In this work, we introduce Gemma Scope, an open suite of JumpReLU SAEs trained on all layers and sub-layers of Gemma 2 2B and 9B and select layers of Gemma 2 27B base models. We primarily train SAEs on the Gemma 2 pre-trained models, but additionally release SAEs trained on instruction-tuned Gemma 2 9B for comparison.

— Lieberum et al., Gemma Scope, arXiv:2408.05147

SAE（sparse autoencoder，稀疏自編碼器）把模型某一層的 hidden state（2304 維）拆成上萬個「feature」的組合，而且每次只有少數幾個 feature 是亮的；理想上每個 feature 對應一個人看得懂的概念。JumpReLU 是 Gemma Scope 採用的一種 SAE 設計（決定 feature 亮不亮的函數），細節留到第 8、9 章。這裡要記住的是摘要的第二句：2B 的 SAE 是在 pt 上訓練的，論文只為 9B 另外釋出了 it 版的 SAE。

sae_lens 是載入這些 SAE 的 Python 套件；release 名稱裡的 2b-pt-res 就是「2B、pt、residual stream」（residual stream 指每一層 decoder 輸出、一路往下一層傳的那條主幹向量，也就是 hidden state），width_16k 是這個 SAE 有約 16k 個 feature。也就是說，Q7 拿一個在 pt 上校正過的 SAE，去解讀 it 模型的 hidden state。這樣做可以嗎？本書在規劃階段實測過（logs/facts_review1_ptit.txt）：用 Q7 的三句測試句，把 pt 與 it 的 hidden state 分別交給同一個 SAE。以第三句、SAE 訓練時的那一層為例，重建誤差（FVU，越小越好）it 是 0.290、pt 是 0.238，it 略大但同一個數量級；Q7 關心的 feature 10004 在兩個模型上都在 ▁travel 那個位置最亮（it 71.23、pt 51.82）。數值會變，結論不變，這是那三句話的實測，不是一般性的結論。G.6.2 節的「權重矩陣只改了約 7.6%」提供了一個合理的背景：兩個模型的內部表示本來就很接近（推論）。

G.9　授權、下載與檔案

Gemma 的權重是開放的，但不是無條件公開：

  • 授權：模型卡標註的 license 是 gemma，也就是 Google 的 Gemma Terms of Use，不是 MIT、Apache 這類常見的開源授權。
  • gated：Hugging Face 上的 google/gemma-2-2b-it 是 gated（有門禁的）模型。要先在模型頁登入、按下同意授權，再在 HF 帳號設定裡建立一個 read token（唯讀權杖），讓程式用它存取。作業投影片（repo 裡的 HW03/hw3.pdf）p.5–11 一步一步示範；在本機登入的指令與沒有授權時的錯誤訊息見第 0 章 0.1 節。連模型卡（README）本身都要登入後才讀得到。
  • 檔案：it 版下載下來是兩個 BF16 的 safetensors（共約 5.23 GB），加上 tokenizer（tokenizer.json 17.5 MB、SentencePiece 的 tokenizer.model 4.2 MB；logs/facts_gemma.txt 的 files 段）與模型卡；本機的 HF 快取裡整個 repo 佔 5.251 GB（第 0 章 0.4 節）。pt 版是 fp32，約 10.5 GB，本作業用不到，只有本章的對照與 Q7 的審稿實驗下載過。

讀 code 不盡信文件：模型卡的範例和 hw3.py 不一樣

模型卡示範 chat template 時，最後是這樣把 prompt 交給模型的：tokenizer.encode(prompt, add_special_tokens=False, return_tensors="pt")。add_special_tokens=False 讓 tokenizer 不要再加一個 <bos>，因為 template 的字串已經以 <bos> 開頭。hw3.py 的 Q1、Q2 照原版 Colab 用預設值，於是模型收到兩個 <bos>：這就是全書第一個「刻意保留的怪地方」R1（第 1 章 1.7 節）。模型的官方文件本身就示範了正確寫法。

G.10　常見錯誤

把 2B 當成精確的參數量

症狀
用 2 × 109 × 2 bytes 估記憶體，或說「這個模型有 20 億個參數」。
後果
實際是 2,614,341,888 個，比 20 億多了三成；fp16 佔 4.87 GiB，不是 2 × 109 × 2 bytes ≈ 3.7 GiB。
正解
2B 是級別名稱；精確數字照 第 0 章 0.8 節用 PyTorch 數，技術報告也會寫成 2.6B。

對 pt 模型套 chat template

症狀
下載 google/gemma-2-2b（沒有 -it）來做 Q1，回答只是一直重複題目；或用 pt 自己的 tokenizer 呼叫 apply_chat_template，直接丟出 ValueError: Cannot use chat template functions because tokenizer.chat_template is not set …（本機實測，logs/facts_gemma.txt 的 tokenizer 段）。
後果
以為程式寫錯，或以為模型壞了。
正解
pt 沒學過對話格式，它的 tokenizer 也沒有 chat template（G.6.1 節）。作業用的是 -it。

以為 it 比 pt 「懂得比較多」

症狀
相信 it 版講的事實，因為它語氣比較像在回答問題。
後果
把編造的內容當真，例如它說李宏毅老師在 UC Berkeley。
正解
post-training 主要改變的是互動方式（G.6.3 節）；事實要另外查證。

技術報告、模型卡、config 的數字混著用

症狀
說詞表是 256128、MMLU 是 51.3，又拿 config 的 256000 去算 embedding 參數。
後果
前後對不上，看起來像算錯。
正解
每個數字註明出處；要和程式對照時，以 config 與實際張量為準（G.5.1 節、G.7 節）。

以為 Gemma Scope 的 SAE 是為 it 訓練的

症狀
把 Q7 的 feature 數值當成 SAE 在它校正過的模型上的表現。
後果
高估了 SAE 在作業裡的重建品質。
正解
2B 的 SAE 是在 pt 上訓練的（G.8 節）；本機實測用在 it 上數值會變、結論不變。

本章小結

  • Gemma 是 Google 用 Gemini 的研究與技術做出的開放權重模型家族；Gemma 2 有 2B、9B、27B，2B 於 2024-07-31 發表，同日發表的還有 Gemma Scope。
  • 名字：gemma-2 是第二代，2b 是級別（實際 2,614,341,888 個參數，報告也寫 2.6B），-it 是 instruction-tuned；沒有尾巴的 gemma-2-2b 是預訓練版 pt。
  • 預訓練用 2 兆個主要是英文的 token，而且 2B 是用 knowledge distillation 學老師模型的機率分布；post-training 依序做 SFT、RLHF、模型平均，並教會它以 <end_of_turn><eos> 收尾（第 4 章 R3 的來源）。
  • 架構：decoder-only、local／global attention 交替、GQA、soft-cap 50／30、pre 與 post RMSNorm、GeGLU、RoPE、8192 context、tied embedding。技術報告的 non-embedding 參數和本機一個不差；實物上只差詞表的 128 列（256128 vs 256000，原因兩份文件都沒說）；FFN 18432 vs 9216 推論是算法不同。
  • pt 與 it 的 config 只差停止 token 與 dtype，tokenizer 詞表相同但 pt 沒有 chat template；attention 與 MLP 的權重矩陣只變了約 7.6%（MLP 約 8%、attention 約 5.7%，每一層都有改；norm 幾乎不動）；行為卻完全不同，而兩者都會編造事實。
  • Q7 用的 SAE 是在 pt 上訓練的；hw3.py 照原版用了兩個 <bos>，模型卡自己示範的是 add_special_tokens=False。

自我測驗

1. google/gemma-2-2b-it 這個名字的四段各代表什麼？為什麼說「2B」不是精確數字？

google 是 Hugging Face 上的組織；gemma-2 是 Gemma 第二代；2b 是尺寸級別；-it 是 instruction-tuned，對應的預訓練版是沒有尾巴的 gemma-2-2b。實際參數是 2,614,341,888 個，約 26 億，技術報告也寫成 2.6B；2B 只是三個尺寸（2B、9B、27B）裡的級別名稱。

2. knowledge distillation 和一般的 next token prediction 差在哪裡？用第 2 章彩虹那一題的機率表說明「學生學到的東西」多了什麼。

一般預訓練的目標是 one-hot：只有實際出現的那個 token 算對。蒸餾的目標是老師模型對下一個 token 的整個機率分布。以第 2 章第一輪為例，如果實際文字接的是 Indigo，one-hot 只告訴學生「答案是 Indigo」；分布則告訴它 Indigo 0.3068、Green 0.2624、Red 0.2012……，也就是「其他顏色也很合理、各有幾分合理」。學生從每一個位置學到的資訊因此多得多。（這裡借用第 2 章的數字只為說明形式：那張表是 Gemma-2-2b-it 自己的輸出，不是它訓練時老師給的分布。）

3. 第 4 章 R3 看到：停止 token 只剩 <eos> 時，模型生成 <end_of_turn> 之後，下一步幾乎一定接 <eos>。技術報告怎麼解釋這個習慣？pt 版的 config 為什麼只有一個停止 token？

技術報告第 4 節說 Gemma 2 的 it 模型被訓練成「explicitly ends generations with <end_of_turn><eos> tokens」，所以它說完話會先打 <end_of_turn> 再打 <eos>。it 的 config 因此把 1（<eos>）與 107（<end_of_turn>）都列為停止 token。pt 沒有經過對話格式的微調，不會用 <end_of_turn> 收尾，config 的 eos_token_id 只有 1（本機實測兩份 config 只差這一欄與 dtype）。

4. 技術報告說 2B 的 embedding 參數是 590,118,912，第 0 章用 PyTorch 數出來是 589,824,000。差了多少？從哪裡來？哪一個數字可以拿來算 hw3.py 的記憶體？

差 294,912 = 128 × 2304。報告的詞表是 256128，590,118,912 = 256128 × 2304；Hugging Face 釋出的 checkpoint 詞表是 256000，589,824,000 = 256000 × 2304。為什麼差 128 列兩份文件都沒說。算 hw3.py 的記憶體要用實際載入的張量，也就是 256000 列的版本；non-embedding 的 2,024,517,888 兩邊完全相同。

5. 把同一句 Q1 的問題套上 chat template，分別交給 pt 與 it，本機看到什麼？從這個例子與「李宏毅老師在哪裡教書」的例子，可以說 post-training 主要改變了什麼？

pt 把題目抄一遍，接著一直重複「Answer in 200 words.」；it 直接開始回答（第一個 token Super，機率 0.6631）。問到李宏毅老師，pt 說 UC Irvine 英文系，it 說 UC Berkeley，兩個都錯（他在台大）。合起來看，post-training 改變的主要是互動方式（看到對話格式就回答、回答完會收尾），而不是讓模型多知道事實；這是推論，本機沒有用評測集量知識量。技術報告的 MMLU pt 52.2、it 56.1 也只差幾分。

  • Hugging Face 模型卡：google/gemma-2-2b-it（需要登入並同意授權才看得到全文）。用法、chat template、評測、限制都在裡面。
  • Lieberum et al., Gemma Scope: Open Sparse Autoencoders Everywhere All At Once on Gemma 2, 2024, arXiv:2408.05147：Q7 用的 SAE 從哪裡來。
  • Hinton, Vinyals, Dean, Distilling the Knowledge in a Neural Network, 2015, arXiv:1503.02531：knowledge distillation 的經典論文，技術報告引用的就是這篇。
  • Google 部落格：Smaller, Safer, More Transparent: Advancing Responsible AI with Gemma（2024-07-31，Gemma 2 2B、ShieldGemma、Gemma Scope 的發表文）。
  • 重跑本章的實測：先照目錄頁 3.2 節建好 .venv、照第 0 章 0.1 節登入 HF，並在 google/gemma-2-2b 與 google/gemma-2-2b-it 兩個模型頁都同意授權（只做作業的話只需要 it 版；pt 版是本章對照才用到）。然後在 repo 根目錄執行 .venv/bin/python docs/tools/hw03_gemma.py。第一次會下載約 10.5 GB 的 pt 權重；權重差異在 CPU 上逐個張量讀進來比較；行為比較要把兩個模型同時放上 GPU，約需 10 GiB。結果印在終端機，不會寫進或覆寫 docs/HW03/logs/facts_gemma.txt，可以拿來逐段對照：files、config、tokenizer 與 weights 段應該逐位相同；behaviour 段在相同的 GPU 與套件版本下應該相同，換了 GPU 或版本，生成的文字可能在後段開始不同；load 段的秒數每次都不同。G.8 節 pt 與 it 的 SAE 對照由另一個指令產生：.venv/bin/python docs/tools/hw03_facts.py ptit（同樣需要兩個模型的授權，另外會下載 Q7 用的 SAE），輸出就是 logs/facts_review1_ptit.txt 的 ptit 段，同樣只印在終端機。
