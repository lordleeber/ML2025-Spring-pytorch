第 3 章　Q3 Tokenization：一句話怎麼變成 token id

前兩章一直在說「32 個 token」「Indigo 是 id 173209」，卻沒有停下來看一句話是怎麼被切開的。Q3 只做這一件事：把一句英文交給 tokenizer，印出每一塊的字串與 id，不經過模型。這一章用它把前面欠的帳一次還清：▁ 是什麼、為什麼 Orange 和 ' Orange' 是兩個 token、中文和數字怎麼切、詞表裡沒有的字元怎麼辦。最後教你自己跑出投影片 p.17 的四個空格。

本章重點

3.2.1　為什麼 add_special_tokens=False

encode 的預設是 add_special_tokens=True，會在最前面加一個 <bos>（id 2，特殊 token 見第 1 章 1.1.1 節）。本機實測預設句子用預設值 encode，得到 19 個 token，開頭是 [2, 235285]，也就是 ['<bos>', 'I']（logs/facts_pre_ch03.txt 第 4 行）。

Q3 問的是「這句話被切成哪些 token」，<bos> 不是句子的一部分，是送進模型時才需要的開頭記號，所以 TODO 的註解直接要求「without adding special tokens」，投影片 p.17 的表也從 I 開始。忘了加這個參數，輸出會多一行 Token: <bos>, token index: 2，後面每一行的位置都往下錯一行。

這和第 1 章的雙 <bos>（1.7 節）是同一個參數：那裡因為沒有關掉它，template 已經帶一個 <bos> 的字串又被加了一個；這裡則是明確關掉，只看句子本身。

3.3　▁ 是什麼

  1. 1句首的 I 前面沒有空白，所以沒有 ▁。
  2. 2love 前面有一個空白，那個空白變成了 ▁，黏在 love 的開頭，成為同一個 token。之後每一個英文字都一樣。
  3. 3逗號緊貼在 Lee 後面、前面沒有空白，所以是不帶 ▁ 的 ,。印出來是 ,,：前一個逗號是 token 本身，後一個是 f-string 裡的逗號。
  4. 4you 前面有空白，是 ▁you，id 692。3.7 節會回到這一行。
  5. 5問號緊貼 you，是不帶 ▁ 的 ?，id 235336。

▁（U+2581，「下八分之一方塊」，看起來像底線但不是底線）是 SentencePiece 用的記號。SentencePiece 是一套把文字切成 subword（介於字元與單字之間的小塊）的 tokenizer 工具；它的做法是先把空白換成 ▁，再把整串文字當成一般字元去切，所以空白本身會成為某個 token 的一部分（Kudo & Richardson 2018，見延伸閱讀）。Gemma 的 tokenizer 是 SentencePiece 系的：HF 快取裡除了 tokenizer.json 還有一個 tokenizer.model（第 0 章 0.8 節的快取清單），那就是 SentencePiece 的模型檔。詞表是怎麼訓練出來的（用哪種演算法、怎麼決定哪些片段收進詞表），本機沒有量，這一章不談。

從上面的輸出可以歸納出 Gemma 的規則：空白併進後面那個 token 的開頭。不是前一個字的結尾，也不是單獨一個 token（除了下面幾種例外）。所以 convert_ids_to_tokens 印出的 ▁love，意思是「一個空白加上 love」；decode([692]) 得到的是 ' you'，前面帶一個空白（logs/facts_pre_ch03.txt 第 7 行：id 692: token '▁you', decode ' you'）。第 2 章 2.6 節那個單獨的 ▁（id 235248），decode 出來就是一個空白 ' '。

空白的幾種特殊情況，本機都實測過（logs/facts_pre_ch03.txt、logs/review_ch03_q3.txt）：

3.4　同一個字，不同的 token

上一節的直接後果：同一個字，前面有沒有空白、大小寫不同，就是不同的 token、不同的 id。本機用 Machine 試了四種寫法（logs/facts_pre_ch03.txt）：

字串tokenid
'Machine'Machine24911
'machine'machine26504
' machine'▁machine6479
' Machine'▁Machine13403

四個 id 彼此毫無關係，數字大小也看不出規律。預設句子裡的是 ▁Machine 13403（它在 a 後面、有空白）。同理，you 是 4747、▁you 是 692（圖 3.2）；transformers 140247 與 Transformers 158434 都是單一 token，但 id 不同（logs/facts_pre_ch03.txt）。

這就是第 2 章 2.5 節的那兩條「Orange」：第 2 輪第 1 名的 'Orange'（id 36565）是緊接在 <start_of_turn>model\n 換行後面、不帶空白的版本；第 10 名的 ' Orange'（id 20723）是前面帶空白的版本，依同樣的規則，convert_ids_to_tokens 會印成 ▁Orange，decode 出來是 ' Orange'。小寫的 orange 又是第三個 token。模型輸出的機率是分給 256000 個 token 的，所以「Orange 這個字」的機率被拆散在好幾個 token 上。

模型怎麼知道 you 與 ▁you 是同一個字？從 id 看不出來：它們在 embedding 表（第 0 章 0.5 節的 256000 × 2304）裡是兩列不同的向量，彼此的關係只能在訓練時從資料中學到。本機量了這兩列向量的 cosine 相似度（logs/review_ch03.txt）：you 與 ▁you 是 0.6692，Machine 與 ▁Machine 0.9081，Orange 與 ▁Orange 0.9197；對照組 you 與 ▁Machine 是 −0.0186，隨機抽 10000 對 id 的平均是 0.1640（99% 分位 0.4201）。訓練確實把同一個字的兩種寫法放得很近，但 id 本身完全看不出這層關係。

反過來，一個字也可能被切成好幾塊：unbelievable → un 549、believable 145340；unsupervised → un 549、supervised 122612（logs/facts_env_model_tok.txt）；ChatGPT → Chat 15180、GPT 98502；naïve → na 556、ï 236370、ve 524（這兩個與 unbelievable 都來自 logs/facts_pre_ch03.txt）；第 2 章看過的 Vermilion → Ver、m、ilion。哪些字是一整塊、哪些被拆開，取決於詞表收了什麼，只能實際切切看。

3.5.3　詞表裡沒有的字元：byte fallback，不是 <unk>

詞表只有 256000 格，世界上的字元比這多。遇到詞表裡沒有的字元怎麼辦？常見的說法是「切成 <unk>（unknown）」，Gemma 的特殊 token 裡也確實有 <unk>（id 3）。但本機實測，從來沒有出現 <unk>（logs/facts_pre_ch03.txt）：

字串切成
🙂🙂 237760（一個 token）
👍🏽（豎拇指加膚色）👍 237019、🏽 239518（膚色修飾是另一個字元，各一個 token）
龘龘 250883
éé 235335
𠀀（U+20000，CJK 擴充 B 區的第一個字）<0xF0> 457、<0xA0> 377、<0x80> 345、<0x80> 345
𓀀（U+13000，埃及象形文字）<0xF0> 457、<0x93> 364、<0x80> 345、<0x80> 345

最後兩列就是 byte fallback：字元不在詞表裡，就把它的 UTF-8 編碼拆成一個一個位元組，每個位元組用一個 <0x..> token 表示。𠀀 的 UTF-8 是 f0 a0 80 80 四個位元組，所以變成四個 token。因為任何字串都能寫成位元組，任何輸入都切得出來，不需要 <unk>。本機測的這些字串，decode 都還原成原本的字元。

詞表裡的位元組 token 本機數過：<0x00> 到 <0xFF> 照理是 256 個，實際只有 255 個（id 217–472），缺 <0x09>；它的位置 id 226 是 tab 字元 \t 本身（上一節的 '\tx'）。所以 tab 走的是一般 token，不需要 fallback。為什麼少這一個，本機沒有追。另外，\x07（響鈴這種控制字元）也有自己的一般 token 249340，沒有用到 <0x07>。

代價是長度：一個字元可能變成 4 個 token，比一般文字貴很多。好在詞表已經收了大量的 emoji、罕見漢字與各種文字（฿、ᚠ、🫠 都是單一 token），本機要特地找 U+20000、U+13000 這類字元才碰得到 fallback。

在 repo 根目錄執行（需要 GPU 與 HF 授權，見目錄頁 3.2 節；Q3 本身不用 GPU，但 main 會先載入模型）：

.venv/bin/python HW03/hw3.py --q 3

不給 --sentence 就是預設句子，輸出是載入模型的進度條、Q3 的分隔線，接著 18 行 Token: …，格式和 3.3 節那段一樣。和投影片 p.17 的表逐行對照：前 9 行（到 ▁Professor）與後 6 行（從 ▁Lee 開始）應該和本書、和投影片一致（投影片有兩行例外，見 3.7 節）；中間那三行就是空格所在的位置，把你跑出來的 token 與 token index 對上去。注意投影片寫的「token」是 convert_ids_to_tokens 的字串，所以前面有空白的 token 要寫出 ▁（投影片用底線 _ 來表示它，3.7 節）。

想換一句話，加 --sentence，用雙引號把整句包起來（句子裡有空白，不包的話 shell 會把它拆成好幾個參數）：

.venv/bin/python HW03/hw3.py --q 3 --sentence "you and you"

應該印出三行：Token: you, token index: 4747、Token: ▁and, token index: 578、Token: ▁you, token index: 692（logs/review_ch03_q3.txt 第 20–25 行）。本章的中文句、"Google "、"In 2025, GPT-4o costs $2.50." 都是這樣跑出來的。句子裡有 $ 時要小心：在 bash 裡，雙引號內的 $2 會被當成「第 2 個位置參數」展開（互動 shell 裡通常是空字串），句子就變了；用單引號 '...' 包住，shell 就不會動它。本機錄製 logs/review_ch03_q3.txt 時是由腳本把 $ 跳脫後傳進去的，所以輸出有 ▁$、2，效果等同單引號。真的在 bash 裡用雙引號打，本機實測（logs/review_ch03.txt）句子會變成 In 2025, GPT-4o costs .50.，只剩 16 個 token，最後幾行是 ▁. 954、5、0、.，▁$ 與 2 都不見了，而且不會有任何錯誤訊息。自己跑的話請用單引號：

.venv/bin/python HW03/hw3.py --q 3 --sentence 'In 2025, GPT-4o costs $2.50.'

預期是 18 行 Token: …，其中 14 行應該和 3.5.2 節列出的相同，另外 4 行是 GPT-4o 的切法（那一節省略了，自己看）。本機照字面跑過這一行，18 行與 logs/review_ch03_q3.txt 第 36–53 行逐字相同（logs/review_ch03.txt）。

想看 3.3 節以後那些空白、大小寫、byte fallback 的對照，用 repo 附的事實腳本（同樣在 repo 根目錄；它也會載入模型，需要 GPU 與 HF 授權；結果印在終端機，不會寫進 logs/）：

.venv/bin/python docs/tools/hw03_facts.py pre_ch03

3.4 節 unsupervised、3.5.2 節 12345 這類切法來自同一支腳本的 tok 段（.venv/bin/python docs/tools/hw03_facts.py tok，輸出格式見 logs/facts_env_model_tok.txt 的 tokenizer 段，第 1 章用過）。pre_ch03 的輸出格式就是 logs/facts_pre_ch03.txt：先印預設句子的字元數與 token 數、幾個 id 的對照，再逐行列出每個測試字串切成的 (token, id) 與 roundtrip True（decode 能還原），最後是詞表統計與 byte fallback。注意它的 id 對照那幾行會直接印出空格的答案，想自己做題的話，先跑 hw3.py 再看它。

3.7　投影片的兩個錯字：讀 code 不盡信文件

讀 code 不盡信文件：S2 投影片 p.17 參考表的兩個錯字

（S2 是全書大綱的問題對照表裡第 2 條「投影片與程式不一致」的編號。）

p.17 的表除了四個空格，最後兩行和本機的輸出對不上：

投影片 p.17hw3.py 實測（logs/run_seed0.txt）差在哪
Token: you, token index: 692Token: ▁you, token index: 692id 對，token 少了 ▁。不帶 ▁ 的 you 是另一個 token，id 4747
Token: ?, token index: 23533Token: ?, token index: 235336token 對，id 少了最後一位 6。23533 是另一個 token：▁Operation

兩個都由本機查證過（logs/facts_pre_ch03.txt 第 7–10 行）：

  id 692: token '▁you', decode ' you'
  id 4747: token 'you', decode 'you'
  id 23533: token '▁Operation', decode ' Operation'
  id 235336: token '?', decode '?'

為什麼會錯：投影片其他行都用底線 _ 代替 ▁（例如 _love、_Machine），唯獨 you 這一行漏了；23533 則像是抄的時候少打一位數。兩者看起來都是手打或轉貼時的筆誤，不是程式的問題（推論）。另外要注意，投影片的 _ 是一般的底線（U+005F），不是 ▁（U+2581），兩者在程式裡是不同的字元；要拿字串去比對時，以程式印出的 ▁ 為準。

這對你的意義：投影片的表是「參考」，不是「標準」。填空時以自己跑出來的輸出為準；看到表上的值和輸出不同，先懷疑表。Gradescope 上這兩行沒有挖空，不影響作答，但如果你拿投影片的表去核對自己的程式，會在這兩行以為自己錯了。

3.8　常見錯誤

忘了 add_special_tokens=False

症狀
輸出第一行是 Token: <bos>, token index: 2，共 19 行。
後果
和投影片的表錯開一行，空格的位置跟著對錯。
正解
tokenizer.encode(sentence, add_special_tokens=False)，只看句子本身。

用 decode 取代 convert_ids_to_tokens

症狀
印出的 token 是 ' love'（前面一個空白）而不是 ▁love；或整串 id 一次 decode，得到原句。
後果
和投影片的格式對不上；整串 decode 更是看不到切在哪裡。
正解
convert_ids_to_tokens 一個 id 給一個詞表字串，保留 ▁；decode 是「還原成文字」，兩者用途不同。

把 ▁ 寫成底線

症狀
照投影片打 _love，拿去 tokenizer.convert_tokens_to_ids("_love") 查，得不到 ▁love 的 2182。
後果
convert_tokens_to_ids 是直接查詞表，不像 encode 會走 byte fallback；詞表裡沒有 _love 這個字串，所以回傳 <unk> 的 id 3；換成 ▁love 才是 2182（本機實測，logs/review_ch03.txt）。
正解
▁ 是 U+2581，不是 _。在程式裡用 "▁love"，或直接從 convert_ids_to_tokens 的輸出複製。

以為同一個字只有一個 id

症狀
查到 you 是 4747，就認定句子裡的 you 都是 4747。
後果
句中前面有空白的 you 其實是 ▁you 692；跟投影片那一行一樣的錯。
正解
token 取決於前面有沒有空白與大小寫；要知道某個位置的 id，就把整句切一次，不要單獨查一個字。

以為詞表裡沒有就變成 <unk>

症狀
預期罕見字元會變成 id 3。
後果
看到 <0xF0> 這種 token 以為是 bug；或高估資訊遺失。
正解
Gemma 用 byte fallback：拆成 UTF-8 位元組 token，decode 能完整還原。本機測過的字串都沒有出現 <unk>。

--sentence 沒有加引號

症狀
--sentence you and you，argparse 先印出 usage，再報錯 hw3.py: error: unrecognized arguments: and you，結束碼 2（本機實測，logs/review_ch03.txt）。
後果
shell 把句子拆成三個參數，--sentence 只拿到第一個字，多出來的 and、you 沒有旗標認領；argparse 在載入模型之前就報錯退出，什麼都不會跑。
正解
整句用引號包起來；句子裡有 $ 時用單引號（3.6 節）。

本章小結

  • Q3 的 TODO：tokenizer.encode(sentence, add_special_tokens=False) 得到 id，tokenizer.convert_ids_to_tokens(token_ids) 得到詞表字串；結果和 tokenize() 一樣，decode 能還原原句。關掉特殊 token 是為了不多一個 <bos>（19 → 18 個）。
  • ▁（U+2581）是 SentencePiece 表示空白的記號。Gemma 把空白併進下一個 token 的開頭；句首沒有 ▁；結尾空白、數字前的空白單獨成為 ▁；連續空白合成 ▁▁、▁▁▁。
  • 同一個字，空白與大小寫不同就是不同的 token：Machine 24911、machine 26504、▁machine 6479、▁Machine 13403；you 4747、▁you 692；第 2 章的 Orange 36565 與 ' Orange' 20723 也是如此。
  • 中文沒有 ▁，有的兩字一個 token（喜歡、老師、機器、學習），有的一字一個（李、宏、毅）；全形與半形標點是不同 token。數字一位一個 token。
  • 詞表裡沒有的字元拆成 UTF-8 位元組 token（byte fallback），本機沒看過 <unk>；位元組 token 只有 255 個，缺 <0x09>，id 226 是 \t。
  • S2：投影片 p.17 的 you 692 應是 ▁you，? 23533 應是 235336。空格的答案用 .venv/bin/python HW03/hw3.py --q 3 自己跑。

自我測驗

1. tokenizer.encode("I love you") 不加任何參數，會得到幾個 id？第一個是什麼？為什麼 Q3 不要它？

預設 add_special_tokens=True，會在最前面多一個 <bos>，id 2。所以是「句子本身的 token 數 + 1」，第一個是 2（本機用預設句子實測：18 → 19 個，開頭 [2, 235285]）。"I love you" 依本章的例子會切成 I、▁love、▁you 三個，加上 <bos> 共 4 個：本機實測是 ['<bos>', 'I', '▁love', '▁you']（logs/review_ch03.txt）。Q3 問的是句子被切成哪些 token，<bos> 不屬於句子，加了會讓每一行和投影片的表錯開。

2. "you and you" 裡兩個 you 的 id 為什麼不同？" you and you"（前面多一個空白）會怎樣？

第一個 you 在句首、前面沒有空白，是 you 4747；第二個前面有空白，空白併進它的開頭，是 ▁you 692。前面多一個空白時，第一個 you 前面也有空白了，依同樣的規則會是 ▁you，兩個 id 相同：本機實測 ' you and you' 切成 ▁you 692、▁and 578、▁you 692（logs/review_ch03.txt）。

3. convert_ids_to_tokens([692]) 和 decode([692]) 分別得到什麼？Q3 為什麼用前者？

前者是 ['▁you']，詞表裡的字串原樣；後者是 ' you'，▁ 換回了空白。Q3 要列出「切成了哪些 token」，用前者才看得到 ▁、也才和投影片的格式一致。

4. 一段文字裡有一個詞表裡沒有的字元，Gemma 的 tokenizer 會把它變成 <unk> 嗎？token 數會怎樣？

不會。它把那個字元的 UTF-8 編碼拆成位元組，每個位元組一個 <0x..> token（byte fallback），decode 可以完整還原。代價是一個字元可能佔 2 到 4 個 token（UTF-8 的長度），例如本機測的 U+20000 變成 4 個。

5. 投影片 p.17 最後一行寫 Token: ?, token index: 23533，你的程式印出 235336。該相信哪一個？怎麼確認？

相信程式。用 tokenizer.convert_ids_to_tokens([23533]) 查，得到的是 ▁Operation，不是 ?；而 235336 查回來是 ?。投影片少打了一位數（S2）。
