補充章　KV cache：生成時模型記住了什麼

語言模型一次只吐一個 token，每吐一個都要「回頭看」前面所有的 token。KV cache 讓它不必每一步都把前面重算一遍：把每一層算過的 key、value 存起來，下一步直接拿來用。這一章用本機實測把它拆開：存了什麼、存在哪、佔多少記憶體、省了多少時間，以及為什麼「同一個模型物件上留著的 cache」會讓 greedy 的答案改變。

本章重點

生成第 t 個 token 時，attention 需要「新 token 的 q」和「前面每個 token 的 k、v」。前面那些 k、v 不會因為後面多了字而改變，所以第一次算出來就存進 KV cache，之後每一步只算新 token。Gemma 2 用的是預先配置好固定長度的 HybridCache：Q1 的那一份是 26 層 × (1, 4, 544, 256) 的 key 與 value，共 0.054 GiB；沒寫到的格子靠 mask 拿到 0 的注意力。它在數學上不改變答案，但會改變 fp16 運算的順序，碰到兩個候選同分時就足以換掉 greedy 的選擇。

  • 為什麼有這一章：KV cache 在第 1 章（Q1 的 greedy 結果）、第 5 章（Q4 的 seed 為什麼不夠）、第 7 章（Q6 手寫生成迴圈）都是主角，第 0 章只用一句話帶過。這一章把它一次講清楚，後面各章回指這裡。
  • 本章對應的原始碼：hw3.py:73–85（generate_text_from_prompt，cache 藏在 generate 裡）、hw3.py:319–358（Q6 自己建 HybridCache）；transformers 4.47.0 的 cache_utils.py（HybridCache）、models/gemma2/modeling_gemma2.py（attention 怎麼用 cache）、generation/utils.py（generate 怎麼管理 cache）。
  • 本章的實測數字來自 docs/HW03/logs/ 底下的三個檔（下文寫成 logs/…）：facts_kvcache.txt（事實腳本 docs/tools/hw03_facts.py 的 kvcache 段，內文的「[1] 段」到「[7] 段」指這個檔裡以 [1]…[7] 開頭的段落）、facts_kvcache_overflow.txt，以及第 1 章審稿時量的 review_ch01_cache.txt。怎麼重跑見章末延伸閱讀。

K.1　生成一個 token 要做什麼

先回想 第 0 章 0.5 節那條路：token id 進 embedding，經過 26 層 decoder，最後的 RMSNorm、lm_head，得到每個位置對「下一個 token」的 256000 個分數（logits）。生成就是把這件事重複做：取最後一個位置的 logits 選出一個 token（greedy 就是選分數最高的），接到序列後面，再把變長了的序列送進模型，選下一個。這種「一次一個、每次都以前面全部為條件」的生成方式叫 autoregressive（自迴歸）。

每一層裡真正需要「看前面」的只有 attention（第 0 章 0.6.2 節）。對序列裡的某個位置 i，attention 做三件事：

  1. 用這個位置的 hidden state 算出 query（qi）；每個位置也各自算出 key（kj）與 value（vj）。
  2. 拿 qi 和位置 0…i 的每一個 kj 做內積，經過 soft-cap、mask、softmax，得到「位置 i 要分多少注意力給位置 j」的權重。因為是 causal（因果）attention，位置 i 只能看自己和前面，看不到後面。
  3. 用這組權重把 v0…vi 加權平均，作為這一層 attention 的輸出。

生成時，我們只在乎最後一個位置的 logits，因為它預測的是下一個 token。所以每一步真正新的計算只有：新 token 的 q，以及它對前面所有 k、v 的那一列 attention。問題是，前面所有 token 的 k、v 從哪裡來？

沒有 cache 的做法：每一步都把整段序列（prompt 加上目前為止生成的全部 token）重新送進模型，從第 0 層重算每個位置的 k、v。第 1 步算 T 個位置、第 2 步算 T+1 個、第 3 步算 T+2 個……前面那些位置每一步都重算一次，算出來的值跟上一步一模一樣（下一節證明）。

有 cache 的做法：第一步把 prompt 的 T 個位置一次算完，同時把每一層每個位置的 k、v 存起來；之後每一步只把一個新 token送進模型，它在每一層算出自己的 q、k、v，把自己的 k、v 寫進 cache，再拿 q 去和 cache 裡全部的 k、v 做 attention。這份存起來的 k、v 就是 KV cache。

本章的例子大多取自 Q1。Q1 把同一個問題用兩種 prompt 各送進模型一次：一次包成 Gemma 的對話格式（有 template，32 個 token），一次直接用純文字（沒有 template，23 個 token），兩次都用 greedy 生成，再用一個評分模型替回答打 coherence 分數。這些是第 1 章的主題，這裡只需要知道「Q1 有兩條路、長度不同、hw3.py 先跑有 template 的那條」。

用 Q1 有 template 那條路的實際規模算一次（logs/facts_kvcache.txt 的 [1] 段）：prompt 有 32 個 token，greedy 生成了 240 個新 token。有 cache 時，第一步送進 32 個，之後 239 步各送 1 個（最後一個生成的 token 不必再送進去），合計 32 + 239 = 271 個 token 通過模型；沒有 cache 時，第 i 步要送進 32 + i 個，加總 Σ(32+i)（i = 0…239）= 36,360 個，是 134 倍（計算值）。序列越長，這個倍數越大：生成 n 個 token，沒有 cache 的總量隨 n² 成長，有 cache 的隨 n 成長。

K.2　為什麼存的是 k、v，而不是 q 或 hidden state

能不能「存起來重用」，關鍵在於算出來之後還會不會變。

  • 前面位置的 k、v 不會變。位置 j 的 kj、vj 是從「位置 j 在這一層的輸入」算出來的，而這個輸入只取決於位置 0…j 的 token（causal attention：誰都看不到自己後面）。所以後面不管接上什麼字，kj、vj 都一樣，算一次就能一直用。
  • 前面位置的 q 用不到。q 只拿來算「這個位置要看誰」。生成時只需要最後一個位置的輸出，前面位置的 q 在它們自己那一步用完就沒用了。
  • 前面位置的 hidden state 也用不到。下一層需要的「前面的資訊」，全部經由 attention 的 k、v 傳進來。所以每一層只要存 k 與 v，其他中間結果都不必留。這就是它叫 KV cache 的原因。

「k、v 不會變」可以直接量。拿 Q7 的 prompt c（Time travel will become a reality as technology continues to advance.，含 <bos> 13 個 token）做兩次 prefill：一次整段 13 個，一次只送前 6 個。比較兩份 cache 在位置 0–5 的 key 與 value，26 層裡最大差異都是 0.0078（logs/facts_kvcache.txt 的 [5] 段）。數學上它們完全相同；那 0.0078 是 fp16 的捨入：GPU 算矩陣乘法時，會把矩陣切成許多小塊分頭計算，再把各塊的部分和加起來；矩陣的形狀不同（13 列 vs 6 列），切法和相加的順序就可能不同。浮點數加法不滿足結合律，(a + b) + c 和 a + (b + c) 的最後幾位可能不一樣，所以數學上相同的東西，算出來差了一點點。這個「數學相同、fp16 不同」的現象，K.8 節會再出現，而且會變得很重要。

存進 cache 的 k 是哪一個版本？看 transformers 4.47.0 的 Gemma2Attention.forward（models/gemma2/modeling_gemma2.py:374–394）：

        query_states = self.q_proj(hidden_states)
        key_states = self.k_proj(hidden_states)
        value_states = self.v_proj(hidden_states)

        query_states = query_states.view(bsz, q_len, self.num_heads, self.head_dim).transpose(1, 2)
        key_states = key_states.view(bsz, q_len, self.num_key_value_heads, self.head_dim).transpose(1, 2)
        value_states = value_states.view(bsz, q_len, self.num_key_value_heads, self.head_dim).transpose(1, 2)

        cos, sin = self.rotary_emb(value_states, position_ids)
        query_states, key_states = apply_rotary_pos_emb(query_states, key_states, cos, sin)

        if past_key_value is not None:
            # sin and cos are specific to RoPE models; cache_position needed for the static cache
            cache_kwargs = {
                "sin": sin,
                "cos": cos,
                "sliding_window": self.sliding_window,
                "cache_position": cache_position,
            }
            key_states, value_states = past_key_value.update(key_states, value_states, self.layer_idx, cache_kwargs)

順序是：投影出 q、k、v → 拆成 head（q 8 個、k 與 v 各 4 組，GQA）→ 對 q、k 做 RoPE（依位置旋轉）→ 才呼叫 past_key_value.update 把這一步的 k、v 寫進 cache，並拿回「cache 裡到目前為止的全部 k、v」。所以 cache 存的是已經轉過 RoPE 的 k：位置資訊已經烙在裡面，之後不必再知道它原本在第幾個位置。v 不做 RoPE，原樣存。（self.rotary_emb(value_states, position_ids) 傳 value_states 進去只是借用它的 dtype 與 device，不會旋轉 v；position_ids 是每個 token 的位置編號，生成時和下面的 cache_position 是同一串數字。）update 的回傳值取代了原本的 key_states、value_states，接下來的 attention 用的就是 cache 裡的全部內容，而不只是這一步新算的那一格。

K.3　cache 裡到底有什麼：形狀與記憶體

Q1 生成完之後，model._cache（generate 留在模型物件上的那一份，K.8 節講它為什麼會留下來）的樣子（logs/facts_kvcache.txt 的 [4] 段前四行；這一段後面還有三行，K.4 與 K.6 節再引用）：

[4] model._cache after generate: HybridCache, max_cache_len 544, layers 26, is_sliding[:4] [True, False, True, False]  «1»
  layer 0 (sliding): key (1, 4, 544, 256) value (1, 4, 544, 256) torch.float16; slots holding non-zero keys: 271; slots after them all zero: True  «2»
  layer 1 (global): key (1, 4, 544, 256) value (1, 4, 544, 256) torch.float16; slots holding non-zero keys: 271; slots after them all zero: True
  total 57,933,824 bytes = 0.0540 GiB; per slot 106,496 bytes  «3»
  1. 1類別是 HybridCache，26 層各一份。max_cache_len 544 = prompt 32 + max_new_tokens 512：cache 的長度是事先依上限配置的，不是生成到哪長到哪（K.4 節）。is_sliding 偶數層是 True，對應 第 0 章講的 sliding window 層與 global 層交替。
  2. 每一層的 key 與 value 都是 (1, 4, 544, 256)：batch 1、4 組 KV head（GQA）、544 格、每格 256 維，fp16。實際寫了東西的是前 271 格（32 + 239，和 K.1 節算的一致），後面 273 格全是 0。Q1 的 prompt 不到 4096 個 token，所以 sliding 層和 global 層的形狀一樣（K.6 節講它們什麼時候不一樣）。
  3. 總共 57,933,824 bytes，就是 第 0 章 0.10 節那個「Q1 跑完之後一直多出來」的 0.054 GiB。

每一格（一個 token 位置）佔多少，可以手算：

每格 = 26 層 × 2（k 與 v）× 4 組 KV head × 256 維 × 2 bytes（fp16）= 106,496 bytes ≈ 104 KiB

乘上 544 格就是 57,933,824 bytes，與實測完全一致。從這條式子可以讀出三件事：

  • GQA 省了一半。如果 k、v 也和 q 一樣有 8 個 head，每格是 212,992 bytes，整份 cache 加倍（計算值）。第 0 章 0.8 節算過 GQA 省下的參數，這裡是它省下的另一份東西：生成時的記憶體。
  • cache 隨長度線性成長，模型權重不會。4.87 GiB 的權重（第 0 章 0.10 節）是固定成本；cache 是每多一個 token 就多 104 KiB 的變動成本。這份作業每題的序列都很短，cache 最多 0.054 GiB；長對話、長文件時，它才是會撐爆記憶體的那一份。
  • cache 跟 batch 成正比。一次生成 8 句，每格就是 8 倍。這份作業都是 batch 1。

K.4　HybridCache：事先配置好的固定長度

KV cache 有兩種做法。直覺的做法是動態長大：每一步把新的 k、v 接在後面，tensor 長度一路加一。transformers 的 DynamicCache 就是這樣；本機實測對 Gemma 2 的 forward 傳 past_key_values=DynamicCache() 也能跑，prefill 32 個 token 後 layer 0 的 key 是 (1, 4, 32, 256)，剛好 32 格、不預留（[4] 段倒數第二行）。

Gemma 2 的 generate 用的是另一種：事先配置好一塊固定長度的空間，生成時只把新 k、v 寫進對應的格子。這是因為模型附的 generation_config（一份「generate 的預設參數」，跟著模型從 generation_config.json 讀進來，掛在 model.generation_config）寫了 'cache_implementation': 'hybrid'（全文在第 1 章 1.3.1 節）。看 transformers 4.47.0 cache_utils.py:1640–1662，HybridCache.__init__ 怎麼配置：

        self.key_cache: List[torch.Tensor] = []
        self.value_cache: List[torch.Tensor] = []
        global_cache_shape = (self.batch_size, self.num_key_value_heads, max_cache_len, self.head_dim)
        sliding_cache_shape = (
            self.batch_size,
            self.num_key_value_heads,
            min(config.sliding_window, max_cache_len),
            self.head_dim,
        )
        for i in range(config.num_hidden_layers):
            if layer_device_map is not None:
                layer_device = layer_device_map[i]
            else:
                layer_device = device
            # Note: `mark_static_address` is used to tag the cache as an fixed data pointer, preventing cuda graph
            # breaks when updating the cache.
            cache_shape = global_cache_shape if not self.is_sliding[i] else sliding_cache_shape
            new_layer_key_cache = torch.zeros(cache_shape, dtype=self.dtype, device=layer_device)
            new_layer_value_cache = torch.zeros(cache_shape, dtype=self.dtype, device=layer_device)
            torch._dynamo.mark_static_address(new_layer_key_cache)
            torch._dynamo.mark_static_address(new_layer_value_cache)
            self.key_cache.append(new_layer_key_cache)
            self.value_cache.append(new_layer_value_cache)

重點在最後那個迴圈：26 層，每層用 torch.zeros 一次配置好 key 與 value 兩塊。global 層的長度是 max_cache_len；sliding 層是 min(config.sliding_window, max_cache_len)，也就是最多 4096 格。之後生成時寫入一格的函式是 _static_update（cache_utils.py:1692–1698）：

    def _static_update(self, cache_position, layer_idx, key_states, value_states, k_out, v_out, max_cache_len):
        k_out[:, :, cache_position] = key_states
        v_out[:, :, cache_position] = value_states

        self.key_cache[layer_idx] = k_out
        self.value_cache[layer_idx] = v_out
        return k_out, v_out

就是一行「把新的 k、v 寫到第 cache_position 格」。cache_position 是這一步的 token 在整段序列裡的位置：prefill 時是 0…T−1，之後每一步加一。tensor 本身的大小從頭到尾不變。

為什麼要這麼麻煩？HybridCache 的 docstring（cache_utils.py:1562–1565）第一句就說它是「to be used with torch.compile」。torch.compile 是 PyTorch 2 的功能：先把模型的 Python 程式追蹤一遍，記下整串 GPU 運算（稱為一張「圖」），之後每一步直接重播這串運算，省掉 Python 逐行發號施令的開銷。重播的前提是每一步的形狀與記憶體位址都和錄製時一樣，所以 cache 必須事先配置好、之後不換位置（:1659–1660 的 mark_static_address 就是在標記這件事）。這份作業沒有用 torch.compile，所以這個好處我們拿不到，卻要承擔它的兩個副作用：

  1. 要事先知道長度。generate 用「prompt 長度 + max_new_tokens」當長度，所以 Q1 配了 544 格，但只用了 271 格。
  2. cache 比序列長，attention 就要對付空格子。下一節講。

不給 cache 時，模型自己會建一份

直接呼叫 model(input_ids, use_cache=True) 而不傳 past_key_values，Gemma 2 會在 forward 裡自己建一個長度剛好等於輸入長度的 HybridCache（modeling_gemma2.py:711–719）。本機實測 32 個 token 的輸入，回傳的 past_key_values 是 HybridCache，max_cache_len 是 32（[4] 段最後一行：forward(use_cache=True) without a cache argument returns HybridCache with max_cache_len 32 (= prompt length)）。第 0 章 0.7 節看到的「past_key_values 是 HybridCache」就是這一份。它沒有預留空間，所以沒辦法拿來接著生成下一個 token；要逐步生成，得像 Q6 那樣自己先建一份夠長的（K.5 節）。

K.5　沒寫到的格子怎麼辦：mask

cache 配了 544 格，第一步只寫了 32 格。attention 的權重矩陣寬度是多少？本機實測 prefill 時 output_attentions=True 拿到的是 26 個 (1, 8, 32, 544)：8 個 query head、32 列（每個 prompt 位置一列）、544 欄（cache 的每一格一欄）。decode 第一步是 (1, 8, 1, 544)（[6] 段）。也就是說，attention 一律對著整個 cache 的長度算，不是只對著已經寫入的那幾格。

那些全是 0 的格子如果參與 softmax，會分走注意力（0 向量的 k 和 q 內積是 0，exp(0) = 1，不是 0）。transformers 用 mask 把它們關掉。Gemma2Model._update_causal_mask 在 cache 是 HybridCache 時，把 mask 的寬度設成 cache 的長度（modeling_gemma2.py:812–813），再這樣填值（:866–872）：

            min_dtype = torch.finfo(dtype).min
            causal_mask = torch.full(
                (sequence_length, target_length), fill_value=min_dtype, dtype=dtype, device=device
            )
            if sequence_length != 1:
                causal_mask = torch.triu(causal_mask, diagonal=1)
            causal_mask *= torch.arange(target_length, device=device) > cache_position.reshape(-1, 1)

先做一張全部是 fp16 最小值（−65504）的矩陣；prefill 一次送進多個 token 時，torch.triu(..., diagonal=1) 先把對角線以下清成 0；接著乘上「欄位置 > 這一列的 cache_position」（True 是 1、False 是 0），只讓那些格子保留 −65504。結果是：每一列只能看到自己和前面已經寫入的格子，自己之後的、以及還沒寫入的，全部加上 −65504。在 eager attention（hw3.py 指定的 attention 實作，照公式一步步算，見第 0 章 0.4 節的「現在的做法」框）裡，這個 mask 在 soft-cap 之後加到分數上，再做 softmax（:183–194）：

    attn_weights = torch.matmul(query, key_states.transpose(2, 3)) * config.scaling

    if config.attn_logit_softcapping is not None:
        attn_weights = attn_weights / config.attn_logit_softcapping
        attn_weights = torch.tanh(attn_weights)
        attn_weights = attn_weights * config.attn_logit_softcapping
    if mask is not None:  # no matter the length, we just slice it
        causal_mask = mask[:, :, :, : key_states.shape[-2]]
        attn_weights = attn_weights + causal_mask

    # upcast attention to fp32
    attn_weights = nn.functional.softmax(attn_weights, dim=-1, dtype=torch.float32).to(query.dtype)

第一行的 config.scaling 是 1/16（第 0 章 0.6.2 節的「除以 16」）；soft-cap 把分數限制在 ±50 以內，加上 −65504 之後在 fp32 的 softmax 裡 exp 下去是精確的 0。本機實測（[6] 段）：

[6] prefill attentions: 26 x (1, 8, 32, 544); weight on slots >= 32 summed over all layers/heads/rows: 0.0; rows sum to 1: max |sum-1| 3.36e-04  «1»
    decode step 1: (1, 8, 1, 544); weight on slots >= 33: 0.0; min weight on slot 32 (the new token itself) over layers/heads 0.0000
    fp16 mask value finfo(float16).min = -65504.0  «2»
  1. 第 32 格以後的權重，26 層 × 8 個 head × 32 列全部加起來是 0.0：沒寫入的格子完全沒有分到注意力。每一列的權重加總與 1 的差最多 0.000336，那是 softmax 在 fp32 算完後轉回 fp16 的捨入（:194 的 .to(query.dtype)）。
  2. mask 用的值。它不是 −∞，而是 fp16 能表示的最小有限值，所以和 soft-cap 後的分數相加不會變成 NaN。

K.5.1　Q6 自己做這件事

Q1、Q2、Q4 都呼叫 model.generate，cache 藏在裡面看不到（K.8 節）。Q6 為了拿到每一步的 attention 權重，自己寫了生成迴圈，cache 的每個環節都攤在程式碼上：

對照本章講過的每一件事：

decode into slot 3: model(...) returned without an exception  «1»
/pytorch/aten/src/ATen/native/cuda/IndexKernel.cu:111: operator(): block: [0,0,0], thread: [32,0,0] Assertion `-sizes[i] <= index && index < sizes[i] && "index out of bounds"` failed.  «2»
...（同樣的 Assertion 一共 160 行，略）

  1. 1越界寫入的那次 model(...) 照常回傳，沒有丟出例外，腳本繼續往下走。
  2. 2PyTorch 在 GPU 上做索引的程式（IndexKernel.cu，GPU 端的 C++/CUDA 原始檔）檢查到索引超出範圍。這類在 GPU 上觸發的檢查叫 device-side assert；GPU 是成千上萬個執行緒同時跑，每個踩到的執行緒各印一行（注意每行的 thread: [...] 不同），所以有 160 行。
  3. 3Python 這邊要到腳本呼叫 torch.cuda.synchronize()（等 GPU 把排隊的工作做完）才收到錯誤。

GPU 上的運算是非同步的：Python 把工作排進佇列就往下走，越界是在 GPU 真正執行時才發現，Python 要等到下一個需要同步的地方才知道。需要同步的地方，是任何「要把 GPU 上的結果拿回 Python」的操作，例如 .item()、.cpu()、print 一個 GPU tensor 的值，或明確呼叫 torch.cuda.synchronize()。而且之後這個 process 的 CUDA 就不能再用了，只能重開。這是自己管 cache 時最容易踩的坑：錯誤出現的位置，不是犯錯的位置。想讓錯誤出現在犯錯的那一行，可以在 repo 根目錄這樣重跑，讓 GPU 改成同步執行：

CUDA_LAUNCH_BLOCKING=1 .venv/bin/python docs/tools/hw03_cache_overflow.py

本機的輸出（同一個 log 第二段）只有三種行：prefill 3 tokens into a 3-slot cache: ok、Assertion 行、最後的 AcceleratorError: CUDA error: device-side assert triggered。和上面的差別是沒有 decode into slot 3: model(...) returned without an exception 那一行：例外就在越界的那次 model(...) 丟出，不再延後。兩種跑法的結束碼都是 0，因為腳本自己接住了例外並印出來。

K.6　sliding 層與 global 層的 cache

第 0 章 0.6.2 節講過，Gemma 2 的偶數層是 sliding window attention：每個 token 最多只看前面 4096 個位置；奇數層是 global attention：看全部。sliding 層既然永遠用不到 4096 格以前的 k、v，就沒必要存。HybridCache 因此給兩種層不同的長度（K.4 節那段 __init__）。用 8192 格配置一份來看（[4] 段）：

  HybridCache(max_cache_len=8192): layer 0 (1, 4, 4096, 256), layer 1 (1, 4, 8192, 256); total 654,311,424 bytes = 0.609 GiB

layer 0（sliding）只有 4096 格，layer 1（global）是完整的 8192 格。如果 26 層都存 8192 格，會是 872,415,232 bytes = 0.8125 GiB（計算值），sliding 省下了四分之一。這就是類別名稱裡 hybrid 的意思：一半的層用固定長度的 static cache，另一半用最多 4096 格、寫滿之後循環覆蓋的 sliding window cache（_sliding_update，cache_utils.py:1664–1690）。

這份作業最長的序列是 Q1 的 544 格，遠小於 4096，所以兩種層的 cache 形狀一樣，循環覆蓋也從來沒有發生；本機沒有實測超過 4096 個 token 時的行為，這裡只依原始碼說明。

序列一長，情況就反過來。沒有 cache 的一步從 256 個 token 開始明顯變慢，到 4096 個 token 要 604 ms；有 cache 的一步從 512 到 4096 都在 23–24 ms，幾乎不變。強制生成 1024 個新 token（min_new_tokens=max_new_tokens=1024）：有 cache 26.3 s，沒有 cache 52.6 s，差了一倍（[3] 段最後兩行）；而且這個差距會隨長度繼續拉大。

記憶體呢？

生成 1024 個新 token 時，峰值 allocated（PyTorch 實際配置給 tensor 的 GPU 記憶體，torch.cuda.max_memory_allocated()，第 0 章 0.10 節用的也是它）有 cache 是 5.77 GiB、沒有 cache 是 5.75 GiB（[3] 段），幾乎一樣。有 cache 多存了 1056 格的 k、v（約 0.1 GiB，計算值），沒有 cache 則每一步都要暫時算出整段的中間結果，兩邊各有各的成本。cache 換的是時間，不是記憶體。

K.8　generate 怎麼管理 cache：留在模型物件上的那一份

hw3.py 的 Q1、Q2、Q4 都只寫一行 model.generate(...)，例如 Q1 的 TODO：

這裡看不到任何 cache，但 generate 裡面替你做了 K.4 節那些事：依 generation_config 的 cache_implementation='hybrid' 準備一個 HybridCache，長度是 prompt + max_new_tokens，prefill 一次，再逐步 decode。準備 cache 的是 GenerationMixin._get_cache（generation/utils.py:1589–1681），其中決定「要不要重建」的部分（:1603–1615）：

        if hasattr(self, "_cache"):
            cache_to_check = self._cache.self_attention_cache if requires_cross_attention_cache else self._cache

        if cache_implementation == "sliding_window":
            max_cache_len = min(self.config.sliding_window, max_cache_len)

        need_new_cache = (
            not hasattr(self, "_cache")
            or (not isinstance(cache_to_check, cache_cls))
            or cache_to_check.max_batch_size != batch_size
        )
        if cache_implementation != "mamba":
            need_new_cache = need_new_cache or cache_to_check.max_cache_len < max_cache_len

重建的條件是：模型上還沒有 _cache、類別不對、batch 大小不同，或者舊的那份太短（其他幾行處理 cross attention、sliding_window、mamba 這些別的架構或 cache 種類，Gemma 2 的 generate 都走不到）。GenerationMixin 是 transformers 提供 generate 的那個類別，model.generate 就是從它繼承來的。反過來說，只要模型物件上已經有一份夠長的，就不重建，只在 :1680 呼叫 self._cache.reset() 把內容清成 0（cache_utils.py:1740–1745），沿用同一塊記憶體。這是為了省掉每次重新配置的成本，也是 torch.compile 需要的「位址固定」。

後果是：上一次 generate 用多長的 cache，會影響這一次用多長的 cache。hw3.py 一個 process 裡七題共用同一個 model 物件（第 0 章 0.2.2 節），具體的鏈條是：

  1. Q1 先跑有 template 的那條路：prompt 32 個 token，max_new_tokens 512，需要 32 + 512 = 544 格。模型上還沒有 cache，所以新配一份 544 格。
  2. 接著跑沒有 template 的那條路：prompt 23 個 token，需要 23 + 512 = 535 格。舊的 544 格夠長，所以沿用 544 格。如果單獨跑這條路（或先把 model._cache 清掉），它會自己配 535 格。
  3. 之後的題目也一樣：Q4 的 prompt 32 個 token、每句最多 30 個新 token，自己只需要 62 格，但在 hw3.py 裡也是沿用 Q1 留下的 544 格。

K.8.1　cache 長度為什麼會改變答案

這裡要分清楚兩種比較：一種是都有用 cache、但 cache 的長度不同（535 格 vs 544 格），另一種是有用 cache vs 完全不用 cache。兩種在數學上都該得到同樣的答案，實際上都可能不同，原因相同：fp16 的運算順序。先看第一種。K.5 節證明了沒寫入的格子分到的注意力精確是 0。照理說，cache 是 535 格還是 544 格，答案應該一模一樣。數學上確實一樣，但 GPU 上的 fp16 運算不只看數學：矩陣的形狀不同，乘加的分塊與順序就可能不同，最後幾位跟著不同（K.2 節那個 0.0078 就是一例）。實測 Q1 沒有 template 那條路，同一個 prompt 分別用 535 格與 544 格的 cache decode（[7] 段，比較的是 decode 第 3 步）：差異最早出現在第 7 層的 attention，已寫入格子上的權重差 0.00037、attention 輸出差 0.0020。為什麼是第 7 層、為什麼多出幾個被遮掉的格子會讓 softmax 的結果改變，本機沒有追；合理的推論是加總的運算順序不同。

這麼小的差異，平常不會改變哪個 token 分數最高。但 greedy 每一步都只看第一名，只要某一步前兩名剛好幾乎同分，0.0156 的差距就足以換掉答案，而之後的每一步都接在不同的字後面，整段回答就分岔了。0.0156 是 fp16 在 16 到 32 之間能表示的最小間隔：fp16 的有效位數只有 11 個二進位位，數值越大、相鄰兩個可表示的數就隔得越遠，在 [16, 32) 這一段是 2−6 = 0.015625，logits 落在 17–19 時，差一格就是這麼多。兩個候選完全同分時，argmax 回傳 id 較小、也就是排在前面的那一個。本書量到的分岔：

讀 code 不盡信文件：「greedy 可以完全重現」的前提

原版 Colab 的註解說用 do_sample=False 就能得到 deterministic（確定）的回答。在同一台機器上，這句話成立的前提比字面多兩條：呼叫順序相同，以及模型物件上留著的 cache 相同。hw3.py 照原版的順序跑，所以本書記錄的數字照作業流程重跑會一樣；單獨跑某一條路、換了順序、或在同一個 notebook 裡多跑過一次別的 generate，都可能得到不同的答案。要排除這個因素，在每次 generate 之前把 model._cache = None（本書的事實腳本就是這樣做的），讓它每次都配置自己的長度。

K.9　常見錯誤

以為 KV cache 存的是 hidden state 或 q

症狀
自己寫生成迴圈時，想把每一層的輸出或 q 也存起來重用。
後果
白費記憶體，而且接不起來：下一層需要的前文資訊只經由 attention 的 k、v 進來。
正解
每層只存 k、v（K.2 節）；q 只用當下這一步的。存的 k 是轉過 RoPE 的版本。

以為 use_cache=False 比較「準」

症狀
看到有 cache 和沒有 cache 的回答不同，以為 cache 是近似、關掉才是正確答案。
後果
花一倍以上的時間（1024 個 token：52.6 s vs 26.3 s），得到的只是另一條 fp16 路徑的結果。
正解
兩者數學上相等，差異來自運算順序（K.8.1 節）。另外 transformers 4.47 對 Gemma 2 用 use_cache=False 時，會印出一段 --- Logging error --- 的 traceback（transformers 自己格式化警告失敗），程式照常繼續，不用理它。

同一個模型物件上連續做實驗

症狀
在 notebook 裡先跑 A、再跑 B，和只跑 B 的結果不同；重開 kernel 又恢復。
後果
以為程式有隨機性、或以為改了某個參數才造成差異。
正解
generate 沿用 model._cache（K.8 節）。要比較就固定順序，或每次 generate 前 model._cache = None。

手動建 cache 少配一格

症狀
自己寫的生成迴圈在某一步之後，下一個不相干的運算才報 CUDA error: device-side assert triggered。
後果
錯誤出現的位置不是犯錯的位置；而且整個 process 的 CUDA 都壞了，只能重開。
正解
長度照 Q6 的算法：prompt 長度 + 要生成的數量 − 1（hw3.py:320）。除錯時設環境變數 CUDA_LAUNCH_BLOCKING=1 讓 GPU 同步執行，例外就會在寫入越界的那次 model(...) 丟出（K.5.1 節）。

以為 attention 權重的寬度就是序列長度

症狀
拿到 (1, 8, 32, 544) 的 attention，以為序列有 544 個 token。
後果
畫 heatmap 時把一大片 0 也畫進去，或用錯的長度去切。
正解
寬度是 cache 的長度（K.5 節）。有效的欄只有前 cache_position + 1 欄。

本章小結

  • 生成是 autoregressive 的：每一步只需要新 token 的 q，以及前面每個 token 的 k、v。前面的 k、v 不會因為後面多了字而改變（causal attention），所以算一次就存進 KV cache；Q1 因此只送 271 個 token 進模型，而不是 36,360 個。
  • cache 每層存轉過 RoPE 的 k 與原樣的 v。Gemma-2-2b-it 每格 106,496 bytes（26 層 × 2 × 4 組 × 256 維 × 2 bytes）；GQA 讓它少了一半。Q1 的 544 格是 0.054 GiB。
  • Gemma 2 的 generate 用 HybridCache：事先用 torch.zeros 配置 prompt + max_new_tokens 格，sliding 層最多 4096 格；每一步把新 k、v 寫進第 cache_position 格。
  • attention 對著整個 cache 的長度算（權重是 (1, 8, 32, 544)），沒寫入的格子在 soft-cap 之後加上 −65504，softmax 後精確是 0。
  • 短序列時一次 forward 約 22 ms，大多是固定開銷，有沒有 cache 差不多（Q1：5.69 s vs 6.10 s）；長序列時差距明顯（1024 個 token：26.3 s vs 52.6 s；4096 長度的一步：24.2 ms vs 604.3 ms）。
  • generate 把 cache 留在 model._cache，夠長就沿用。cache 長度不同時數學上答案相同，但 fp16 的運算順序不同，碰到前兩名幾乎同分就會換掉 greedy 的答案。這是第 1 章 Q1、第 5 章 Q4 的數字會隨執行順序改變的原因。

自我測驗

1. 生成第 t 個新 token 時，attention 需要哪些東西？為什麼前面位置的 k、v 可以存起來重用，q 卻不必存？

需要新 token 這一步的 q，以及位置 0 到目前為止每個 token 的 k、v。causal attention 讓每個位置只看得到自己和前面，所以位置 j 的 k、v 只取決於位置 0…j 的 token，後面接什麼字都不會改變它們，算一次就能一直用（本機實測前綴的 k、v 在不同長度的輸入下只差 fp16 捨入的 0.0078）。前面位置的 q 只在它們自己那一步用來決定「看誰」，之後生成只需要最後一個位置的輸出，所以不必存。

2. 一份 max_cache_len 2048 的 HybridCache，在 Gemma-2-2b-it 上佔多少 bytes？如果 Gemma 2 沒有用 GQA（k、v 也有 8 個 head）呢？

2048 < 4096，所以 sliding 層與 global 層都是 2048 格，每格 106,496 bytes：2048 × 106,496 = 218,103,808 bytes，約 0.203 GiB。沒有 GQA 時每格 212,992 bytes，加倍成 436,207,616 bytes，約 0.406 GiB。（都是計算值。）

3. Q6 的 cache 是 22 格。第一步的 attention 為什麼是 (1, 8, 3, 22)？第 5 步呢？22 是怎麼算出來的？

第一步送進 3 個 token（<bos>、Google、▁），所以 3 列；8 是 query head 數；22 是 cache 的長度，attention 一律對著整個 cache 算，沒寫入的欄靠 mask 拿到 0。之後每一步只送 1 個 token，所以第 5 步是 (1, 8, 1, 22)。22 = 20 + 3 − 1：prompt 的 3 格，加上之後 19 步各寫一格（第 20 個選出來的 token 不必再送進模型）。

4. 本機實測 Q1 用 cache 只比不用快 7%，生成 1024 個 token 時卻快一倍。為什麼？

一次 forward 有大約 22 ms 的固定開銷（26 層、每層多個 kernel 的發送），序列在 128 個 token 以內時，多算幾倍的 token 幾乎不花額外時間。Q1 的序列最長只到 271 個 token：前段的步驟有沒有 cache 一樣快，只有後段沒有 cache 的一步慢了四到五成，所以合計只差 7%。序列一長，沒有 cache 的一步要重算整段（4096 個 token 要 604 ms），有 cache 的一步仍然只算一個 token（24 ms），差距就顯現出來。（「固定開銷」是推論，本機沒有用 profiler 拆過。）

5. 同學說：「沒寫入的 cache 格子被 mask 成 0，所以 cache 配 535 格還是 544 格，greedy 的答案一定一樣。」哪裡錯了？

沒寫入的格子分到的注意力確實精確是 0，所以數學上答案一樣。但 fp16 運算的結果還取決於矩陣的形狀與運算順序：本機實測 535 格與 544 格在第 7 層的 attention 權重就差了 0.00037。差異雖小，Q1 沒有 template 那條路第 30 步的前兩名剛好同分（17.875），544 格時 ▁outputs 多了一格精度，greedy 的選擇就換了，Q1 評分模型給的 coherence 分數從 4.2210 變成 5.0104。
