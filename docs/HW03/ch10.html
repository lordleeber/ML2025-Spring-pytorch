  • 本章不引用新的原始碼行號；提到的行號都在前面各章逐字引用過。

10.3　重現性：什麼會讓結果不同

10.3.1　同一台機器、同一條指令：逐行相同

寫這一章之前，本機用同一個環境把 .venv/bin/python HW03/hw3.py --seed 0 重跑一次，和最早的 logs/run_seed0.txt 比對（兩邊都先去掉 tqdm 與載入的進度列、警告、空行、本機絕對路徑）。結果（logs/rerun_seed0_check.txt）：

  • 原 log 201 行、重跑 203 行；差別只有重跑多出的 2 行 tqdm 進度列（top-k、top-p），七題的輸出逐行相同：Q1 的回答與 coherence、Q2 的 top-10、Q4 的 40 句與 self-BLEU 0.2020／0.5542、Q5、Q6、Q7 的數字都一樣。
  • HW03/outputs/ 重新產生的 9 張圖，和 docs/HW03/img/ 的對應檔 md5 全部相同。
  • 整條指令 real 44.3 s（原 log 45.7 s）。

所以全書引用的 hw3.py 輸出，在同一台機器、同一套版本、同一條指令下可以逐字重現。你在自己的機器上跑，數字不一定和本書相同；下面是全書找到的「會讓結果改變」的原因。

10.4.2　進階：改一兩行程式

進階 1　Q1 改成單 <bos>，再比 coherence

做什麼：讓有 template 的那條路只有一個 <bos>。注意 hw3.py:77 的 tokenizer(prompt, ...) 是兩條路共用的：沒有 template 的純文字本身沒有 <bos>，靠 tokenizer 加的那一個，所以不能兩條路一起加 add_special_tokens=False。一個做法（本書的示意，沒有照字面跑過）是只在字串已經以 <bos> 開頭時不加：

input_ids = tokenizer(prompt, return_tensors="pt", add_special_tokens=not prompt.startswith(tokenizer.bos_token)).input_ids.to(DEVICE)

關鍵：結果取決於 KV cache。hw3.py 先跑有 template（配 544 格），沒有 template 那次沿用 544 格。要公平比較，在 :80 的 model.generate 前面加一行 model._cache = None，讓每次都自己配置。

參考（FACTS「ch01 審稿補測」的 cache 表，logs/review_ch01_cache.txt；這是事實腳本的數字，不是改過的 hw3.py 的輸出）：

路徑自己配置 cache沿用 544 格（hw3.py 的順序）
有 template、雙 <bos>（hw3.py）544 格：6.07346.0734
有 template、單 <bos>543 格：6.39926.1188
沒有 template535 格：4.22105.0104

所以「單 <bos> 比雙 <bos> 高多少」，答案是 0.05 還是 0.33，取決於 cache 怎麼配；連沒有 template 那一欄都會跟著變。這一題真正要學的是：比較兩種寫法時，先把其他會變的東西固定住（第 1 章 1.7 節、補充章 K.8.1 節）。

進階 2　Q2 改成單 <bos>

做什麼：Q2 的 prompt 一律來自 chat template，可以直接把 hw3.py:139 改成 tokenizer(chat_template_format_prompt, return_tensors="pt", add_special_tokens=False)，並在 :162 的 model.generate 前加 model._cache = None。三輪的 prompt 變成 26、58、81 個 token。

參考（FACTS「ch02 審稿補測」，logs/review_ch02.txt；事實腳本每輪從新的 cache 開始）：三輪的回答從 Indigo、Orange、Green 變成 Red、Orange、Yellow。第 1 輪的前幾名是 Red 0.2591、Green 0.2434、Indigo 0.2182；第 3 輪 Yellow 0.8378、Green 0.1479。同一個程序裡的雙 <bos> 對照組，三輪和 hw3.py 的 log 逐字相同（第 2 章 2.8 節）。一個 token 的差別，就讓第 1 輪換了顏色，後面兩輪的 prompt 跟著全部不同。

進階 3　Q5 改成排除 pad 的平均

做什麼：把 hw3.py:275 換成第 6 章 6.6 節的兩行：

mask = inputs.attention_mask.unsqueeze(-1).to(hidden_states.dtype)   # (6, 9, 1)

參考（FACTS「ch06 審稿補測」，logs/review_ch06.txt，這兩行本機照字面跑過）：fp16 裡加總沒有溢位（最大 407.0）；餘弦相似度 Apple(f)–Orange(f) 0.924、Apple(c)–MS 0.915、Orange(t)–MS 0.869、Apple(f)–Apple(c) 0.728（含 pad 時依序是 0.902、0.924、0.868、0.757）；t-SNE 的座標整個不同，但最近鄰關係和 hw3.py 相同。

挑戰 2　Q4 的 top-p 加 top_k=0（R2）

做什麼：先用沒改的 hw3.py 跑下面兩條當基準，再把 :231 的 top_p=top_p 後面加 top_k=0，兩條各再跑一次，比較前後的句子與分數。

.venv/bin/python HW03/hw3.py --q 4 --seed 0 --top-k 200 --top-p 0.999

參考（FACTS「ch04 審稿補測」與「Q4 實測」）：

  • 照 hw3.py 的順序（先 20 句 top-k、再 20 句 top-p，同一個亂數流），上面兩條指令（p=0.6 與 p=0.999），加了 top_k=0 之後 top-k 組與 top-p 組都 20/20 句相同；但每步的候選最多從 50 個變成 5,766 個，top_k=0 確實生效了。
  • 事實腳本每個設定各自從 seed 起算時，p=0.999 加不加 top_k=0 就會不同：seed 0 是 0.1257 vs 0.1343、seed 3 是 0.1371 vs 0.1329；p=0.6 則 5 個 seed 都完全相同。

要解釋的：為什麼同樣加了 top_k=0，一種跑法完全沒差、另一種有差？參考解讀（第 4 章 4.9 節的說法）：被 top_k=50 擋掉的那些 token 機率加起來很小，torch.multinomial 只有在亂數剛好落在那一小段時才會抽到不同的 token；hw3.py 那條亂數流剛好一次都沒落進去，換一個起點就落進去了。p=0.6 時 60% 的機率質量本來就落在前 50 個 token 之內（FACTS R2 的說法），top-p 留下的候選不受 top_k=50 影響，所以每個 seed 都相同。

10.5　從這份作業學到的 transformer

  • 對話模型吃的是格式：同一個問題，套不套 chat template，回答的形狀與分數都不同；<bos> 多一個，Q2 的顏色就換了（第 1、2 章）。
  • 模型看到的是 token，不是字：▁ 記號、同一個字有不同 id、數字一位一個、詞表外的字元拆成位元組（第 3 章）。
  • 生成是一次一個 token：logits → softmax → greedy 或取樣，再接回去；top-k、top-p 是在取樣前把候選砍掉，預設值會悄悄生效（第 2 章、第 4 章）。
  • 評估指標本身也要讀：self-BLEU 量的是 20 句彼此多像，單次的數字會隨 seed 大幅波動（第 5 章）。
  • hidden state 是一條一路加上去的 residual stream：範數從約 80 長到約 740，最後的 norm 再壓回約 100；hidden_states 有 27 個，索引比 block 編號大 1（第 0 章 0.9 節）。
  • 句子的表示反映語境：Apple 的兩個意思（0.757）不如 Apple 公司與 Microsoft（0.924）接近；怎麼把一串向量變成一個（含不含 pad）會改變數字（第 6 章）。
  • attention 是每列加總為 1 的權重：因果遮罩讓右上角是 0；有的 head 看前一個 token，大部分 head 有一半以上的注意力流向 <bos>（attention sink）（第 7 章）。
  • KV cache 讓逐步生成變便宜，也帶來邊界：sliding 與 global 兩種層用不同的 cache，cache 的長度會改變 fp16 的結果，剛好配滿會碰到捲動（補充章 KV cache、第 7 章 7.7 節）。
  • SAE 把 hidden state 拆成稀疏的 feature，但量尺只在一層校正過：JumpReLU 的門檻、在訓練的那一層 FVU 最低、拿去別層就失準（第 8、9 章）。
  • 同一個骨架，兩份權重：pt 與 it 的 config 幾乎一樣，權重矩陣只改了約 7.6%，行為卻差很多（Gemma 補充章 G.6 節）。
  • 讀 code 不盡信文件：投影片、註解、圖的標籤、旗標的名字都可能和程式實際做的不一樣；16 條裡沒有一條會讓程式當掉，全都要靠印出中間值才看得到（10.2 節）。

自我測驗

1. Q5、Q7.2 與 Q7.4 各自用的是哪一個 hidden_states 索引？分別是哪個 block 的輸出？

Q5 用 hidden_states[-1]，也就是 [26]：block 25 的輸出再經過最後的 norm。Q7.2–7.3 用 [20]：block 19 的輸出（R5；SAE 要的是 [21]，block 20 的輸出）。Q7.4–7.6 預設 [24]：block 23 的輸出（S4）。

2. Q1 單 <bos> 的 coherence，FACTS 裡有 6.1188 與 6.3992 兩個數字。哪個才對？

兩個都對，條件不同。6.1188 是沿用前一次 generate 留下的 544 格 KV cache；6.3992 是自己配置 543 格。這正是 10.3 節「沿用的 cache 長度會改變結果」的例子；比較時要先把 model._cache 設成 None，讓每次的條件相同。

3. 同一個 --seed 0，hw3.py --seed 0 與 hw3.py --q 4 --seed 0 的 top-k self-BLEU 是 0.2020 與 0.2029。原因是亂數被 Q1 用掉了嗎？

不是。本機實測 Q1 前後的亂數狀態完全沒變；差別來自 Q1 的 generate 把 544 格的 HybridCache 留在 model._cache，Q4 沿用它，運算的形狀不同，fp16 的數值有極小差異，剛好讓第 13 句的某一步抽到不同的 token（R10，第 5 章 5.6 節）。

4. 修好 R5（Q7.2 改用 [21]）之後，prompt b 的最大值會變成 0 嗎？

不會。只修 R5 時 prompt b 是 30.95，仍然來自 <bos>；要再排除第 0 個位置（R6）才會變成 0.0。兩個問題是獨立的（挑戰 1）。

5. 「hw3.py 已經把這 16 條都修好了」這句話對嗎？

不對。hw3.py 的 docstring 寫明，除了必要的移植（HF token、存圖、Q2 的預設對話、旗標）之外，原版的寫法包括這些怪地方都保留，好讓結果對得上助教的參考答案。本書的修法都是示意，要自己改（10.4 節）。
