5.2　BLEU 在量什麼

BLEU 原本是機器翻譯的評分方法：拿模型翻出來的句子（hypothesis，待評的句子）去和人翻的句子（reference，參考答案）比，看兩者有多少連續的字串相同。self-BLEU 借用它來量「一組生成的句子彼此有多像」。先看一對句子的 BLEU 怎麼算。

hw3.py:195 的 sentence_bleu([ref.split()], hypothesis.split()) 先把兩句都用 split() 依空白切成詞的 list（reference 外面多包一層 list 的原因見 5.3 節），再計算：

  1. n-gram 精確度 pn，n = 1, 2, 3, 4。n-gram 是連續 n 個詞的片段。pn = 「hypothesis 的 n-gram 裡，有出現在 reference 裡的個數」÷「hypothesis 的 n-gram 總數」。同一個 n-gram 在 hypothesis 出現的次數若比 reference 多，多出來的不算（這叫「修正」精確度，防止一直重複同一個字騙分數）。
  2. 幾何平均：四個 pn 取 log、等權（各 1/4）平均、再取 exp。也就是 (p1 × p2 × p3 × p4)1/4。
  3. brevity penalty（BP，簡短懲罰）：hypothesis 比 reference 短時，精確度很容易灌高（說得越少越不會錯），所以乘上一個懲罰。hypothesis 長度 c、reference 長度 r：c < r 時 BP = exp(1 − r/c)，否則 BP = 1。
  4. BLEU = BP × 幾何平均，介於 0 與 1 之間。
BLEU = BP × (p1 · p2 · p3 · p4)1/4，　BP = exp(1 − r/c)（c < r 時），否則 1

這是 BLEU 的標準定義（Papineni et al. 2002，見延伸閱讀）。nltk 的 sentence_bleu 不給 weights 時就是 4 階等權，hw3.py 沒有給。對應的 nltk 3.10.3 原始碼（.venv/lib/python3.12/site-packages/nltk/translate/bleu_score.py，本機查的行號）：sentence_bleu 定義在 :45，預設 weights=(0.25, 0.25, 0.25, 0.25) 在 :48，它只是把一句包成一個 corpus 交給 corpus_bleu（:132）；modified_precision 在 :285，分子是每個 n-gram 的次數不超過它在 reference 裡出現的次數（clip，:384–388），分母是 hypothesis 的 n-gram 總數（:391）；brevity_penalty 在 :416，hypothesis 比 reference 長就是 1（:499），否則 exp(1 - r/c)（:505）；最後 :279–280 把各階取 log、乘權重、加總、取 exp，再乘上 BP。

  lengths 12/14; p1..p4 10/12, 8/11, 6/10, 4/9; BP 0.8465; BLEU 0.5367

  • p1 = 10/12：第 0 句的 12 個詞裡，top 不在第 2 句、education.（帶句號）也不在，其餘 10 個都在。

  • BP：c = 12 < r = 14，exp(1 − 14/12) = exp(−0.1667) ≈ 0.8465。
  • BLEU ≈ 0.8465 × 0.634 ≈ 0.5367，和工具算出來的一致。

5.2.2　「BLEU 等於 0」其實是極小值

幾何平均是連乘：只要四個 pn 裡有一個是 0，整個乘積就是 0。兩句話沒有任何共同的 4 個連續詞，這在短句之間很常見。這時 nltk 會發出警告，hw3.py --q 4 --seed 0 的 stderr 印出了三則（logs/run_q4_seed0.txt 第 54–71 行；本機路徑改成相對路徑；三則格式相同，這裡只貼第一則）：

.venv/lib/python3.12/site-packages/nltk/translate/bleu_score.py:577: UserWarning:
The hypothesis contains 0 counts of 4-gram overlaps.
Therefore the BLEU score evaluates to 0, independently of
how many N-gram overlaps of lower order it contains.
Consider using lower n-gram order or use SmoothingFunction()
  warnings.warn(_msg)

另外兩則是 3-gram 與 2-gram 的版本。警告說「BLEU evaluates to 0」，第 0 章 0.1 節也說「那一對的 BLEU 記為 0」。但本機實際拿一對 4-gram 完全沒有重疊的句子去算（logs/facts_pre_ch05_selfbleu.txt 第 49–51 行，逐字）：

hyp: He is highly regarded as a top expert in machine learning education.
ref: Professor Lee is a renowned machine learning educator.
sentence_bleu = 6.223629500679345e-155 ; sys.float_info.min = 2.2250738585072014e-308

回傳的是 6.22 × 10−155，不是 0。沒有指定平滑時，nltk 用 SmoothingFunction().method0（bleu_score.py:261–262）：某一階的分子是 0，就發出那則警告，並把這一階的精確度換成 sys.float_info.min（:583），也就是 Python 一般浮點數能表示的最小正數，約 2.2 × 10−308，好讓後面的 log 不會變成 log(0)。這一對的精確度是 4/12、1/11、0/10、0/9，BP = 1（hypothesis 12 個詞，比 reference 的 8 個長），所以 BLEU = (4/12 × 1/11 × 2.2×10−308 × 2.2×10−308)1/4，正好是 6.22 × 10−155：兩個最小正數各開四次方根，乘起來約 10−154（本機重算，logs/review_ch05.txt）。真的回傳 0 只有一種情況：連 1-gram 都沒有任何重疊（:257–258）。對 self-BLEU 的平均來說，10−155 和 0 沒有差別，所以「等同 0」的說法在數值上成立；只是嚴格說它不是 0。hw03_selfbleu.py 用「小於 10−10」來判斷一對「實際為 0」。

那 log 裡只有三則警告，是不是只有三對？不是。hw03_selfbleu.py 把警告設成每次都記錄，（在 warnings.catch_warnings(record=True) 裡呼叫 warnings.simplefilter("always")，見 docs/tools/hw03_selfbleu.py 第 65–66 行），數出 run_q4_seed0 的 top-k 組實際觸發了 4-gram 146 次、3-gram 36 次、2-gram 2 次（第 5 行）。log 只印各一次，是因為 Python 的 warnings 預設同一個程式位置、同一則訊息只顯示一次，後面的都被默默略過。top-p 組（p=0.6）一次都沒觸發，原因下一節會看到。

警告最後建議「use SmoothingFunction()」：nltk 提供幾種平滑方法，讓沒有重疊的那一階不會把整個分數壓到接近 0。method1（bleu_score.py:586–597）把分子為 0 的那一階換成 (0 + epsilon) / 分母，epsilon 預設 0.1（:517），其他階不動。hw3.py 與原版都沒有用。本機用 SmoothingFunction().method1 重算同樣的句子（logs/facts_pre_ch05_selfbleu.txt）：

log、組hw3.py 的 self-BLEU加 method1實際為 0 的對數（共 380）
run_q4_seed0 k=20.20290.2270146
run_q4_seed0 p=0.60.55420.55420
run_q4_k200_p0999_seed0 k=2000.13430.1616184
run_q4_k200_p0999_seed0 p=0.9990.06250.0972290
run_seed0 k=20.20200.2265150

平滑只會改變「有某一階完全沒重疊」的那些對，所以 p=0.6（一對都沒有）完全不變；其他組都往上調，但排序不變（k=2 > k=200、p=0.6 > p=0.999）。p=0.999 有 290 對、超過四分之三實際為 0，它的低分有很大一部分來自「大部分句對被算成 0」。換一種平滑方法，數字就不同，所以 self-BLEU 的絕對值只在同一種算法之內比較才有意義。

5.3　self-BLEU：每一句拿其他 19 句當參考答案

逐行：

  • :194：第 i 句當 hypothesis，其他所有句子（j != i）當 references。
  • :195：對每一個 reference 各自算一次 BLEU。注意 [ref.split()] 外面那層 list：sentence_bleu 的第一個參數是「多個參考答案」的 list，這裡每次只放一個。（BLEU 本來可以一次給多個 reference，取最好的匹配；hw3.py 沒有這樣用，而是一對一對分開算。）
  • :196：這 19 個 BLEU 取平均，加進總分。
  • :197：再對 20 句平均。

所以 20 句的 self-BLEU 一共算了 20 × 19 = 380 個有序句對的 BLEU。因為 BLEU 不對稱，(i, j) 與 (j, i) 兩格都要各算一次。

讀這個數字的方向：

  • 越高代表 20 句越像，也就是多樣性越低。兩句完全相同時那一格是 1（上一節自己對自己的那一列）；所有句子完全相同，self-BLEU 就是 1.0000。本機 k=1、p=0 用 --num-samples 2 抽的 2 句完全相同，分數就是 1.0000（5.4 節的表、第 4 章 4.7.2 節）。
  • 越低代表句子彼此越不像。這是「多樣」，但不保證是「好的多樣」：第 4 章看過 k=200、p=0.999 會寫出偏離指令、被截斷的句子，它們和其他句子當然不像，也會把 self-BLEU 拉低。
  • 它不是品質分數。self-BLEU 完全不看句子通不通順、有沒有照指令改寫，只看彼此重疊多少。投影片要你「Observe fluency, coherence, and diversity」，self-BLEU 只量得到最後一項。

p=0.6 那組只有 8 種句子，其中 Professor Lee is highly regarded as a leading expert in machine learning education. 出現 10 次（第 4 章 4.6 節數過）。這 10 句兩兩之間的有序句對是 10 × 9 = 90 個，每個都是 1；其他重複的句子再貢獻 8 對，合計 98 對 BLEU = 1（計算值，98 這個總數是工具量的）。380 格裡有 98 格是 1、沒有一格是 0，平均自然高。k=2 的 20 句都不一樣，而且有 146 格實際為 0，平均就低。這就是第 4 章用「幾種不同的句子」看到的同一件事，換成一個數字。

5.5　單次的數字不是定值

self-BLEU 是從 20 句隨機抽出來的句子算的，換一批句子，數字就變。FACTS「Q4 實測」用事實腳本把每個設定各自從 5 個 seed 起算（括號是 20 句裡不同句子的數量，第 4 章用過）：

seedk=2k=200p=0.6p=0.999
00.2029 (20)0.1343 (19)0.5013 (9)0.1257 (20)
10.2552 (19)0.1403 (20)0.5349 (10)0.1403 (20)
20.2740 (18)0.0423 (20)0.4284 (13)0.0662 (20)
30.2529 (17)0.1329 (20)0.7719 (5)0.1371 (20)
40.2037 (19)0.0859 (20)0.5104 (9)0.0859 (20)
  • 方向穩定：5 個 seed 都是 k=2 > k=200、p=0.6 > p=0.999。
  • 數值波動大：p=0.6 在 0.4284 到 0.7719 之間，k=200 在 0.0423 到 0.1403 之間。所以「k=2 的 self-BLEU 是 0.2029」只是一次執行的結果，不是這個設定的固定值。
  • k=2 與 k=200 的 seed 0 欄和 hw3.py --q 4 --seed 0（0.2029）、--top-k 200（0.1343）相同，因為 top-k 是 hw3.py 先抽的那一組，起點一樣；p 的兩欄就和 hw3.py 不同（上一節）。
  • 這張表事實腳本還多量了 top_k=0 的兩欄（R2 的對照），在 FACTS 原表裡，第 4 章用過。

5.6　seed 管得到什麼、管不到什麼

第 0 章 0.2.2 節說過：--seed 只做這一件事，在載入模型之前呼叫一次 torch.manual_seed，設定 PyTorch 的 CPU 與 CUDA 亂數產生器。之後 torch.multinomial 每抽一個 token 就從這條亂數流取一段（第 4 章 4.2 節）。所以 seed 決定的是「抽籤用的亂數序列」：同樣的 seed、同樣的抽籤次數、同樣的機率分布，就會抽出同樣的 token。

問題在最後一個條件：機率分布本身也要一樣。本機發現，它會被前面跑過的題目改變。這是 R10。

5.6.1　R10 的現象：同一個 seed，第 13 句不同

5.4 節的表裡，--q 4 --seed 0 的 top-k 是 0.2029，--seed 0（全部 7 題一起跑）卻是 0.2020。兩次的 40 句逐句比對，只有 top-k 的第 13 句不同，其他 19 句與 top-p 的 20 句完全一樣（本書用 diff 比對兩份 log）：

13. He is highly regarded as an expert in machine learning and is considered to be among the top educators in the field.
13. He is highly regarded as a leading expert in the field of machine learning, renowned for his exceptional teaching abilities.

第一行來自 logs/run_q4_seed0.txt 第 23 行（只跑 Q4），第二行來自 logs/run_seed0.txt 第 165 行（全部題目）。兩句前 5 個詞相同，第 6 個詞（an 與 a）起分岔。

5.6.2　找出是誰造成的

本機分兩步追（logs/facts_review1_r10.txt）。第一步：分開跑，前面只放一題，看是哪一題讓 Q4 變了（每一列都是一條獨立的 hw3.py ... --seed 0 指令）：

指令top-k（k=2）top-p（p=0.6）
--q 4 --seed 00.20290.5542
--q 3 4 --seed 00.20290.5542
--q 2 4 --seed 00.20290.5542
--q 1 4 --seed 00.20200.5542

只有 Q1 放在前面時會變。最直覺的猜測是「Q1 用掉了一些亂數」，但 Q1 是 greedy，理論上不抽籤。第二步在同一個 process 裡直接檢查（docs/tools/hw03_r10_cache.py 的輸出，同一份 log 第 8–13 行）：

做法Q1 前後亂數狀態有沒有變Q4 用的 cache 長度top-k
先跑 Q1，再跑 Q4（和 hw3.py 一樣）沒變（CUDA、CPU 都沒變）5440.2020
先跑 Q1，跑 Q4 前把 model._cache = None沒變620.2029
不跑 Q1，直接放一個 544 格的 HybridCache，再從 seed 0 跑 Q45440.2020
不跑 Q1，放一個 282 格的 HybridCache2820.2029

四列 top-p 都是 0.5542。結論是：

  • 不是亂數：Q1 前後，CUDA 與 CPU 的亂數狀態完全沒變。
  • 是 KV cache：Q1 的第一次 generate 在模型物件上留下一份 544 格的 cache（model._cache，Q1 的 32 個 prompt token + max_new_tokens 512）；Q4 的 generate 只需要 30 + 32 = 62 格（最多 30 個新 token 加上 prompt 的 32 個 token，第 4 章 4.4 節的 max_length），發現舊的夠長，就清空沿用，於是 Q4 實際上是用 544 格的 cache 在算。把 cache 清掉，Q4 自己配 62 格，結果就回到 0.2029；不跑 Q1、只人工放一個 544 格的 cache，結果就變成 0.2020。cache 長度決定了結果，和 Q1 有沒有跑無關。
  • 為什麼 cache 長度會改變抽到的 token：沒寫入的格子在 attention 裡被 mask 掉，數學上不影響答案，但運算的形狀不同，fp16 的最後幾位會有極小的差異；機率差一點點，剛好讓第 13 句某一步的抽籤落到相鄰的 token 上。這個機制與 _get_cache 的原始碼在補充章 K.8 節，這裡不重講。
  • 282 格的那一列（282 是 Q2 單獨跑時最後一輪留下的長度：prompt 82 + max_new_tokens 200，計算值；第一步 --q 2 4 也是 0.2029）和 62 格一樣是 0.2029：cache 長度不同只是「可能」改變結果，不是一定。為什麼 544 格會翻、282 格不會，本機沒有追。

所以 R10 的定論是：「設了 seed 還不一定一樣」的原因不是亂數，而是同一個模型物件上留著前一次 generate 的狀態。換句話說，--seed 能保證的是「同一條指令在同一台機器、同一套版本上重跑會一樣」，不保證「Q4 的結果和前面有沒有跑別的題目無關」。本機的 hw3.py --q 4 --seed 0 --top-k 200 --top-p 0.999 連跑兩次，輸出逐字相同（FACTS「ch04 審稿補測」），就是前一種保證。

幾個由此推出的情況：

  • --q 4 1 --seed 0：Q4 先跑，這時模型上還沒有 cache，Q4 自己配 62 格，結果和 --q 4 --seed 0 相同：本機實測 0.2029／0.5542，Q4 的 40 句與 logs/run_q4_seed0.txt 逐字相同（logs/review_ch05.txt）。第 0 章常見錯誤那條「--q 4 1」說的「順序不同，Q4 的結果可能跟著變」，指的是和 --q 1 4 比。
  • 在 Colab 或 notebook 裡：同一個 kernel 先跑過哪些格子、跑過幾次 generate，都會留下 cache。即使自己加了 seed，重新執行 Q4 的格子也不一定得到上一次的結果（推論，本機沒有在 notebook 裡試）。
  • 換 GPU 或套件版本，fp16 的運算本來就可能不同，同一條指令也不保證和本書的句子一樣（補充章 K.8.1 節）。

想讓 Q4 不受前面題目影響，可以在 Q4 的 generate 之前把 model._cache 設成 None（上表第二列就是這樣做的，本機實測回到 0.2029）。hw3.py 為了和原版一致，沒有這樣做。

5.9　常見錯誤

把 self-BLEU 當成品質分數

症狀
說「p=0.6 的 self-BLEU 比較高，所以生成得比較好」。
後果
方向完全相反：高代表 20 句很像、多樣性低；它也完全不看通不通順。
正解
self-BLEU 只量多樣性（越高越不多樣）。流暢、連貫要另外看句子本身。

看到警告就以為只有幾對是 0

症狀
log 只有三則「0 counts of N-gram overlaps」警告，以為只有三對沒重疊。
後果
低估了 0 的比例；p=0.999 那組其實有 290／380 對實際為 0。
正解
Python 的警告預設同一個位置只顯示一次。要數，像 hw03_selfbleu.py 那樣把警告設成每次都記錄。

拿一次執行的分數當定值

症狀
「k=2 的 self-BLEU 是 0.2029」寫進結論，或和同學的數字對不上就以為寫錯。
後果
本機 5 個 seed 下 k=2 在 0.2029–0.2740、p=0.6 在 0.4284–0.7719；不同 seed、不同執行本來就不同。
正解
比較方向（k=2 > k=200、p=0.6 > p=0.999），而不是小數點後的數字；要比數字就固定 seed 與整條指令。

以為設了 seed 就一定一樣

症狀
--seed 0 全部題目一起跑，和只跑 --q 4 --seed 0 的結果不同，以為程式有 bug。
後果
去查亂數，找不到原因。
正解
R10：前面的 Q1 在模型上留下 544 格的 cache，Q4 沿用它。要比較就用完全相同的指令；要隔離，就在 Q4 前把 model._cache 清掉。

--num-samples 給 1

症狀
只想看 k=1 生成什麼，給 --num-samples 1，句子印出來後程式以 ZeroDivisionError 結束。
後果
結束碼 1；如果 --q 後面還有別的題目，它們都不會跑。
正解
至少給 2（R9）。

以為 split() 會處理標點

症狀
以為 education. 與 education 是同一個詞。
後果
手算 BLEU 時 p1、p2 對不上工具的數字。
正解
str.split() 只依空白切，標點黏在前一個詞上；hw3.py 的 self-BLEU 就是這樣算的。

本章小結

  • BLEU = BP × (p1p2p3p4)1/4：pn 是修正 n-gram 精確度，BP 罰比 reference 短的 hypothesis。本機第 0 句對第 2 句：10/12、8/11、6/10、4/9，BP 0.8465，BLEU 0.5367；反過來是 0.5317（不對稱）。split() 不拆標點。
  • 沒有 smoothing 時，任一階沒有重疊，nltk 3.10.3 回傳極小值（例如 6.22 × 10−155），等同 0；警告實際觸發上百次，log 只顯示一次。加 SmoothingFunction().method1 分數會變，但排序不變。
  • self-BLEU（hw3.py:188–197）：每句當 hypothesis、其他 19 句各當一次 reference，380 個有序句對平均。越高越像、多樣性越低，不是品質分數。p=0.6 有 98 對完全相同，k=2 有 146 對實際為 0。
  • hw3.py：--q 4 --seed 0 0.2029／0.5542；k=200、p=0.999 是 0.1343／0.0625；k=1、p=0 是 1.0000。從 log 的句子重算全部一致。hw3.py 的 p=0.999（0.0625）與事實腳本各自 seed 0 的 0.1257 不是同一批句子。
  • 單次數字不是定值：5 個 seed 下方向穩定、數值波動大；不給 seed 每次都不同。
  • R10（實測定論）：--seed 只在載入模型前設一次亂數；先跑 Q1 會在模型上留下 544 格 cache，Q4 沿用它，top-k 第 13 句因此不同（0.2029 → 0.2020），亂數狀態完全沒變。R9：--num-samples 1 會除以零。

下一章是 Q5：不再生成，而是看模型內部。六句話各取最後一層的 hidden state 平均成一個句子向量，再用 t-SNE（一種把高維向量壓到 2 維、盡量保留「誰跟誰近」的方法）畫到平面上，看同一個字 Apple 在不同語境下會不會被分開。

自我測驗

1. 20 句完全相同時 self-BLEU 是多少？20 句彼此沒有任何 4 個連續詞相同時呢？

完全相同時每一對的 BLEU 都是 1，self-BLEU 是 1.0000（本機 k=1、p=0 抽 2 句時就是這樣；20 句全同依定義也一樣）。都沒有 4-gram 重疊時，沒有 smoothing 的 BLEU 每一對都是極小值（例如 10−155 等級），self-BLEU 等同 0。所以 self-BLEU 越高，句子越像、越不多樣。

2. 本機第 0 句對第 2 句的 BLEU 是 0.5367，反過來是 0.5317。為什麼不一樣？哪一個方向被 BP 罰了？

精確度的分母是 hypothesis 的 n-gram 數，所以誰當 hypothesis 會改變 pn（10/12 對 10/14 等）；BP 只罰 hypothesis 比 reference 短的情況。第 0 句（12 個詞）當 hypothesis、第 2 句（14 個詞）當 reference 時被罰，BP = exp(1 − 14/12) ≈ 0.8465；反過來 hypothesis 比較長，BP = 1。

3. log 裡 4-gram 的「0 counts」警告只出現一次，k=2 那組實際上有幾對 4-gram 完全沒重疊？為什麼只印一次？

本機數到 146 次（380 對裡）。Python 的 warnings 預設同一個程式位置、同一則訊息只顯示第一次，後面的被略過，所以 log 只看得到一次。

4. 同學用 --seed 0 跑全部題目，得到 top-k 0.2020；你用 --q 4 --seed 0 得到 0.2029。誰錯了？

都沒錯（假設同樣的 GPU 與版本）。全部題目一起跑時，Q1 在模型上留下 544 格的 KV cache，Q4 沿用它；只跑 Q4 時，Q4 自己配 62 格。兩者的亂數狀態相同，但 fp16 的運算形狀不同，讓第 13 句某一步抽到不同的 token（R10）。要對數字，就用完全相同的指令。

5. --num-samples 1 為什麼會當掉？原版 Colab 為什麼沒有這個問題？

只有一句時，「其他句」是空的，bleu_scores 是空 list，hw3.py:196 的 sum([]) / len([]) 是 0 / 0，丟出 ZeroDivisionError（R9）。原版寫死生成 20 次，永遠有 20 句，碰不到這個邊界；hw3.py 把次數做成旗標，邊界才露出來。

  • Chen & Cherry, A Systematic Comparison of Smoothing Techniques for Sentence-Level BLEU, WMT 2014, aclanthology.org/W14-3346：nltk SmoothingFunction 的各種 method 的來源。
  • nltk 文件 nltk.translate.bleu_score：sentence_bleu 與 SmoothingFunction。
  • Python 文件 warnings：預設的警告過濾規則（同一位置只顯示一次）。
  • PyTorch 文件 Reproducibility：torch.manual_seed 能保證與不能保證的事。
