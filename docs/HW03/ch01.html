第 1 章　Q1 Chat template：同一個問題，兩種 prompt

同一句「Please tell me about the key differences between supervised learning and unsupervised learning. Answer in 200 words.」，一次包成 Gemma 的對話格式再送進模型，一次直接把純文字送進去。這一章逐字看兩種 prompt 變成了哪些 token、模型各自回了什麼、回答怎麼從輸出裡切出來，以及那個替回答打分數的小模型到底在量什麼。最後拆開原版留下來的雙 <bos>。

本章重點

IT 模型是用 <start_of_turn>user … <end_of_turn> 這種對話格式訓練的；套上它，Gemma-2-2b-it 本機實測回了 240 個 token 的散文加條列，評分 6.0734；不套，回了 138 個 token 的純條列，評分 5.0104。這只是一題、一個評分器、一次 greedy（每一步都取機率最高的 token，不抽籤）的結果。

  • 本章對應的原始碼：hw3.py:65–70（calculate_coherence）、:73–85（generate_text_from_prompt，TODO 在 :79–81）、:88–108（q1）。
  • 本章的實測數字來自 logs/run_seed0.txt 的 Q1 段（hw3.py 的實際輸出）與 logs/facts_q1_q2.txt、logs/facts_env_model_tok.txt（事實腳本 docs/tools/hw03_facts.py 的輸出）。哪個數字來自哪一份，會在用到時註明。
  • Q1 這一題在投影片 p.12–13，配分 1 分：要你算出兩種回答的 coherence 分數並比較。

1.1　IT 模型為什麼需要對話格式

Gemma-2-2b-it 名稱裡的 -it 是 instruction-tuned（目錄頁第 1 節）。它的底子是一個「讀前面的字、預測下一個 token」的語言模型，再用大量「使用者問、模型答」的對話資料微調過。微調時的每一筆對話，都不是單純把問句和答句接起來，而是用一組特殊 token 把「誰在說話、這一段從哪裡開始到哪裡結束」標出來。模型學到的是：看到「使用者那一段結束、輪到 model 開始」的記號，接下來就該寫一段回答，寫完再補上「這一段結束」的記號。

這組格式寫在 tokenizer 的設定裡，叫 chat template。所以「套 template」這件事，就是把你的問題排成模型微調時看過的樣子；不套，就是把一句裸的英文交給一個學過對話的模型，讓它自己決定怎麼接。Q1 要觀察的就是這兩種情況的差別。

1.1.1　要認得的特殊 token

Gemma 的 tokenizer 有 256000 個 token，其中幾個是特殊 token，不代表任何文字，只是記號（logs/facts_env_model_tok.txt 的 tokenizer 段）：

tokenid意思
<pad>0補位用，湊齊同一批句子的長度（第 6 章）
<eos>1end of sequence，整段序列結束
<bos>2beginning of sequence，序列從這裡開始，正常只出現一次、在最前面
<start_of_turn>106一個人開始說話；後面緊接著角色名稱 user 或 model
<end_of_turn>107這個人說完了
\n（換行）108不是特殊 token，但 template 裡到處都是，列出來方便對照

tokenizer 的 special_tokens_map 把 <start_of_turn>、<end_of_turn> 列在 additional_special_tokens，所以 decode(..., skip_special_tokens=True) 會把它們連同 <bos>、<eos> 一起拿掉。這一點在 1.4 節切回答時會用到。

1.1.2　Gemma 的 chat_template 全文

chat template 是一段 Jinja 樣板（一種用 {% if %}、{% for %}、{{ 變數 }} 把資料填進文字的樣板語言），存在 tokenizer.chat_template。本機印出來是一整行（logs/facts_env_model_tok.txt 的 chat_template: 那一行，逐字）：

chat_template: "{{ bos_token }}{% if messages[0]['role'] == 'system' %}{{ raise_exception('System role not supported') }}{% endif %}{% for message in messages %}{% if (message['role'] == 'user') != (loop.index0 % 2 == 0) %}{{ raise_exception('Conversation roles must alternate user/assistant/user/assistant/...') }}{% endif %}{% if (message['role'] == 'assistant') %}{% set role = 'model' %}{% else %}{% set role = message['role'] %}{% endif %}{{ '<start_of_turn>' + role + '\n' + message['content'] | trim + '<end_of_turn>\n' }}{% endfor %}{% if add_generation_prompt %}{{'<start_of_turn>model\n'}}{% endif %}"

為了閱讀，下面把同一段依 {% %} 斷行、加上縮排。這是本書排版過的版本，內容與上面那一行相同，程式不會這樣印：

{{ bos_token }}                                         «1»
{% if messages[0]['role'] == 'system' %}
    {{ raise_exception('System role not supported') }}  «2»
{% endif %}
{% for message in messages %}
    {% if (message['role'] == 'user') != (loop.index0 % 2 == 0) %}
        {{ raise_exception('Conversation roles must alternate user/assistant/user/assistant/...') }}  «3»
    {% endif %}
    {% if (message['role'] == 'assistant') %}
        {% set role = 'model' %}                         «4»
    {% else %}
        {% set role = message['role'] %}
    {% endif %}
    {{ '<start_of_turn>' + role + '\n' + message['content'] | trim + '<end_of_turn>\n' }}  «5»
{% endfor %}
{% if add_generation_prompt %}
    {{ '<start_of_turn>model\n' }}                         «6»
{% endif %}
  1. 1開頭先放一個 <bos>。bos_token 就是 <bos> 這個字串。template 產生的字串本身就以 <bos> 開頭，這是 1.7 節雙 <bos> 的起點。
  2. 2不支援 system role。很多聊天模型可以在最前面放一則 {"role": "system", ...} 給整段對話下指示；Gemma 的 template 一看到就丟出例外。要給這類指示，只能寫進第一則 user 訊息裡。本機實測丟出的是 jinja2.exceptions.TemplateError: System role not supported（logs/review_ch01.txt）。
  3. 3user 與 assistant 必須交替。loop.index0 是從 0 起算的訊息編號：偶數則必須是 user、奇數則必須不是 user。兩則 user 連在一起，或第一則就是 assistant，都會丟出例外。第 2 章的多輪對話就是靠這條規則一來一往地接下去。
  4. 4assistant 改名為 model。你在 Python 裡寫 "role": "assistant"，進到 prompt 裡變成 model。所以 Gemma 的 prompt 裡只會看到 user 與 model 兩種角色。
  5. 5每則訊息的固定形狀：<start_of_turn> + 角色 + 換行 + 內容 + <end_of_turn> + 換行。Jinja 的 filter（| trim）比 + 先結合，所以 trim 只作用在 message['content'] 上：內容頭尾的空白與換行會被去掉。第 2 章會看到這個 trim 把模型回答尾巴的 ' \n' 吃掉。
  6. 6add_generation_prompt：對話最後補上「輪到 model 說話」的開頭 <start_of_turn>model\n，但不補 <end_of_turn>。模型看到這裡，下一個 token 就是回答的第一個字。不加的話，prompt 停在 user 那則的 <end_of_turn>\n，模型得自己猜下一步要幹嘛。

這個字串變成 token 之後，本機量到的是 32 個（logs/facts_env_model_tok.txt）：前 6 個是 [2, 2, 106, 1645, 108, 5958]，也就是 ['<bos>', '<bos>', '<start_of_turn>', 'user', '\n', 'Please']；後 5 個是 ['<end_of_turn>', '\n', '<start_of_turn>', 'model', '\n']。沒套 template 的純文字問題是 23 個，開頭是 ['<bos>', 'Please', '▁tell']（▁ 是什麼，第 3 章再講）。把兩邊對起來，32 個 token 可以拆成：

前 6 個與後 5 個是實測印出來的；中間 22 個是「純文字 23 個扣掉 <bos>」推出來的，前提是同一句話放在換行後面和放在句首切法相同（兩邊開頭都是不帶 ▁ 的 Please，加總也剛好等於實測的 32）。另一個旁證：Q1 跑完後留在 model._cache 的 KV cache 長度是 544（第 0 章 0.10 節），正好是 32 + max_new_tokens 512。generate 一開始就照「prompt 長度 + 最多生成幾個」把 cache 配置好，不管實際生成了幾個（這次是 240）；Q1 的第二次 generate（沒有 template，23 + 512 = 535 格就夠）發現模型上已經有一份夠長的 cache，就清空沿用，不重新配置。所以留下來的是第一次、32 個 token 那條路配置的長度。這個「夠長就沿用」的機制本機在第 5 章的實驗裡確認過。

1.3.1　greedy 為什麼可以重現

原版註解特別交代「Make sure to use 'do_sample=False' to get a deterministic response, otherwise the coherence score may be different from the sample answer」。greedy 每一步都取 argmax，整個過程沒有亂數，所以 --seed 對 Q1 沒有作用（第 0 章說過 seed 只影響 Q4）。本機的證據是：hw3.py --seed 0（logs/run_seed0.txt）與事實腳本另外一個 process 重跑（logs/facts_q1_q2.txt），兩次的回答逐字相同，分數都是 6.0734 與 5.0104。

「可以重現」的範圍是同一台機器、同一套軟體版本。換一張 GPU 或換版本，fp16 運算的最後幾位可能不同，只要某一步前兩名的分數夠接近，argmax 就可能翻過去，後面的回答整段改寫（推論，本機只有一張 GPU，沒有跨機比較過）。這也是為什麼投影片 p.12 的填空題寫「Error with 0.5 is accepted」，允許分數有誤差。

本機還量到一個更意外的前提：同一台機器上，前一次 generate 留下的 KV cache 長度也會改變 greedy 的結果。generate 會把 KV cache 留在 model._cache，下一次呼叫只要長度夠用就沿用（第 0 章 0.2.2 節）。Q1 先跑有 template 的那條路，配置了 32 + 512 = 544 格；接著沒有 template 的那條路只需要 23 + 512 = 535 格，於是沿用那 544 格。把沒有 template 的那條路換成各種 cache 長度單獨跑（docs/tools/hw03_q1_cache.py，logs/review_ch01_cache.txt）：

沒有 template 那條路用的 cache新 token字數coherence
544 格（hw3.py 的順序：沿用有 template 那次留下的）138875.0104
535 格（單獨跑，自己配置）136854.2210
600 格、1024 格136854.2210

兩個版本從第 30 個新 token 開始分岔。那一步在 535 格之下，▁outputs 和 ▁the 的 logit 都是 17.875，完全同分，argmax 選了 ▁the；在 544 格之下，▁outputs 是 17.8906，多了一格 fp16 的精度，argmax 就選它。cache 長度不同時，前 30 步每一步 logits 的最大差異都在 0.05 以內（第 0、1 步完全相同）：平常不影響誰是第一名，碰到同分才翻過去。為什麼 544 格會算出不同的數值、而 600 與 1024 格不會，本機沒有追。

所以「可以重現」更精確的說法是：同一台機器、同一套版本、同樣的呼叫順序。hw3.py 照原版 Colab 的順序（先有 template、再沒有 template，共用同一個模型物件），所以本書的 5.0104 是照作業流程跑會得到的數字；只跑沒有 template 的那條路，會得到 4.2210，兩者差 0.79，超過投影片允許的 0.5。原版 Colab 也是同一個順序、同一個 transformers 版本，推論會有同樣的沿用行為，但 Colab 的 GPU 不同，數值本來就可能不同。有 template 的那條路在 hw3.py 裡是第一次 generate，用的是它自己的 544 格，不受影響（換成 600 格是 6.0616，1024 格仍是 6.0734）。

那不寫 do_sample=False 會怎樣？這要看 generation_config：它是模型附帶的一份「generate 的預設參數」（從模型的 generation_config.json 讀進來，掛在 model.generation_config 上），呼叫 generate 時沒傳的參數就從這裡拿，這裡也沒寫的，再用 transformers 的 GenerationConfig 類別內建的預設值。本機印出的內容是（logs/facts_env_model_tok.txt 第 47 行，事實腳本 model 段的輸出，逐字）：

generation_config: {'cache_implementation': 'hybrid', 'pad_token_id': 0, 'bos_token_id': 2, 'eos_token_id': [1, 107], '_from_model_config': True, 'transformers_version': '4.47.0'}

裡面沒有 do_sample，所以會用 GenerationConfig 類別的預設值 False。本機實測拿掉 do_sample=False、其他不變，兩條路生成的 token 與用 do_sample=False 時逐一相同（同樣的 cache 長度下比較，logs/review_ch01.txt）：不寫也是 greedy。明寫的好處是不依賴模型附的設定檔。

長度就不一樣了。原版 Colab 的 generate_text_from_prompt 沒有 max_new_tokens 參數，TODO 若只寫 model.generate(input_ids, do_sample=False)，本機實測（logs/review_ch01.txt）：

有 template20**4.0107
沒有 template20)−2.8643

兩條路都只生成 20 個新 token，句子寫到一半就斷了，分數也掉很多，沒有 template 的甚至是負的。generation_config 沒有 max_length，所以用 GenerationConfig 類別的預設 20；transformers 4.47 看到「長度是預設值」時，會把它解讀成「20 個新 token」，加上 prompt 長度當上限（transformers/generation/utils.py:1471–1473）。這次執行沒有印出任何警告，很容易以為程式正常。所以 hw3.py 把 max_new_tokens 加成函式參數、預設 512（--max-new-tokens，第 0 章旗標表）。

1.3.2　為什麼會停在 <end_of_turn>

上面那行 generation_config 的 'eos_token_id': [1, 107] 決定了何時停：generate 生成出 id 1（<eos>）或 id 107（<end_of_turn>）任何一個，就停下來。hw3.py:80 沒有傳 eos_token_id，所以用的是模型附的這份設定。本機量到兩條路最後一個新 token 都是 <end_of_turn>（logs/facts_q1_q2.txt 的 last token '<end_of_turn>'）：模型寫完回答，自己補上「這一段結束」的記號，generate 看到 107 就收工，遠在 512 的上限之前。

這兩個 id 的 list 是 Q4 的伏筆：Q4 自己傳了 eos_token_id=tokenizer.eos_token_id，也就是只有 1，把 107 蓋掉了，所以 Q4 的句子遇到 <end_of_turn> 不會停（第 4 章）。

另外，Q1 跑完 generate 會在模型物件上留下一份 KV cache，後面的題目會沿用它，並因此影響 Q4 的取樣結果，見 第 0 章 0.2.2 節，第 5 章詳談。

1.4　怎麼把回答切出來

generate_text_from_prompt 回傳的是整段「prompt + 回答」decode 後的字串，q1 再各自切出回答。先看有 template 的那條路：

skip_special_tokens=True 把兩個 <bos>、<start_of_turn>、<end_of_turn> 全部拿掉之後，字串剩下角色名稱與內容。本機 decode 出來的前 300 個字元（logs/facts_q1_q2.txt，repr，逐字）：

'user\nPlease tell me about the key differences between supervised learning and unsupervised learning. Answer in 200 words.\nmodel\nSupervised and unsupervised learning are two fundamental types of machine learning. \n\n**Supervised learning** involves training a model on labeled data, where each input ha'

原本 template 裡的 <start_of_turn>model\n 只剩 model\n，所以 split("model\n")[-1] 取「最後一個 model\n 之後的所有文字」，再去掉頭尾的換行與空白，就是回答。

沒有 template 的那條路沒有 model\n 可以切，改用問題的最後一個字：

question.split(" ")[-1] 是 'words.'（事實腳本印的 split key for no-template: 'words.'）。decode 出來的字串是問題原文接著回答（logs/facts_q1_q2.txt，前 300 字元，逐字）：

'Please tell me about the key differences between supervised learning and unsupervised learning. Answer in 200 words.\n\n**Supervised Learning:**\n\n* **Labeled data:** Uses data with known outputs (labels) to train models.\n* **Goal:** Predict outputs for new, unseen data.\n* **Examples:** Image classific'

以 'words.' 切開、取最後一段，就是 \n\n**Supervised Learning:** 開始的回答。

兩種切法都靠一個沒有寫出來的假設：

  • 有 template 時，假設回答裡不會出現 model\n。這題問的是機器學習，回答裡 model 這個字到處都是；只要某一行剛好以 model 結尾（例如 ... train a model 後面換行），[-1] 就會只拿到那之後的半段。
  • 沒有 template 時，假設回答裡不會出現 words.。題目要求「Answer in 200 words.」，模型很可能在回答裡寫出同樣的字（例如結尾補一句「… in 200 words.」），那樣回答前面整段都會被切掉。

本機這一次的兩段回答剛好都沒有這兩個字串，所以切得正確。換一個問題、換一次生成，就不保證了。比較穩的做法是不切字串、直接切 token：output_ids[0][input_ids.shape[1]:] 只留新生成的部分再 decode。hw3.py 自己的 Q2（:163，沿用原版 Colab 第 19 格的寫法）就是這樣切的，第 2 章會看到。

1.5　coherence 評分器在量什麼

投影片 p.13 說評分模型的目的是「Calculate the coherence score between the question (prompt) and the model response」。hw3.py 的函式：

對照原版 Colab 第 13 格：

SCORING_MODEL = AutoModelForSequenceClassification.from_pretrained('cross-encoder/ms-marco-MiniLM-L-6-v2')
SCORING_TOKENIZER = AutoTokenizer.from_pretrained('cross-encoder/ms-marco-MiniLM-L-6-v2')


def calculate_coherence(question, answer, scoring_model=SCORING_MODEL, tokenizer=SCORING_TOKENIZER):
  features = tokenizer([question], [answer], padding=True, truncation=True, return_tensors="pt")
  scoring_model.eval()
  with torch.no_grad():
      scores = scoring_model(**features).logits.squeeze().item()
  return scores

函式本體一樣，差在評分模型從哪裡來：原版在格子裡載入成全域變數、當預設參數；hw3.py 在 q1 裡載入（:89–90）再明確傳進來，所以每次呼叫 q1 都會從快取讀一次評分模型。第 0 章 0.10 節量過 Q1 的 10.7 s 包含了這次載入，而評分模型跑在 CPU 上，這裡不重複。

1.5.1　cross-encoder：一次讀兩段

cross-encoder/ms-marco-MiniLM-L-6-v2 是一個很小的 BERT 類模型（BERT 是只有 encoder 的 Transformer：不逐字往後生成，而是一次讀完整段、每個 token 前後都看得到，最後接一個小的輸出層），22,713,601 個參數，大約是 Gemma-2-2b-it 的百分之一。它用 AutoModelForSequenceClassification 載入，這個類別名稱是「序列分類」，但 num_labels 是 1，也就是輸出層只有一個數字，拿來當分數而不是分類；tokenizer 的 model_max_length 是 512（logs/facts_q1_q2.txt 的 scoring model params 那一行）。名字裡的幾個部分：

  • cross-encoder：:66 把 [question] 與 [answer] 當成「一對」交給 tokenizer（回傳一個像 dict 的物件，裝著 input_ids、attention_mask 等 tensor；:69 的 **features 把這些 key 當成具名參數傳給模型，模型回傳的物件上 .logits 就是輸出層的數值），兩段被接成一個序列一起送進模型，模型同時看到兩段、讓兩段的 token 互相做 attention，最後只輸出一個數字。對比的是 bi-encoder：兩段各自算一個向量，再算相似度。
  • ms-marco：它是在 MS MARCO 這個搜尋資料集上訓練的，原本的任務是「給一個搜尋查詢和一段文章，判斷這段文章跟查詢有多相關」，用來替搜尋結果排序（依 Hugging Face 模型頁的說明）。所以它量的嚴格說是相關性：這段回答像不像是在回應這個問題。作業把它叫做 coherence。
  • MiniLM-L-6：MiniLM 是一種從大模型蒸餾（distillation，讓小模型模仿大模型的輸出）出來的小型 BERT；從名稱看，L-6 指 6 層，本機沒有另外核對。

1.5.2　輸出是 logit，不是機率

:69 的 .logits.squeeze().item() 拿到的是模型最後那一個輸出的原始數值，沒有經過 sigmoid 或 softmax。它沒有上下限：可以是負的，也可以超過 1。本機的 6.0734 和 5.0104 都遠大於 1，就是因為它不是機率。

如果硬把它當 logistic 迴歸的 logit 套上 sigmoid，6.0734 → 0.9977、5.0104 → 0.9934（計算值，hw3.py 沒有做這一步）：兩個回答在這個評分器眼裡都是「非常相關」，差別在很靠近 1 的地方。這提醒我們，這個分數沒有校準過的尺度：「差 1 分」既不是「好 1 成」，也沒有人定義過「幾分算及格」。它只能拿來比較同一個問題下的兩個回答，而且只代表這一個評分器的看法。

1.5.3　512 token 的截斷有沒有碰到

:66 的 truncation=True 表示問題加回答超過 512 個 token 時，評分器只看前 512 個，後面的被丟掉。如果被截斷，回答後半段寫得好不好就不影響分數了。本機量到評分器實際收到的 token 數（含它自己的特殊 token，也就是 BERT 類模型開頭與分隔兩段用的記號）：有 template 285 個、沒有 template 189 個（logs/facts_q1_q2.txt 的 scorer tokens），都遠低於 512，截斷沒有碰到。padding=True 在只有一對的時候不會補任何東西。

1.7　雙 <bos>：讀 code 不盡信文件

讀 code 不盡信文件：R1 Q1 的 prompt 開頭有兩個 <bos>

（R1 是全書大綱的問題對照表裡第 1 條 repo 問題的編號。）

現象：apply_chat_template(..., tokenize=False) 產生的字串已經以 <bos> 開頭（template 第一句就是 {{ bos_token }}），接著 hw3.py:77 的 tokenizer(prompt) 預設 add_special_tokens=True，又在最前面加一個。本機實測 input_ids 開頭是 [2, 2, 106, …]，共 32 個 token；用 apply_chat_template(..., tokenize=True) 直接拿 id，是 31 個，只有一個 <bos>（logs/facts_env_model_tok.txt）：

tokenizer(prompt).input_ids: len 32, first 6 [2, 2, 106, 1645, 108, 5958] -> ['<bos>', '<bos>', '<start_of_turn>', 'user', '\n', 'Please'], last 5 ['<end_of_turn>', '\n', '<start_of_turn>', 'model', '\n']
apply_chat_template(tokenize=True): len 31, first 3 ['<bos>', '<start_of_turn>', 'user']

為什麼看不出來：hw3.py 印的是 tokenize 之前的字串（1.2 節），上面只有一個 <bos>；第二個是在印完之後才加的。decode 時 skip_special_tokens=True 又把兩個都拿掉，輸出裡也看不到。只有直接看 input_ids 才會發現。沒有 template 的那條路沒有這個問題：純文字裡沒有 <bos>，tokenizer 加一個，剛好一個。

影響（本機實測，greedy、max_new_tokens=512）：事實腳本把同一個 template 字串改用 tokenizer(prompt, add_special_tokens=False) 轉成 id，只留 template 自帶的那一個 <bos>，其餘設定不變。這是事實腳本的實驗，不是 hw3.py 的輸出（logs/facts_q1_q2.txt 的 with template, single <bos> 段）：

開頭幾乎一樣（「two fundamental approaches in machine learning」對「two fundamental types of machine learning」），接著就分岔了：單 <bos> 的版本沒有比喻、沒有「Key differences」條列，兩段散文加一句「In essence」總結。多一個 token、而且是放在最前面的 <bos>，就足以讓 greedy 的回答換一條路走。

表中單 <bos> 有兩列，原因是 1.3.1 節的 cache 長度效應：事實腳本是在雙 <bos> 那次之後跑的，沿用了 544 格，得到 161 個 token、6.1188；自己配置 31 + 512 = 543 格時，第 76 個新 token 開始不同，得到 149 個 token、6.3992（logs/review_ch01_cache.txt，這兩列都是實驗，不是 hw3.py 的輸出）。兩列的結論一樣：回答內容換了，分數和雙 <bos> 的 6.0734 相差 0.05 到 0.33（計算值）。上面描述的文字是 161 個 token 那一版。

為什麼保留：hw3.py 的 docstring（hw3.py:11–12）說「Everything else (including quirks like the double <bos> in Q1/Q2) is kept identical to the Colab so results match the TA reference answers」，:76 的註解也寫明「a chat-template prompt ends up with two <bos>」。作業要和助教的參考答案比對，所以照原版保留。

正確的寫法（二選一）：

# 1) 字串已經有 <bos>，tokenize 時不要再加
input_ids = tokenizer(prompt, add_special_tokens=False, return_tensors="pt").input_ids.to(DEVICE)

# 2) 讓 apply_chat_template 直接回傳 token id，不經過字串
input_ids = tokenizer.apply_chat_template(chat, tokenize=True, add_generation_prompt=True,
                                          return_tensors="pt").to(DEVICE)

第 1 種只改一個參數，但要記得「字串從哪裡來」：同一個函式也拿來處理沒有 template 的純文字，那時候不加 <bos> 反而錯了，所以要分開處理。第 2 種從源頭就不經過字串，不會有這個問題。上面這兩段是本書寫的示意，不在 hw3.py 裡；第 1 種的效果就是表中「單 <bos>」那一列，第 2 種本機只量過 token 數（31），沒有跑過生成。

1.9　常見錯誤

把 coherence 當成機率或百分比

症狀
看到 6.07，以為「超過 1 是程式錯了」；或說「有 template 好了 1 成」。
後果
誤判程式有 bug，或對分數差做出評分器撐不起的解讀。
正解
它是 cross-encoder 的原始 logit，沒有上下限、沒有校準過的尺度。只能在同一個問題下比較兩個回答。

以為印出來的 prompt 就是模型看到的

症狀
從「Prompt inputted to the model」那幾行判斷只有一個 <bos>。
後果
看不到雙 <bos>；修改 prompt 時也可能重複加特殊 token。
正解
要知道模型收到什麼，印 input_ids 或 tokenizer.convert_ids_to_tokens(input_ids[0])，不要看 tokenize 之前的字串。

以為 decode(output_ids[0]) 就是回答

症狀
把 generate 的輸出整段 decode 拿去評分。
後果
回答前面黏著整個問題，評分器看到「問題 + 問題 + 回答」，分數失真。
正解
generate 的輸出包含 prompt。照 hw3.py 用字串切，或更穩地切 token：output_ids[0][input_ids.shape[1]:]。

用字串切回答，卻沒檢查切點

症狀
換一個問題後，回答莫名只剩後半段。
後果
回答裡出現了 model\n 或問題的最後一個字，split(...)[-1] 從錯的地方切。
正解
印出切之前的完整字串確認一次；或改成切 token，不依賴回答內容。

給 Gemma 加一則 system 訊息

症狀
chat = [{"role": "system", ...}, {"role": "user", ...}]。
後果
apply_chat_template 丟出 jinja2.exceptions.TemplateError: System role not supported（本機實測，logs/review_ch01.txt）。連續兩則 user 訊息則是 Conversation roles must alternate user/assistant/user/assistant/...。
正解
Gemma 的 template 只接受 user／assistant 交替。要下指示，寫進第一則 user 訊息。

改用單 <bos> 之後，拿分數去對助教的答案

症狀
修掉雙 <bos>，回答和 hw3.py 的整段不同。
後果
本機這一題的分數差 0.05 到 0.33（看 cache 長度，1.7 節），回答內容換了一套；其他依賴生成內容的地方就對不上了。
正解
交作業時照原版（雙 <bos>）跑；想知道正確寫法的效果，另外跑一份對照，像 1.7 節那樣分開記錄。

本章小結

  • Gemma 的 chat template：開頭 {{ bos_token }}；不支援 system role；user／assistant 必須交替；assistant 改名 model；每則訊息是 <start_of_turn> + 角色 + 換行 + trim 過的內容 + <end_of_turn> + 換行；add_generation_prompt 補上 <start_of_turn>model\n。
  • Q1 的 TODO 是一行 model.generate(input_ids, max_new_tokens=max_new_tokens, do_sample=False)。greedy 沒有亂數，同一台機器、同樣的呼叫順序可以完全重現；但前一次 generate 留下的 KV cache 長度會改變 fp16 的數值，碰到同分就換答案（沒有 template 那條路：沿用 544 格是 5.0104，單獨跑是 4.2210）。不給 max_new_tokens 只會生成 20 個新 token，而且沒有警告；generation_config 的 eos_token_id 是 [1, 107]，所以兩條路都停在 <end_of_turn>。
  • generate 的輸出包含 prompt。有 template 用 split("model\n")、沒有用 split("words.") 切出回答，兩者都假設回答裡不會出現切點。
  • 評分器 cross-encoder/ms-marco-MiniLM-L-6-v2 一次讀「問題、回答」這一對，輸出一個沒有上下限的相關性 logit，不是機率；這次的輸入 285 與 189 個 token，沒碰到 512 的截斷。
  • 本機實測：有 template 240 個新 token、6.0734；沒有 template 138 個新 token、5.0104。回答形狀一個是完整回答、一個是條列筆記；兩者都沒寫到 200 字；沒套 template 也用 <end_of_turn> 收尾。這是一題、一個評分器、一次 greedy 的證據。
  • R1：有 template 時 input_ids 是 [2, 2, 106, …] 共 32 個；單 <bos> 是 31 個，實驗得到 149 或 161 個新 token、6.3992 或 6.1188（看 cache 長度），回答內容都和 hw3.py 不同。hw3.py 為了和助教答案一致而保留。

下一章是 Q2：同一套 template 拿來做多輪對話，chat_history 一輪一輪把 prompt 接長，並且不再直接 generate，而是先看模型對下一個 token 的機率分布。

自我測驗

1. 有 template 的 prompt 印出來只有一個 <bos>，為什麼 input_ids 是 32 個、開頭兩個 2？把 32 拆成各部分。

template 自己以 {{ bos_token }} 開頭，印出來的字串就有一個 <bos>；hw3.py:77 的 tokenizer(prompt) 預設 add_special_tokens=True，又在最前面加一個。32 = 2（兩個 <bos>）+ 3（<start_of_turn> user \n）+ 22（問題本身）+ 5（<end_of_turn> \n <start_of_turn> model \n）。

2. 沒有套 template 時，prompt 裡沒有任何 <start_of_turn>，為什麼模型還是在 138 個 token 就停了，沒有寫到 512？

模型最後生成了 <end_of_turn>（id 107）。模型附的 generation_config 的 eos_token_id 是 [1, 107]，hw3.py 沒有覆蓋它，所以 generate 看到 107 就停。IT 模型在微調時學到「回答完寫 <end_of_turn>」，就算 prompt 沒有對話格式也照做。

3. 同學說：「有 template 的 coherence 是 6.07、沒有的是 5.01，所以套 template 的回答品質好了大約 1 成。」哪裡有問題？

兩個地方。第一，分數是 cross-encoder 的原始 logit，不是機率或百分比，也沒有校準過的尺度，「差 1 分」不能換算成「好幾成」。第二，這只是一個問題、一個評分器（而且是搜尋相關性模型）、一次 greedy 的結果，不能推廣成「套 template 一定比較好」。單 <bos> 的實驗版回答更短、沒有 Key differences 條列，分數反而更高，說明分數高低的原因並不清楚。

4. 假設有 template 的回答裡有一行寫「… we train a model」然後換行。split("model\n")[-1] 會拿到什麼？怎麼改比較穩？

decode 後那一行會變成 ... we train a model\n，split("model\n") 在這裡多切一刀，[-1] 只拿到這一行之後的部分，回答前半段就不見了。比較穩的做法是切 token 而不是切字串：tokenizer.decode(output_ids[0][input_ids.shape[1]:], skip_special_tokens=True)，只 decode 新生成的部分。

5. 要讓模型只看到一個 <bos>，有哪兩種改法？為什麼不能直接在 generate_text_from_prompt 裡一律加 add_special_tokens=False？

一是 tokenizer(prompt, add_special_tokens=False)，二是 apply_chat_template(..., tokenize=True, return_tensors="pt") 直接拿 id。這個函式同時處理沒有 template 的純文字：那時字串裡沒有 <bos>，一律關掉特殊 token 會讓純文字那條路變成零個 <bos>。所以第一種改法要依 prompt 的來源分開處理。
