0.2.2　一題一個函式，模型只載入一次

原版的七題是 notebook 裡一段一段的格子；hw3.py 把每一題包成一個函式 q1…q7，簽名都一樣是 (tokenizer, model, args)，再用一個 dict 把題號對應到函式。七題各自在做什麼，目錄頁第 1 節的表格列過一次，這一章只看它們共用的骨架：

串起來看，main 做的事依序是：解析旗標 → 有 --seed 就設 torch.manual_seed → 有 HF_TOKEN 就登入 → 載入一次模型（:514）→ 照 --q 給的順序逐題呼叫（:515–517），每題前面印一條 # 分隔線。幾個從這兩段程式碼直接讀得出來的細節：

  • --q 的 nargs="+" 讓它可以給多個題號，例如 --q 1 3 4；不給就是 list(QUESTIONS)，也就是 1 到 7 全跑；choices 限定只能是 1–7，給 8 會被 argparse 擋下來。
  • 執行順序是你寫的順序，不是由小到大：for q in args.q 直接照 list 走。
  • 七題共用同一個 model 物件。這省下了重複載入的時間，代價是前一題留在模型物件上的狀態會被下一題看到。最明顯的是 KV cache：模型逐字生成時，把前面每個 token 在每一層算過的 key、value 存起來，下一步就不必重算（Gemma 2 用的類別叫 HybridCache；它存了什麼、佔多少、怎麼被沿用，補充章整章講）。Q1 跑完後，model.generate 會在 model._cache 留下一個 0.054 GiB 的 HybridCache（0.10 節），後面的題目會沿用它。這件事會讓 Q4 的取樣結果跟「只跑 Q4」不同，第 5 章專門處理。
  • --seed 只做一件事：在載入模型之前呼叫一次 torch.manual_seed。沒給就完全不設（原版 Colab 也沒設，見 :487 的 help）。只有 Q4 有隨機取樣，所以 seed 實際上只影響 Q4。
  • ArgumentParser(description=__doc__) 把整段 docstring 當成 --help 的說明文字。--help 在 argparse 解析時就結束程式，不會載入模型：本機實測先印 usage: hw3.py [-h] [--q {1,2,3,4,5,6,7} ...，接著是整段 docstring 與旗標說明，整條指令 2.2 秒，時間花在 import torch、transformers 這些套件（logs/review_ch00_errors.txt 第 3 段）。

0.4　模型從哪裡來：load_model

對照原版 Colab 第 10 格：

import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

model_id = "google/gemma-2-2b-it"
dtype = torch.float16

# Load tokenizer and model
tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    device_map="cuda",
    torch_dtype=dtype,
)

兩者幾乎一樣，hw3.py 多了兩行：attn_implementation="eager"（下面的「現在的做法」框）與 model.eval()。逐項看：

  • google/gemma-2-2b-it：Hugging Face Hub 上的模型 id。from_pretrained 第一次會下載到 HF 快取，之後直接讀快取；本機快取裡這個模型佔 5.251 GB。AutoTokenizer 依模型的設定檔挑出 GemmaTokenizerFast，AutoModelForCausalLM 挑出 Gemma2ForCausalLM（「CausalLM」指只能看前面、一次預測下一個 token 的語言模型）。
  • torch_dtype=torch.float16：每個參數用 2 bytes 的 fp16 存。模型自己的 config.json 寫的是 bfloat16（另一種 2 bytes 的浮點格式，數值範圍較大、精度較低），這份作業跟原版 Colab 一樣用 fp16 載入。所以 2,614,341,888 個參數 × 2 bytes = 4.87 GiB（0.8 節）。
  • device_map="cuda"：載入時直接把權重放到 GPU。本機紀錄：model dtype: torch.float16 device: cuda:0，載入後 torch.cuda.memory_allocated() 是 4.87 GiB，PyTorch 實際向驅動程式保留（reserved）的是 5.06 GiB。
  • model.eval()：切換成推論模式。原版只在 Q6 的格子裡呼叫，hw3.py 統一在載入時呼叫一次。注意 eval() 不會關掉梯度計算；各題自己用 torch.no_grad()（例如 hw3.py:68、:140），Q7 的函式則加了 @torch.no_grad()。

載入要多久：本機三次紀錄的 load_model 分別是 2.2 s、3.1 s、4.2 s（logs/facts_env_model_tok.txt、facts_review1_shapes_q4steps_rescale26.txt、facts_review1_perq.txt），都是模型已經在快取裡的情況。

現在的做法：明寫 attn_implementation="eager"

attn_implementation 選的是 attention 用哪一套實作：eager 是照公式一步一步用 PyTorch 運算算出 q·kᵀ、softmax 等中間結果（所以 attention 權重拿得到），sdpa 是呼叫 PyTorch 合併好的 scaled_dot_product_attention，比較快，但中間的權重不留下來。原版 Colab 沒寫這個參數，hw3.py:56 寫了，:55 的註解說明原因：「Gemma2 uses eager attention by default in transformers 4.47; Q6 needs attention weights」。

  • 不寫的話是什麼？本機實測，transformers 4.47.0 不指定時，Gemma 2 用的就是 eager（logs/facts_env_model_tok.txt 的 without attn_implementation: eager）。所以寫不寫，行為相同。
  • 為什麼預設不是 SDPA？transformers 4.47.0 的 models/gemma2/modeling_gemma2.py:553–562，Gemma2PreTrainedModel._check_and_enable_sdpa 會把預設的 sdpa 換成 eager，docstring 寫的是「SDPA reduces the model performance on Gemma2 because of the logits softcapping」。soft-capping 是 Gemma 2 在 attention 分數上多做的一步（0.6 節），eager 實作在同檔 :185–188 做這一步。
  • 那為什麼還要寫？不依賴預設值。第 7 章（Q6）要拿 outputs.attentions 畫 attention map，寫明之後，讀程式的人不必知道 transformers 內部的這段邏輯，就能確定走的是 eager 路徑。

在本機核對上面的 transformers 原始碼，檔案在 .venv/lib/python3.12/site-packages/transformers/models/gemma2/modeling_gemma2.py。

版本的部分，目錄頁已經說過 transformers 釘在 4.47.0、sae-lens 釘在 5.x。這一章的模型結構、行號都以 transformers 4.47.0 為準；換版本後 modeling_gemma2.py 的行號與部分行為可能不同。

0.5　模型總覽：一次 forward 經過哪些站

Gemma-2-2b-it 的 config（logs/facts_env_model_tok.txt）裡跟結構有關的值：

config 欄位值意思
num_hidden_layers26decoder block 的數量，model.model.layers[0] 到 [25]
hidden_size2304每個 token 在層與層之間傳遞的向量長度
intermediate_size9216MLP 中間層的寬度（2304 的 4 倍）
num_attention_heads ／ num_key_value_heads8 ／ 48 個 query head 共用 4 組 key／value（GQA）
head_dim256每個 head 的向量長度。注意 8 × 256 = 2048 不等於 hidden_size 2304：Gemma 2 的 head 數 × head_dim 和 hidden_size 是分開設定的，所以 q_proj 是 2304 → 2048、o_proj 再 2048 → 2304

把這些值放回資料流裡，一次 forward 長這樣：

逐站說明，括號裡是 transformers 4.47.0 modeling_gemma2.py 的行號：

  1. input_ids → embed_tokens：每個 token id 到一張 256000 × 2304 的表裡查出一列，得到 (1, T, 2304)。
  2. × √2304：Gemma 把 embedding 乘上 √hidden_size = √2304 = 48 才送進第一層（:740–741，normalizer = torch.tensor(self.config.hidden_size**0.5, dtype=hidden_states.dtype)）。本機實測 hidden_states[0] 和 embed_tokens(ids) * sqrt(2304) 逐元素完全相等（torch.equal 為 True）。
  3. 26 層 decoder：每一層輸入、輸出都是 (1, T, 2304)，內部結構見下一節。偶數層（0, 2, …, 24）是 sliding window 層，奇數層是 global 層（:440，self.is_sliding = not bool(layer_idx % 2)；實測 sliding 層的清單就是 0 到 24 的 13 個偶數）。
  4. model.norm：26 層跑完之後再做一次 RMSNorm（:778）。
  5. lm_head：一個 2304 → 256000 的線性層，把每個位置的向量變成 256000 個詞各自的分數。它的權重就是 embed_tokens 的那張表：本機實測兩者的 data_ptr() 相同，也就是指向同一塊 GPU 記憶體。
  6. final soft-cap：logits / 30 → tanh → × 30（:993–996）。tanh 的值域是 (−1, 1)，所以 logits 一定落在 (−30, 30)，大的值被「軟性地」壓扁，而不是硬截斷。本機用 Q7 那句 13 個 token 的句子實測，logits 絕對值最大是 26.16。

第 2 章（Q2）看的 top-10 機率、第 4 章（Q4）的取樣，都是從最後一站的 logits 出發。

圖裡的每一個方框，都對得上 print(model.model.layers[0]) 印出來的子模組（0.6.3 會逐行對照）。下面分三塊說明。

0.6.1　「三明治」RMSNorm 與 residual stream

RMSNorm 是把向量除以它自己的均方根（root mean square），讓長度回到固定尺度，再乘上一組可學的權重；它比 LayerNorm 少了「減平均」這一步。Gemma 2 每一層用了四個 RMSNorm，transformers 4.47.0 的 Gemma2DecoderLayer.forward 的後半（:488–495）寫成：

        hidden_states = self.post_attention_layernorm(hidden_states)
        hidden_states = residual + hidden_states

        residual = hidden_states
        hidden_states = self.pre_feedforward_layernorm(hidden_states)
        hidden_states = self.mlp(hidden_states)
        hidden_states = self.post_feedforward_layernorm(hidden_states)
        hidden_states = residual + hidden_states

前面還有 residual = hidden_states、input_layernorm 與 self_attn 這三步（:474–487）。所以每個分支都是「input／pre norm → 做事 → post norm → 加回 residual」，norm 把子層夾在中間，這就是「三明治」的意思。注意 post_* 那兩個 norm 作用在子層的輸出上，加回去之前；residual stream 本身在層與層之間不經過 norm，要到 26 層全部跑完、進入 model.norm 才 norm 一次。這一點在 0.9 節解讀 hidden state 的大小時會用到。

0.6.2　Attention：GQA、除以 16、soft-cap 50、sliding window

  • q、k、v 投影：q_proj 把 2304 投影成 2048 = 8 個 head × 256，k_proj、v_proj 只投影成 1024 = 4 組 × 256。
  • GQA（grouped-query attention）：8 個 query head 只配 4 組 key／value，每組 k、v 由 2 個 query head 共用。transformers 在算分數前用 repeat_kv 把 4 組複製成 8 組（:180–181）。好處是 k_proj、v_proj 的參數與 KV cache 都只要一半；0.8 節會算出省了多少參數。
  • RoPE：位置資訊不是加在 embedding 上，而是在每一層把 q、k 依位置旋轉一個角度（Gemma2RotaryEmbedding，rope_theta = 10000），讓 q·k 的值只跟兩個 token 的相對距離有關。
  • 除以 16：分數是 q·kᵀ × scaling，scaling = query_pre_attn_scalar ** -0.5 = 1/√256 = 1/16（:344、:183）。
  • attention soft-cap 50：分數再經過 s / 50 → tanh → × 50（:185–188），壓進 (−50, 50)。這和 0.5 節最後 logits 的 soft-cap 是兩個不同的地方、兩個不同的值：attention 分數是 50，logits 是 30。
  • mask：因果 mask 讓每個 token 只能看到自己和前面的 token。偶數層另外加 sliding window：每個 token 最多只看前面 4096 個位置；奇數層（global）看全部。本作業的每一個 prompt 都遠短於 4096 個 token，所以這兩種層在這份作業裡的行為其實一樣。
  • softmax → × v → o_proj：softmax 後得到 attention 權重 (1, 8, T, T)，用它對 v 加權平均，8 個 head 的結果接回 2048 維，再由 o_proj 投影回 2304。第 7 章（Q6）畫的 heatmap，就是其中一層、一個 head 的那張 T × T 權重。

同一次 forward 打開 output_attentions=True、output_hidden_states=True 時的回傳值：

  • outputs.attentions：26 個（每層一個），每個 (1, 8, 13, 13)：batch 1、8 個 head、13 個 query 位置 × 13 個 key 位置。

這一個形狀是推出來的，不是量出來的

q、k、v 拆成 head 之後的 (1, 8, T, 256) 與 (1, 4, T, 256)，是在 attention 函式內部用 view 加 transpose 做出來的（transformers 4.47.0 modeling_gemma2.py:379–381），不經過任何子模組，forward hook 抓不到。表裡實測到的是 q_proj 輸出 2048、k_proj／v_proj 輸出 1024；再加上 config 的 num_attention_heads = 8、num_key_value_heads = 4、head_dim = 256，推出 2048 = 8 × 256、1024 = 4 × 256，拆開後就是這兩個形狀。

後面幾章會再看到這些形狀，只是 T 和 batch 換了：第 6 章（Q5）一次餵 6 句、padding 到 9 個 token，hidden_states[-1] 是 (6, 9, 2304)；第 7 章（Q6）逐步生成的第一步一次餵 3 個 token，每層的 attention 是 (1, 8, 3, 22)，22 是 KV cache 的長度；第 9 章（Q7）SAE 對 13 個 token 各輸出 16384 個 feature，形狀是 [13, 16384]。

0.9　hidden_states 的 27 個索引

這一節是第 6、8、9 章的前置知識，後面會一直回來查。呼叫模型時加上 output_hidden_states=True，回傳的 outputs.hidden_states 是一個長度 27 的 tuple。26 層為什麼有 27 個？看 transformers 4.47.0 Gemma2Model.forward 怎麼收集它們（:747–781 節錄）：

        for decoder_layer in self.layers[: self.config.num_hidden_layers]:
            if output_hidden_states:
                all_hidden_states += (hidden_states,)
            ...
            hidden_states = layer_outputs[0]
            ...
        hidden_states = self.norm(hidden_states)

        if output_hidden_states:

驗證的方法（docs/tools/hw03_facts.py 的 model 段，也就是 0.6.3 那條指令；結果與下面的範數表都在 logs/facts_env_model_tok.txt）：在每一層掛 forward hook 記下輸出，再和 hidden_states 逐一比對。這裡用的句子是較短的 "Time travel will become a reality."，不是 0.7 節那句 13 個 token 的。記住兩條就不會搞錯：

  • 索引比 block 編號大 1。要拿「block 20 的輸出」，要寫 hidden_states[21]。第 8 章（Q7）會看到程式在這裡差了一：Q7 的 SAE 是在 block 20 的輸出上訓練的，Q7.2–7.3 算最大 activation 的函式卻寫死拿 hidden_states[sae.cfg.hook_layer]（hw3.py:393，hook_layer 是 20），也就是 block 19 的輸出，不受任何旗標控制。Q7.4–7.6 則用旗標 --sae-layer-idx（預設 24），它同樣是索引，不是 block 編號。
  • 最後一個是 norm 過的。hidden_states[-1] 就是 [26]，它的尺度跟 [25] 差很多。下表是同一句話裡每個位置向量的 L2 範數（長度），「其他 token」是除了 <bos> 以外各位置的平均：

residual stream 在層與層之間沒有被 norm（0.6.1），每一層都往上加東西，所以範數從 [1] 的約 80 一路長到 [25] 的約 740；到了 [26] 經過最後的 norm，又回到約 100。第 6 章（Q5）用 [26] 做句子向量，第 9 章（Q7）把只在 block 20 輸出上校正過的 SAE 拿去量別的索引（Q7.4–7.6 預設量 [24]，Q7.7–7.9 逐一量 [0] 到 [26]），都要記得這個尺度差異。

另一個值得先記下的現象：<bos> 的範數在 [5] 到 [20] 大約是其他 token 的 10 倍（[5] 約 11 倍、[20] 約 9 倍），之後倍數變小（[25] 約 6 倍），norm 之後的 [26] 兩者就差不多了。第 7 章「大家都注意 <bos>」（attention sink）與第 8 章「<bos> 有很大的 SAE activation」，和這件事可能是同一個現象的不同面向；這是推論，本機沒有直接證明三者的因果關係。

  • 評分模型在 CPU：Q1 的 cross-encoder/ms-marco-MiniLM-L-6-v2 在 hw3.py:89 載入時沒有 .to(DEVICE)，calculate_coherence（hw3.py:65–70）的輸入也沒有搬到 GPU，所以它整個跑在 CPU 上，不佔 GPU 記憶體。第 1 章會再看這個函式。
  • Q1 之後一直多出來的一點：Q1 跑完後，allocated 從 4.87 GiB 變成 4.95 GiB，其中 0.054 GiB 是 model.generate 留在 model._cache 的 HybridCache（同一份 log 每題那一行的 model._cache 0.054 GiB (max_cache_len 544)）。它會被後面的題目沿用，這正是第 5 章「設了 seed 為什麼還不一定一樣」的主角，這裡先不展開。

那需要多大的 GPU？本機用的是 23.9 GiB 的卡，遠超過需要。依上表的峰值 5.26 GiB，再加上 PyTorch 自己保留、沒有分配出去的部分（載入後 reserved 比 allocated 多約 0.2 GiB），推論約 6 GiB 顯示記憶體的 GPU 就跑得動這份作業。這是從紀錄推出來的，本機沒有在 6 GiB 的卡上實際跑過。

0.11　常見錯誤

把兩個 soft-cap 混在一起

症狀
說「logits 被 cap 在 50」或「attention 分數 cap 在 30」。
後果
解讀 Q2 的 logit 數值（例如 24.125）或 Q6 的 attention 時，對不上上限。
正解
attention 分數是 attn_logit_softcapping = 50，在每一層的 attention 裡；最後的 logits 是 final_logit_softcapping = 30，在 lm_head 之後。實測 logits 最大絕對值 26.16 < 30。

把 lm_head 再算一次

症狀
手算總參數得到 3,204,165,888，和 PyTorch 的 2,614,341,888 對不上。
後果
多算了一張 256000 × 2304 的表，也會高估記憶體。
正解
tie_word_embeddings 為 True，lm_head 與 embed_tokens 是同一塊記憶體，只算一次。

把 hidden_states 的索引當成 block 編號

症狀
想拿 block 20 的輸出，寫成 hidden_states[20]。
後果
拿到的是 block 19 的輸出；Q7 正是這樣差了一層（第 8 章）。
正解
block k 的輸出是 hidden_states[k+1]；[0] 是 embedding × 48，[26] 是最後 norm 之後。

以為評分模型也在 GPU 上

症狀
看到 Q1 要 10.7 s，以為是 GPU 慢；或替評分模型預留 GPU 記憶體。
後果
錯估瓶頸與需要的顯示記憶體。
正解
評分模型（cross-encoder）跑在 CPU，hw3.py 沒有把它搬上 GPU。Q1 的 10.7 s 還包含從快取載入它的時間。

以為 --q 會照題號排序

症狀
下 --q 4 1，以為會先跑 Q1。
後果
題目間共用同一個模型物件，順序不同，前一題留下的狀態就不同，Q4 的取樣結果可能跟著變（第 5 章）。
正解
for q in args.q 照你寫的順序跑；要和書中紀錄比對，用和紀錄相同的指令。

在 WSL 裡沿用 Windows 的 HF 登入

症狀
Windows 那邊登入過 Hugging Face，WSL 裡跑 hw3.py 仍然下載不到模型。
後果
卡在授權，以為授權還沒核准。
正解
token 存在 WSL 自己的 ~/.cache/huggingface/token，在 WSL 裡再 .venv/bin/hf auth login 一次，或設 HF_TOKEN。

  • hw3.py 的骨架：QUESTIONS 把題號對到 q1…q7，main 解析旗標、設 seed、登入 HF、載入一次模型，再照 --q 的順序逐題呼叫；圖一律存到 HW03/outputs/。
  • 每題的旗標與預設值見 0.3 節的總表；--num-samples 至少 2，--sae-layer-idx 是 hidden_states 的索引。
  • load_model 用 fp16、device_map="cuda"、eval() 載入 google/gemma-2-2b-it，佔 4.87 GiB；attn_implementation="eager" 在 transformers 4.47 本來就是預設，寫明是為了 Q6。
  • Gemma-2-2b-it：embedding × 48 → 26 層（偶數 sliding、奇數 global）→ 最後 norm → 與 embedding 共用權重的 lm_head → soft-cap 30。每層四個 RMSNorm、GQA 8 對 4、head_dim 256、attention soft-cap 50、MLP 9216。
  • 總參數 2,614,341,888 = 26 × 77,865,984 + 2,304 + 589,824,000，手算與 PyTorch 一致。
  • hidden_states 有 27 個：[0] 是 embedding × 48，[i] 是 block i−1 的輸出，[26] 是最後 norm 之後。
  • 七題合計 39.0 s，Q4 最慢；GPU 記憶體峰值 5.26 GiB（Q7）。

下一章是補充章：生成時模型記住了什麼（KV cache）。它在第 1、5、7 章都會用到，所以先講。之後從 Q1 開始：同一個問題，套不套 chat template，模型看到的 token 與回答有什麼不同。

自我測驗

1. Q7 預設用 hidden_states[24]。它是哪一個 decoder block 的輸出？如果要拿「最後一個 block（layers[25]）未經 norm 的輸出」，該用哪個索引？

hidden_states[24] 是 layers[23]（block 23，0 起算）的輸出，因為索引比 block 編號大 1。layers[25] 的原始輸出不在 hidden_states 裡：[26] 是它經過 model.norm 之後的結果，[25] 則是 layers[24] 的輸出。要拿 layers[25] 的原始輸出，只能自己在 layers[25] 掛 forward hook。

2. 有人把 embed_tokens、lm_head 和 26 層、最後 norm 的參數全部加起來，得到 3,204,165,888，和 PyTorch 印的 2,614,341,888 不同。差在哪裡？

差 589,824,000，正好是一張 256000 × 2304 的表。tie_word_embeddings 為 True，lm_head 與 embed_tokens 是同一塊記憶體（實測 data_ptr 相同），model.parameters() 只回傳一次，所以 PyTorch 的總數只算一次。

3. Q2 印出的 logit 有 24.125、25.312 這類數值。Gemma-2-2b-it 的 logits 有可能是 35 嗎？attention 分數（softmax 之前）有可能是 60 嗎？

都不可能。logits 在 lm_head 之後經過 30·tanh(x/30)，值域是 (−30, 30)；attention 分數在每層經過 50·tanh(s/50)，值域是 (−50, 50)。兩個上限不同：logits 是 30、attention 是 50。實測一句 13 個 token 的話，logits 絕對值最大是 26.16。

4. 執行 .venv/bin/python HW03/hw3.py --q 6 3：模型載入幾次？哪一題先跑？圖存到哪裡、檔名是什麼？

模型只在 main 裡載入一次（hw3.py:514）。照 --q 給的順序，先跑 Q6 再跑 Q3。Q6 用預設 --layer-idx 10 --head-idx 7，圖存到 HW03/outputs/q6_attention_L10_H7.png；Q3 沒有圖。

5. 每一層的 k_proj 只輸出 1024 維，q_proj 卻輸出 2048 維。8 個 query head 要算 attention 時，各自的 key 從哪裡來？

這是 GQA：1024 = 4 組 × 256，只有 4 組 key／value。transformers 用 repeat_kv 把每組複製給 2 個 query head 共用，湊成 8 組再算 q·kᵀ。這讓每層的 k_proj、v_proj 參數各少一半，26 層共省 122,683,392 個參數（計算值）。
